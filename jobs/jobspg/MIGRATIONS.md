# PostgreSQL jobs migrations

`Driver.Prepare` migrates only under `SchemaManagement: jobspg.ManageSchema`: it serializes replicas, migrates, binds the application catalog, validates the exact contract, and keeps an already prepared startup read-only against delivery tables. Saying nothing is `UnsetSchemaManagement`, which resolves to `VerifySchema`: startup then performs only fail-closed verification and never creates, migrates, or binds schema state. Run `Migrate` and `BindCatalog` from the deployment migration step before starting a verify-only process.

`jobspgfx.Application` derives the choice from its `Environment`. A `dev`, `local`, `test` or `ci` environment is a development or test profile and keeps the zero-configuration managed path; every other value, including an empty or misspelled one, is the production profile and verifies. Asking for `ManageSchema` from a production profile is refused unless `AllowManagedSchemaInProduction` is set, and an accepted override is recorded in the supplied `SchemaManagementDecision`. The lower-level `jobspgfx.Settings` and `jobspg.Spec` have no environment to read and verify until told otherwise. The rule is `[[D-101]]`.

`MigrationStatements` is the operator-managed path. Execute its statements in order, one statement per autocommit operation. Do not wrap the returned list in a transaction: it contains `CREATE INDEX CONCURRENTLY`. The schema version is advanced only after exact index validation and provenance stamping.

Every index this package declares is created by a version step and by nothing else, so changing what it declares takes a schema version: v6 is the step that creates the operational indexes a v5 schema is missing, and any later addition to `operationalIndexes` or `retentionIndexes` needs its own bump. A start-up on a schema that is already current writes nothing at all — no index is created, rebuilt or locked. A missing index is created by the upgrade; an operational index that exists with a different definition is refused rather than replaced, because it may be a deliberate change, while a drifted retention index is dropped and rebuilt `CONCURRENTLY` under its provenance comment. The rule, and the build-time guard that stops a declaration from changing without a version, is `[[D-138]]`.

When a start-up refuses with `schema mismatch`, the answer is a migration or a person — never dropping schema state. `deliveries` and `intents` hold queued invocations and retained records that no rerun reconstructs, and under `[[D-118]]` some of them were written inside the caller's own transaction, so `DROP SCHEMA ... CASCADE`, dropping either table or truncating it cancels work the application already committed to. The refusal is the safe state: it keeps every row while somebody decides. Read the named object out of the error, compare it against `MigrationStatements`, and fix that object.

Upgrading to v6 needs no operator step beyond the usual one: run `MigrationStatements` (or let a `ManageSchema` deployment migrate) and a v5 schema reaches v6, creating what it lacks. Plan it as a normal version rollout — once a replica has stamped v6, a replica still running a v5 binary refuses to start, by the same fail-closed rule that rejects any stored version above the build's own.

For a rolling upgrade from a v2 jobs binary, first deploy v4 with `jobspgfx.HousekeepingSettings{Disabled: true}`, drain every v2 replica, and then enable housekeeping. A running v2 process predates terminal tombstones and cannot safely share their lifecycle. Fresh v4 installations and fleets already fully on v4 use the default enabled housekeeping.

Each definition persists an application-owned codec high-water mark and its supported revisions. A newer deployment must keep every persisted revision readable. Older replicas may continue during a rolling deployment, but they never lower the high-water mark and their claim targets cannot select newer payloads. Queue policy changes are independent of the payload schema and do not require a codec version bump.

Codec identity, codec mode, partition mode, and payload identity are stable wire contracts. Changing one under the same definition name is rejected. Use a new stable definition name for an incompatible contract.

When upgrading an existing v3 catalog row, the first v4 process backfills compatibility metadata only when its definition fingerprint matches the last v3 binding. This fail-closed bootstrap prevents an unprovable wire-contract replacement. Once backfilled, policy-only rolling changes and monotonic codec upgrades use the compatibility metadata instead of the aggregate fingerprint.

Definition removal is not inferred from a smaller local catalog because an older replica must remain valid while a newer replica adds definitions. Keep retired definitions declared until their queued and retained records are drained and an explicit retirement mechanism is available. The `fingerprint` columns preserve bootstrap and high-water snapshots; they are not a live checksum of every policy used by every rolling replica.

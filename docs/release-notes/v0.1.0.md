# v0.1.0 release notes

## OpenTelemetry extension candidate

This release candidate adds the optional `github.com/frostgrove/vv/otel`
module (`vvotel`) for service command spans, storage spans, terminal cache
observations and a generated, privacy-reviewed schema.

- The root module and non-OTel modules remain free of OpenTelemetry dependencies.
- Applications inject providers and own SDK exporters, readers/processors,
  flush and shutdown.
- Unknown cache values and non-standard error codes are omitted; IDs, keys,
  URLs, payloads, messages and credentials are not telemetry attributes.
- Provider and instrument panics are isolated from business results, errors and
  panic semantics.
- `ContractVersion` is `vv-otel/v1`; `ScopeVersion` follows the lockstep OTel
  module version.

Publication is gated until the root `v0.1.0` and `otel/v0.1.0` tags are available
to the Go module proxy and both strict consumer checks pass. Logs, jobs
propagation, repository spans and outbox/messaging remain deferred.

## `event/projection` — `InUnit` now refuses a unit that binds two transactions

`Advance: InUnit` promises that the checkpoint advance and the handler's writes
commit together. Until now the framework checked as far as "the unit bound a
transaction for the checkpoint store" and "the unit bound a transaction for
`Destination`", and never that the two were **the same** transaction. A
composition that opened one transaction per resource passed both checks and
quietly delivered `AfterApply` atomicity under an `InUnit` spec — a crash between
the two commits leaves one of them.

The two authorities are now compared for identity inside the unit, before the
handler runs, on every pass.

**What changes for a deployment.** A shipped spec whose `Unit` binds one
transaction for `Destination` and another for the checkpoint store used to run;
it now **halts** on its first pass with `ErrSpec` naming the projection, without
reaching the classifier and without downgrading. Two remedies, and they are the
whole set:

- bind both to one transaction — `crud.InNewTx(ctx, source, work)` over the
  source the checkpoint store lives in, with the handler writing through the
  context the unit gave it; or
- say `Destination: projection.Unchecked`, which is the composition stating out
  loud that the handle cannot be resolved through `crud`'s binding, and which
  makes no comparison at all.

An `Advance: AfterApply` spec is untouched, and so is an `InUnit` spec that was
already aligned.

## `event/projection` — a partitioned runner filters its pages, and only the first start chooses a topology

`Spec.Partition`, `Spec.Sequence` and `Spec.Generation` arrive together with
`Cover`, `Identity`, `Partition` and the four sequencers. Every zero value is
what a projection that exists today already is — `Whole()`, `ByStream()`,
`Ungenerated`, which renders nothing — so no name and no checkpoint row moves
because these fields exist.

**What changes for a deployment.** Nothing, unless a spec names a partition. One
that does reads only the envelopes its mask matches, keyed by `Spec.Sequence`,
and is **refused at its first resume** when a checkpoint row for a coarser share
of the same key space is live — which is exactly what "add `Partition:` to the
spec and deploy" is. The refusal is `ErrTopology` naming the row it found; the
supported route from a projection that has run is a split, which hands the
parent's cursor to its children and retires the parent.

A projection name carrying `@` or `#` is refused at construction, and so is one
the kernel's identifier rule refuses — an empty name, one over
`event.MaxNameBytes`, invalid UTF-8, a control character, a bracket. `orders.v2`
and `orders/paid` are unaffected.

## `event/projection` — `Split` is the route from one partition to two

`projection.Split(ctx, SplitSpec{Checkpoints, Identity, Unit})` answers the two
identities a `Cover` is then declared from. One partition becomes two, both
starting at the parent's exact cursor and carrying its `Progress.Highest`, and
the parent's row is retired — four writes inside the transaction **you** open, on
your goroutine, through the `event.Track` door. The lower-numbered child takes the
parent's `Applied` and `Quarantined` and the higher starts at zero, so the sum
across the set is unchanged.

Drain the parent first: a running parent whose row is split away finds it absent
at its next save and halts, which is what retiring a live row has always done. A
parent with no row at all is refused with `ErrTopology` — a partition that never
ran and one whose row was lost read alike from the rows, and guessing "fresh"
starts two children at the origin against a live read model — and so is a child
row that is already there beside a live parent. There is no merge.

**A split is one way, and the thing a deploying team has to know is what happens
if you put the previous release back.** The fourth write is the record of the
retirement: a checkpoint row named `<identity>#split`, carrying the cursor the
parent was handed down from. Redeploying the spec that ran before the split —
release *n*, with no `Partition:` — is refused at its first resume with
`ErrTopology` naming that row. Without it that release would find no row of its
own, resume from the origin and walk the whole log again into the read model the
live children are filling, with every row reporting a healthy watermark while it
happened. The way back to one runner over that share is a new generation;
forgetting the `#split` row is the deliberate act that re-admits the old topology,
and the refusal says so. A projection name within six bytes of `event.MaxNameBytes`
has no room for the mark and `Split` refuses it rather than retiring a share it
could not record.

## `event/eventtest` — `RunCheckpoints` dispatches fourteen sections

A store that certified twelve is now asked two more, and they are what a split
rests on. **`topology` is mandatory**: a cursor written under one projection name
must read back unchanged under another, and a save at advance 1 over a live row
must be refused by the store's own fence. **`topology handoff`** runs for a store
claiming `Transactions` and asks that a `Load`, two `Save`s at advance 1 and a
`Forget` inside one caller-opened transaction are all or nothing.

**What changes for a store author.** A third-party `event.Checkpoints` that
passed twelve sections is measured on fourteen. Neither shipped store needed a
change: `eventmemory.Checkpoints` certifies thirteen and goes on declining
`durability`, and `eventpg.Checkpoints` certifies fourteen. Nine more defects
join the suite's own falsification inventory, which now stands at fourteen — one
per section but `durability` — and a second test asserts the direction that was
missing: every section is named by a defect that breaks it, so a section whose
body is gutted is reported rather than passing everywhere.

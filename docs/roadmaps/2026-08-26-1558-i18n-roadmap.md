# Internationalization roadmap — 2026-08-26 15:58 +05

This roadmap proposes full application internationalization for vv without
mistaking translation for error formatting or moving a global i18n framework
into the dependency-free root module. It covers locale negotiation, catalogue
loading, ICU/CLDR-grade plural/select semantics, typed message references,
transport rendering, tenant/user preference, translation release management and
the cross-cutting privacy/audit/telemetry implications.

## Architectural decision

[[D-048]] is binding: `i18n` is refused as a root subsystem because the current
`errs.MessageSource` and on-disk catalogue are the right-sized solution for
localized errors today. Stdlib-only i18n cannot supply CLDR plural rules; the
day full i18n exists it is an external-dependency satellite. The root continues
to carry no `golang.org/x/text`, global locale state or generic translation
contract.

The likely module split is:

| Module | Consumer decision | Role |
|---|---|---|
| root `errs` | current stdlib error code/message source | stays unchanged |
| `vv/i18n` | choose vv full i18n + `golang.org/x/text` | catalogue/message/locale satellite |
| `vv/i18nhttp` | choose/own HTTP boundary policy | optional transport bridge |
| `vv/i18ngrpc` | choose/own gRPC metadata policy | optional transport bridge |
| `vv/i18notel` | choose OTel bridge | future stable-code-only observability |

The satellite isolates one decision: consumer wants full i18n rules. It must not
also select a web router, template engine, database, translation SaaS, feature
flag service, log backend or user-profile store. Under [[D-051]], each of those
is another decision owned by the host or another narrow adapter.

## Product intent

The safe application path should make it hard to use human strings as program
identifiers and easy to give a user one culturally correct message:

```go
locale := i18n.Resolve(ctx, i18n.Request{
    Supported: []language.Tag{language.English, language.Kazakh, language.Russian},
    Default: language.English,
})

text, err := catalog.Format(locale, i18n.Message{
    ID: "orders.validation.quantity_positive",
    Args: i18n.Args{"quantity": quantity},
})
```

The API sketch is not committed. Its non-negotiable properties are:

- application/domain code uses stable message IDs and typed/bounded arguments;
- locale is explicit/context-derived, never a process-global mutable setting;
- language negotiation uses declared supported/default/fallback policy;
- formatting follows declared plural/select rules, not English singular hacks;
- a missing/broken translation follows a safe policy chosen at bootstrap;
- raw translation text/arguments do not leak into OTel metrics/traces or audit
  unintentionally;
- errors keep stable codes and `errs` semantics; localization is rendering;
- content written by users is data, not a translation catalogue entry;
- catalogue/schema changes are versioned/reviewed like a public contract.

- [Go `golang.org/x/text/message`](https://pkg.go.dev/golang.org/x/text/message)
- [BCP 47 language tags](https://www.rfc-editor.org/rfc/rfc5646)
- [Unicode CLDR plural rules](https://cldr.unicode.org/index/cldr-spec/plural-rules)
- [ICU MessageFormat](https://unicode-org.github.io/icu/userguide/format_parse/messages/)

These sources guide language/tag/plural semantics. The project must select a
message syntax/compile strategy in an ADR before public adoption; “we support
translations” is not a sufficient specification.

## Vocabulary

| Term | Meaning |
|---|---|
| language tag | canonical BCP 47 tag such as `en`, `kk`, `ru`, `pt-BR` |
| locale | resolved language plus any explicitly supported formatting policy |
| catalogue | immutable versioned map of message IDs/templates for one language |
| message ID | stable machine-facing key, never localized copy |
| template | translation source with declared argument/plural/select grammar |
| fallback | deterministic lookup to default/base language or safe code |
| negotiation | resolving requested tags against supported application tags |
| formatter | parser/compiler that turns template + typed args into text |
| translation release | reviewed coherent catalogue version published together |
| pseudolocale | test locale exposing hard-coded strings/overflow/concatenation |

## Invariants

1. **Stable code before text.** Domain/errs code remains canonical; text is a
   locale-specific projection and never used for control flow.
2. **No global current locale.** All rendering accepts a tag/context resolver;
   concurrent requests/users cannot affect each other.
3. **Closed catalogue at release.** Runtime does not download/edit arbitrary
   translations in a request path or accept template content from users.
4. **Format data is untrusted.** Arguments are typed/escaped/size-bounded for
   output context; formatter never creates HTML/SQL/URL safety by implication.
5. **Fallback is visible.** Missing translation is observable by bounded ID/
   language-family counters but does not expose message arguments.
6. **Errors retain existing ownership.** `errs.MessageSource` continues until
   an explicit adapter maps stable error code/key into the i18n catalogue.
7. **No i18n in root policies.** Authorization, storage keys, event types,
   schema names, audit action codes and telemetry enums never localize.
8. **Locale is not tenant identity.** Locale selection can consider a preference
   only after policy, but it never selects a database/bucket or authorizes data.
9. **Catalogues are executable artefacts.** Build/test validates syntax, IDs,
   args/plural coverage/fallback before deployment.
10. **Translation is not user content CMS.** Localized product content needs its
    own domain/version/authoring/audit model, not static error catalogue APIs.

## Locale resolution precedence

The host chooses a resolver policy explicitly. A conservative HTTP application
example is:

1. authenticated user's validated saved preference, if access/policy permits;
2. explicitly supplied application request preference;
3. accepted `Accept-Language` values, parsed with q weights and limits;
4. tenant/application configured default, if such setting is safe/authorized;
5. service default language.

Invalid/malicious headers/preferences never become raw errors/telemetry labels.
The resolver maps them to supported tags or fallback and returns provenance as a
bounded enum (`user`, `request`, `header`, `tenant_default`, `service_default`)
only where an application genuinely needs it. `Accept-Language` is a preference,
not a security claim and not a guarantee that translation exists.

## Message model decision points

| Choice | Requirement |
|---|---|
| IDs | ASCII-like namespaced stable keys with reserved/deprecation policy |
| source format | selected/compiled at build time; no per-request parse if avoidable |
| arguments | declared names/types per message; unknown/missing args fail safely |
| plural | CLDR cardinal/ordinal support where message declares it |
| select/gender | explicit only; do not infer user gender from profile text |
| escaping | renderer-specific (plain/HTML/JSON); no universal “safe string” |
| fallback | deterministic tag/message fallback and developer/operator signal |
| catalogue load | embedded or caller-owned `io/fs`, immutable after bootstrap |
| reload | defer; dynamic reload needs atomic/version/security design |
| user copy | separate domain, not catalogue |

## Cross-roadmap synergy

| Domain | i18n contribution | i18n must not do |
|---|---|---|
| `errs` | render stable code/message key at boundary | replace codes/error identity |
| OTel | bounded error code/outcome remains language-neutral | record text, args or locale label |
| audit | may store message ID/action code if useful | store translated snapshot by default |
| event source | event type/schema uses stable IDs; projections may render later | persist localized human text as event authority |
| tenancy | tenant may supply allowed default locale policy | route/select tenant/data source |
| storage | localized filename/display labels stay domain data | localize opaque storage key/path |
| API | docs can localize descriptions separately/versioned | localize wire enum/code values |

## I-01 — satellite bootstrap and immutable catalogue ownership

**Decision.** `vv/i18n` receives caller-selected catalogue source and supported
language set at bootstrap, parses/validates all declared artefacts before
traffic, then exposes an immutable formatter/resolver dependency. It does not
read current directory, environment locale, network translation service or
global `message` printer behind the caller's back.

### Top-level declarative DX

```go
catalog, err := i18n.New(i18n.Config{
    Source: i18n.FS(embedFS),
    Supported: []language.Tag{language.English, language.Kazakh, language.Russian},
    Default: language.English,
    Missing: i18n.FallbackToDefault,
})
```

### Happy use cases

1. Service embeds three reviewed catalogue files, validates them at startup and
   serves concurrent requests from immutable compiled structures.
2. A test injects an in-memory `io/fs` catalogue with one language/ID and
   exercises formatting without process locale or network dependency.
3. A CLI configures English default and Russian supported tag; its locale comes
   from explicit command option/context, not developer workstation settings.
4. Two services in one process build distinct catalogues/defaults safely without
   changing shared global x/text/message registration state.
5. Bootstrap prints safe catalogue version/language counts to application logs;
   it does not print full translations or source filesystem paths by default.

### Edge use cases

1. Catalogue has duplicate ID, unsupported tag, invalid syntax or argument
   declaration mismatch. Bootstrap fails deterministically before serving traffic.
2. Default language catalogue is missing a required message. Strict bootstrap
   refuses because fallback would hide a deployment defect.
3. A catalogue file is world-writable or loaded from untrusted mounted path.
   Caller/infrastructure owns filesystem security; i18n docs require immutable
   deployment source and do not auto-watch/reload it.
4. A source returns enormous file/ID set. Loader applies byte/count/depth limits
   before parse/compile and emits safe configuration error.
5. One service needs dynamic translation updates. First release refuses; later
   reload must use signed/versioned atomic catalogue swap with audit/rollback.
6. Host uses global x/text printer elsewhere. vv/i18n instance remains isolated;
   it never registers or changes global message catalogues.

### Invariants and acceptance evidence

- root module has no `golang.org/x/text` import or i18n config;
- two concurrent catalogues/tests prove no global mutable locale/catalogue state;
- invalid corpus fails before route/worker starts and reports no translation text;
- all supported/default/fallback rules are in one immutable config snapshot;
- embedded and caller-owned `io/fs` sources pass same loader conformance suite.

### First implementation slice

Implement catalogue manifest/loader/validator before a rich template language.
Start with message IDs and plain templates only if necessary, but reserve the
schema for declared arguments/plural forms so a later formatter does not break
all existing IDs.

## I-02 — language tags, negotiation and fallback

**Decision.** Resolve a requested ordered set of BCP 47 tags against a declared
supported set using `golang.org/x/text/language` semantics. Resolution result is
one canonical supported tag plus a bounded source/fallback classification; raw
header/preference strings never escape the boundary.

### Top-level declarative DX

```go
locale := resolver.Resolve(ctx, i18n.Preference{
    User: "kk-KZ",
    Header: acceptLanguage,
})
```

### Happy use cases

1. `kk-KZ` matches configured `kk` when regional catalogue is absent and policy
   permits base-language fallback.
2. Header `ru-RU,ru;q=0.9,en;q=0.5` resolves Russian from configured supported
   tags with correct quality ordering and deterministic tie policy.
3. Authenticated profile prefers `en-GB`; app supports `en`, so resolution picks
   documented base/default instead of returning an invalid unsupported tag.
4. A background job has no request/user preference and consistently uses service
   default rather than machine environment locale.
5. Application passes locale explicitly for an e-mail/report generation task;
   rendering is independent from unrelated current HTTP request context.

### Edge use cases

1. Header has 10,000 ranges/invalid q values/control characters. Parser limits
   count/bytes, rejects/safely ignores invalid input and falls back without echo.
2. User profile contains obsolete/unsupported language tag. Resolver gives
   declared fallback/source classification; it does not mutate profile silently.
3. A tenant default conflicts with a user's allowed preference. Host policy sets
   precedence; i18n resolver receives already-authorized inputs, not tenant data.
4. Requested tag could imply script distinctions (`zh`, `sr`, etc.). Supported
   set/matcher behavior is recorded/tested; no naive string prefix matching.
5. Locale intentionally affects number/date format but message language falls
   back. API either separates language/format locale explicitly or documents one
   canonical resolution; do not create accidental hybrid text.
6. A request uses locale as a cache key/metric label. Integration maps only
   configured small language enum where approved, never raw tag/header.

### Invariants and acceptance evidence

- property corpus covers malformed/large headers and never panics/allocates
  unboundedly or returns unsupported internal tag;
- resolution is pure/deterministic for same config/preference inputs;
- background/CLI/HTTP contexts use one explicit policy, no OS environment read;
- raw preference values are absent from errors, traces, metrics and audit defaults;
- fallback events/counters use bounded language family/source values only.

### First implementation slice

Define `Resolver` independently from transports and catalogues. Use test vectors
for English, Kazakh, Russian and regional/invalid examples before offering HTTP
middleware; a router must not decide locale algorithm by accident.

## I-03 — message IDs, declared arguments and safe formatting

**Decision.** A message is a stable ID with a declared argument schema and one
template per supported language. Formatting receives typed values and an output
context selected by the caller. It is forbidden to use translated strings,
English default copy or dynamically constructed IDs for program control flow.

### Top-level declarative DX

```go
text, err := catalog.Format(locale, i18n.Message{
    ID: "orders.validation.quantity_positive",
    Args: i18n.Args{"quantity": int64(0)},
})
```

### Happy use cases

1. One validation ID formats English, Kazakh and Russian copy with the same
   declared `quantity` argument name/type.
2. Application checks stable validation/error code then asks formatter for text;
   translated copy can change without changing branch condition or API enum.
3. A message declares string, number, date and select/plural arguments. Compiler
   validates every language template uses a compatible schema before release.
4. Plain text API returns plain text. HTML renderer receives a distinct escaped
   rendering policy so no `SafeHTML` is implied by translation data.
5. A template argument is absent. Formatter returns typed catalogue/argument
   failure or safe configured fallback, rather than substituting Go `%!s` noise.
6. A translator reorders placeholders for grammar. Named arguments preserve
   semantic mapping; code does not depend on positional English word order.

### Edge use cases

1. Message ID is built from user input (`"product."+name`). API requires parsed/
   generated registry ID or returns unknown; dynamic IDs cannot grow catalogue
   lookup/log/metric cardinality.
2. Argument is a struct/map/secret-bearing error. Schema refuses unbounded raw
   values; app maps it to safe display value or keeps details out of message.
3. A translated template treats numeric argument as string/select differently.
   Catalogue compiler catches declared type mismatch before deployment.
4. Template includes HTML/script/URL context. Plain formatting does no implicit
   escaping; renderer-specific API encodes every arg and review owns template
   trust/translator access.
5. Argument value is huge/unicode-invalid. Formatter applies length/type limits
   or returns safe format error; it never causes unbounded result allocation.
6. A missing ID occurs in error handling. Safe fallback returns stable code/
   controlled developer marker without leaking runtime args to user/telemetry.
7. Translator accidentally changes a machine-facing JSON field value. Wire data
   never comes from catalogue; only explicitly human-facing fields are localized.

### Invariants and acceptance evidence

- generated/validated manifest lists all IDs, args, types and source locations;
- compile test rejects missing/extra/wrong-type args in every language template;
- hostile args corpus proves no HTML/JSON/log/trace injection through format path;
- message-ID reference search finds no code branch comparing localized text;
- format result limit/failure semantics are deterministic and documented.

### First implementation slice

Choose one template grammar with CLDR-compatible plural/select support and a
build-time compiler. Avoid a generic `fmt.Sprintf` wrapper: it cannot validate
translator argument usage or plural grammar as a catalogue contract.

## I-04 — plural, select and culturally correct format rules

**Decision.** Full i18n uses CLDR language rules through selected external
library/compiler. Code passes semantic count/selector values; templates select
the grammatical form. English `one/other` is never assumed to represent Kazakh,
Russian or future supported languages.

### Top-level declarative DX

```go
text, err := catalog.Format(locale, i18n.Message{
    ID: "orders.items_selected",
    Args: i18n.Args{"count": count},
})
```

### Happy use cases

1. English, Kazakh and Russian templates render their own cardinal plural form
   for selected count values from the same typed integer argument.
2. A user-facing date/number is formatted through resolved locale policy rather
   than a hard-coded `fmt.Sprintf` in a handler.
3. A select expression uses a bounded domain state (`draft`, `published`) with
   default branch; code retains stable enum/state separately from translated text.
4. A scheduled report passes explicit locale and time zone policy, rendering
   consistent number/date text independent of worker host locale.
5. Template compiler validates every plural/select branch required by the chosen
   syntax and provides a readable build error with message ID/language only.

### Edge use cases

1. Count is negative, fractional or too large. Message schema declares accepted
   numeric form; formatter does not silently coerce a domain-invalid value.
2. Translator misses Russian plural category. Strict catalogue build fails, not
   runtime fallback that users discover later.
3. Locale is unsupported but base language template exists. Resolver/fallback
   chooses documented tag; formatting does not invent rules from header string.
4. Select value is untrusted user text. Schema maps it to bounded enum/default;
   raw value is never reflected as template branch/format error.
5. Date has no time zone. Caller must provide stable instant/zone convention; the
   i18n formatter cannot guess tenant/user time zone from language tag.
6. An application demands currency conversion. Formatting may format a supplied
   currency amount; exchange rate/conversion is a separate financial contract.

### Invariants and acceptance evidence

- plural test matrix includes representative zero/one/two/few/many/other cases
  for every supported language, not English-only snapshots;
- date/number tests use fixed time zone/clock and explicit locale;
- raw selector/count/format error values never reach telemetry by default;
- adding a language cannot ship without its plural/select validation corpus;
- all formatter output is treated as presentation, never stable API data.

### First implementation slice

Support cardinal plural and number formatting first. Defer gender/ordinal/date
richness until a real use case selects exact grammar and template syntax; the
catalogue manifest still reserves explicit extension/version fields.

## I-05 — error rendering bridge preserves `errs` ownership

**Decision.** Existing errors retain their code, status, wrapping and `errs`
message source behaviour. An optional adapter maps a stable error code/message
key to i18n message ID at the transport/application rendering boundary. No root
error method imports x/text or reads locale globally.

### Top-level declarative DX

```go
problem := errorshttp.Render(ctx, err, i18nErrorRenderer)
// machine fields use stable code; human detail/title uses resolved locale.
```

### Happy use cases

1. A conflict error returns same stable code/status in every locale while its
   human detail is translated from a declared error message mapping.
2. Existing `errs.MessageSource` catalogue continues rendering errors for users
   who do not import full i18n satellite; migration is opt-in and incremental.
3. HTTP/gRPC adapter resolves locale once at boundary, renders human message and
   preserves all transport-neutral service/repository error identity below it.
4. An error mapping uses only safe declared args such as bounded field label key,
   not raw rejected request value, SQL/driver error or principal data.
5. A missing translation uses configured safe fallback while response still has
   reliable code/status; clients never need to parse translated text.

### Edge use cases

1. Error wraps a driver string with secret SQL/bind data. Adapter extracts known
   public `errs` code only and refuses to format `err.Error()` as message arg.
2. An API client asks locale `zz-evil`. Resolver falls back; response does not
   echo requested tag or change code/status.
3. Transport has already written headers/body when formatting fails. Adapter
   follows ordinary renderer error path; no partial mixed-language response.
4. Error code has no i18n mapping during rollout. It returns stable generic safe
   title/detail/code and increments bounded missing-mapping diagnostic.
5. Developer wants localized validation field names. Field labels are separate
   declared IDs, not Go field/reflection names or attacker JSON paths by default.
6. A machine-to-machine API needs no human messages. Adapter can omit localized
   text entirely; importing i18n must not add translation overhead to core flow.

### Invariants and acceptance evidence

- same error has equal machine code/status/JSON shape across language tests;
- error identity/wrapping is unchanged before boundary renderer;
- raw error/message arguments corpus absent from response where not explicitly
  allowed and from OTel/audit/log defaults;
- legacy `errs.MessageSource` and full i18n bridge run side-by-side in fixtures;
- no `errs` package gains a dependency on full i18n satellite.

### First implementation slice

Add an external renderer adapter and migration table, not new root error methods.
Start with one error family and golden multilingual transport outputs, then prove
fallback/missing mapping before expanding every historical error code.

## I-06 — catalogue source format, compiler and manifest

**Decision.** A catalogue is source data plus a generated/validated manifest.
The repository chooses one translation syntax and compiles/parses it during
build/bootstrap, not in every request. The manifest is the authoritative list
of message IDs, arguments, languages, source locations, schema version and
deprecation state.

### Top-level declarative DX

```text
i18n check ./locales
i18n manifest ./locales > internal/i18n_manifest.json
```

### Happy use cases

1. A translator edits `orders.validation.quantity_positive` in Russian; CI
   compiles it, validates its `quantity` argument and records the source location.
2. A service embeds generated catalogue assets and manifest with the binary; no
   production filesystem mount/network request is necessary to render messages.
3. A test loads a minimal in-memory source and receives same parser/manifest
   validation as the embedded production source.
4. A new ID is added to default source with all required language translations;
   generated diff clearly shows its arguments and lifecycle state.
5. A catalogue supports comments/context for translators without making comments
   an application output or runtime lookup value.
6. Build step produces deterministic byte-for-byte manifest for same sources,
   making review/source control and release comparisons meaningful.

### Edge use cases

1. Two language files define same ID with incompatible argument names/types.
   Compiler fails before package/test/deploy rather than choosing one arbitrarily.
2. A source parser has nested template/deep recursion/large literal attack. It
   applies file/template/depth/output limits before allocation grows unbounded.
3. Translator adds a new ID only in non-default language. Strict policy fails;
   fallback policy must never make a foreign-only ID an accidental public API.
4. Source is UTF-8-invalid or contains unexpected BOM/control characters. Loader
   uses declared encoding/normalization rule and reports safe location/ID error.
5. A code change removes an ID still used by an old binary during rolling deploy.
   Manifest/release check marks it deprecated until compatible readers retire.
6. Generated manifest itself is stale after source edit. CI compares source hash/
   manifest output and fails instead of shipping mismatched artefacts.
7. A catalogue uses remote translation SaaS export. Host fetches/commits/signed
   artifact in CI; runtime satellite does not hold SaaS credentials or webhooks.

### Invariants and acceptance evidence

- one compiler/validator path handles every catalogue source implementation;
- source/manifest checksum and ID/argument diff are CI-visible release artefacts;
- parser fuzz corpus never panics, loops or emits partial catalogue on failure;
- codegen/import graph leaves root `errs`/vv without i18n external dependency;
- catalogue artefacts contain no production user data, secrets or runtime values.

### First implementation slice

Decide syntax and write a standalone `check` command that validates IDs and
argument schema. Do not expose live format API before the team can detect a
broken translation in CI with a precise source location.

## I-07 — missing message, missing translation and fallback policy

**Decision.** Missing ID and missing locale translation are different defects.
The first is normally a programmer/release error; the second can use a declared
fallback chain. Both return a controlled result, increment bounded diagnostics
and never expose raw args/template internals to end users by accident.

### Top-level declarative DX

```go
catalog, err := i18n.New(i18n.Config{
    MissingMessage: i18n.FailClosed,
    MissingTranslation: i18n.FallbackToDefault,
})
```

### Happy use cases

1. Supported `kk` translation exists and renders directly; no fallback counter
   increments and response uses resolved Kazakh language.
2. `pt-BR` resolves to supported `pt`, then message uses Portuguese base template
   under documented matcher policy.
3. A message lacks `ru` but default English has it; renderer returns English
   text with bounded fallback state observable to release owners.
4. A program asks unknown ID. Strict formatter returns typed missing-message
   error, letting boundary render stable generic code/detail safely.
5. A machine-to-machine response chooses no human text and still carries normal
   stable error code/status even if translation would be missing.
6. A staging environment uses visible developer fallback marker/pseudolocale;
   production policy uses user-safe default language without stack/template text.

### Edge use cases

1. Default translation is malformed at runtime due corrupt asset. Construction
   should already prevent it; defensive runtime path returns controlled failure.
2. Fallback template needs args that requested template did not declare. Manifest
   schema validation prevents this incompatible language drift at build time.
3. A cascade `zh-Hant-TW -> zh-Hant -> zh -> en` is too long/missing. Resolver
   has bounded deterministic chain and reports only final safe fallback class.
4. Missing ID is triggered by attacker-controlled dynamic ID. Error/telemetry
   records bounded `unknown_message`, not raw requested string/cardinality leak.
5. Translator intentionally leaves a message untranslated with marker. Policy
   treats it as absent/fallback or CI failure; it never returns marker to users.
6. Default catalogue is removed during hot reload proposal. First release has no
   reload; later atomic swap validates complete fallback set before activation.

### Invariants and acceptance evidence

- tests distinguish missing ID, unsupported locale, missing translation and
  malformed template outcomes;
- production fallback never returns formatter exception, template source or args;
- fallback metrics use finite configured language/source/message-family enums;
- every fallback chain test is deterministic and bounded in steps/allocation;
- service/error functional result is unchanged when i18n formatter is disabled.

### First implementation slice

Implement strict missing-ID plus default-language fallback for full catalogue.
Expose a safe format result/error type; defer runtime reload and partial language
shipping policy until basic release artifact validation is reliable.

## I-08 — renderer-specific escaping and output safety

**Decision.** Translation syntax is not an output escaping policy. Plain text,
HTML, JSON, e-mail subject/body, CLI and document rendering use distinct
renderers/encoders. Templates are trusted reviewed deployment assets; arguments
are untrusted data and must be handled in the output context that owns them.

### Top-level declarative DX

```go
plain, err := catalog.FormatText(locale, message)
html, err := catalog.FormatHTML(locale, message, htmlRenderer)
```

### Happy use cases

1. Plain validation message receives user-supplied name as plain text and an HTTP
JSON encoder safely serializes resulting string in response body.
2. An HTML e-mail renderer escapes each string argument for HTML text context;
template/language file is reviewed as trusted rich-content source if HTML allowed.
3. A CLI uses plain formatter and displays Unicode text without HTML escaping
  artifacts or global locale mutation.
4. An API returns stable code/argument-safe field identifier and optional text;
  clients choosing their own locale do not parse server HTML/text for behavior.
5. A document/PDF renderer owns typography/font/line-break rules after it receives
  formatted text; catalogue does not claim visual layout correctness.

### Edge use cases

1. Argument contains `<script>`, quote, bidi control, JSON delimiter or URL.
   Renderer-specific golden tests verify it cannot inject markup/structure there.
2. Translator puts argument into an HTML attribute/URL/JS context. First release
   forbids rich templates or requires distinct context-aware template review;
   generic HTML escape cannot make arbitrary placement safe.
3. Template itself contains unsafe markup introduced by compromised source. Build
   source review/signing/trusted access is the control; runtime can't infer intent.
4. Caller formats an error then logs it. Log sink policy owns redaction; i18n does
   not treat localized text as safe for secrets if args policy was violated.
5. Output expansion creates huge text from one small arg/template. Compiler/
   formatter caps template/result size and returns safe failure class.
6. A display string is reused as database key, URL slug or storage key. Code
   review/static examples forbid it; formatting results are presentation only.

### Invariants and acceptance evidence

- plain/HTML/JSON/context tests are separate, never one generic `SafeString`;
- hostile argument corpus covers markup/control/Unicode/large-value cases;
- rich template allowance has explicit source trust/translator review policy;
- formatted output never becomes an authorization/persistence/telemetry enum;
- escaping failure never causes raw template/argument disclosure in response.

### First implementation slice

Ship plain text only unless a real HTML/e-mail/document use case supplies a
renderer-specific threat model. Make it impossible to imply that a catalogue
template gives generic XSS/JSON/URL safety.

## I-09 — transport boundaries and locale propagation

**Decision.** HTTP, gRPC, CLI, background jobs and webhooks resolve locale at
their own trusted boundary and pass a resolved locale/context into application
rendering. `vv/i18n` remains transport-neutral; protocol adapters are optional
satellites and must not change business/service error semantics.

### Top-level declarative DX

```go
// http adapter: resolve preference once, attach resolved Locale to ctx.
ctx = i18n.WithLocale(ctx, resolved)
response := renderer.Render(ctx, err)
```

### Happy use cases

1. HTTP adapter parses bounded Accept-Language and profile preference, resolves
   once, then renderer translates public error title/detail at response boundary.
2. gRPC server maps a verified/declared locale metadata value to context and
   serializes stable status/code independent from localized message wording.
3. CLI accepts explicit `--locale=ru`, validates it against supported set and
   renders output without HTTP dependencies.
4. A scheduled job/e-mail command carries an explicit locale argument chosen by
   domain preference policy, preventing stale request context leakage.
5. Webhook integration uses stable machine event/code; human diagnostic text is
   either omitted or explicitly rendered in partner-agreed locale.
6. Nested service calls see same resolved locale context but do not themselves
   negotiate headers or invoke formatter on every internal error.

### Edge use cases

1. A malformed locale carrier is too long. Adapter applies limit before parser
   and responds according to fallback policy without echoing carrier text.
2. Invalid authentication must not become anonymous locale preference. Auth
   boundary preserves normal failure; locale fallback is not an auth bypass.
3. A message is rendered after response transport has committed headers. Adapter
   follows normal safe generic error path and avoids partial/mixed response body.
4. A background goroutine inherits request context incorrectly. Worker contract
   requires explicit locale/job input; i18n never stores global last locale.
5. External caller sends locale as a privacy/correlation probe. Trace/metrics
   avoid raw carrier values and response does not reveal unsupported catalogue set.
6. Different transports choose different fallback policy. Each adapter declares
   it; common catalog formatting remains deterministic for supplied resolved tag.

### Invariants and acceptance evidence

- core i18n package imports no router, HTTP, gRPC or CLI implementation;
- external package integration tests prove stable wire code/status across locales;
- malformed/oversized carrier corpus has no panic/value leak/global mutation;
- request/job/webhook fixtures prove locale does not cross concurrent boundaries;
- disabling adapter leaves service/repository/domain behavior byte-for-byte same.

### First implementation slice

Write transport-neutral resolver/context and an HTTP reference adapter only after
the resolver corpus passes. Defer gRPC/webhook packages until consumers need
them; copying header parsing into every adapter is prohibited.

## I-10 — user preferences, tenant defaults and consent boundaries

**Decision.** User locale preference and tenant/application default are domain
data selected by a host policy. i18n consumes a verified allowed preference but
does not persist profiles, choose tenant, infer language from names/location or
override a user's consent/preference with a raw request hint.

### Top-level declarative DX

```go
preference := profiles.AllowedLocale(ctx, principal)
locale := resolver.Resolve(ctx, i18n.Preference{User: preference, Header: header})
```

### Happy use cases

1. Authenticated user saved `kk` preference is allowed and supported, so it wins
   over browser header under documented precedence.
2. New anonymous visitor has no saved preference; bounded Accept-Language picks
   supported Russian or service default cleanly.
3. Tenant config sets default English for new users; a permitted user preference
   still wins where product policy says it should.
4. A profile change validates language tag against approved supported set and
   audit records stable old/new preference under profile/audit policy.
5. A tenant's default is changed for future renders; no storage key, event type,
   database routing or telemetry identity changes as a side effect.

### Edge use cases

1. User preference is `zh-Hant` but app only has `zh`. Resolver applies declared
   matcher/fallback and optionally offers supported choice UI, not silent raw tag.
2. Tenant default contains a stale unsupported value. Resolver falls back safely
   and control-plane validation/alert catches configuration defect.
3. A cross-tenant admin view renders data for many tenants. Locale selection is
   explicit viewer/report policy; it never reads a tenant default to route data.
4. User account is deleted/suspended. Locale is not a durable independent
   identifier retained by i18n logs/metrics; profile/audit retention owns it.
5. Browser header conflicts with email/report locale saved at scheduling time.
   Scheduled command's explicit locale wins; no ambient request header leaks.
6. Product wants auto-detect by IP/geolocation. That is a privacy/vendor policy
   separate from i18n core; first satellite refuses to add it as resolver magic.

### Invariants and acceptance evidence

- resolver accepts tag/provenance, not principal/tenant/database implementation;
- profile/tenant values are validated before resolver and raw value never emitted;
- precedence table fixtures cover authenticated, anonymous, background/admin cases;
- locale change affects presentation only and cannot modify authorization/routing;
- audit/telemetry tests differentiate protected preference data from bounded mode.

### First implementation slice

Document a host-owned `PreferenceProvider` example and test precedence using
simple strings/tags. Defer persistent profile schema, tenant administration and
geolocation integrations to their owning domain satellites.

## I-11 — static UI messages versus localized domain content

**Decision.** The i18n catalogue carries stable application/system messages.
User-authored or product-managed localized content—article title, product copy,
legal terms, document template—is a versioned domain/CMS concern with authoring,
publication, permission, audit and fallback policy. It must not be smuggled into
static translation files or rendered via dynamic message IDs.

### Top-level declarative DX

```go
title := product.LocalizedTitle(locale) // domain content
errorText := catalog.FormatText(locale, errorMessage) // static system message
```

### Happy use cases

1. A validation error ID is static/coded and resides in a reviewed catalogue;
   a product description has localized domain records and publication version.
2. A UI combines translated label `product.description` with a domain-provided
   localized title, while each source follows its own access/revision policy.
3. A system e-mail uses static translated template shells but inserts authorized
   domain content through a renderer with separate escaping/length controls.
4. Legal text is versioned/published by domain workflow and associated with user
   acceptance audit; catalogue does not mutate legal evidence on app deploy.
5. A content translation is missing. Product/domain chooses draft/default/omit
   behavior, without treating it as a broken system message compiler failure.

### Edge use cases

1. Product creates one dynamic message ID per user/product. Catalogue/compiler
   refuses unknown/dynamic IDs; cardinality and translator workflow stay bounded.
2. User content includes message-template syntax braces. It is displayed as data,
   never parsed/executed by static formatter.
3. Content fallback from `kk` to `ru` has legal/brand implications. Domain model
   selects it; generic resolver doesn't silently publish a different contract.
4. A domain event needs historic title. It stores/version-controls explicitly
   approved content reference/snapshot, not “whatever current translation says.”
5. CMS translation is edited at runtime. It cannot reload static catalogue or
   alter system error behavior; its own audit/publish cache invalidation applies.
6. Translator assumes static string changes automatically update PDFs/contracts.
   Product generation pins content/catalogue version according to domain release.

### Invariants and acceptance evidence

- catalogue manifest IDs are finite/code-owned; dynamic source attempts fail;
- domain content integration tests retain output escaping/authorization/version;
- static message release cannot silently alter legal/user-authored history;
- telemetry/audit distinguish static message ID from protected content subject;
- user text never enters template compiler/parser through an i18n convenience API.

### First implementation slice

Publish this boundary prominently before adding a generic `Translate(key)` API.
Offer a small example showing both sources in one renderer; do not create a CMS
or content database inside the i18n satellite.

## I-12 — language-neutral OpenTelemetry and metrics

**Decision.** OpenTelemetry and metrics observe stable operation/error/catalogue
states, not translated copy, raw locale preferences or interpolation arguments.
Locale can be a bounded configured language-family dimension only where a real
operational question and cardinality/privacy review justify it; default metrics
do not include it.

### Top-level declarative DX

```go
renderer := i18notel.Decorate(catalog, i18notel.Config{
    Telemetry: telemetry,
    RecordFallbacks: true,
})
```

### Happy use cases

1. A command error trace records `vv.error.code=invalid` before/after localized
   render identically; dashboard groups failures independent of user language.
2. Catalogue formatter increments bounded `i18n.fallback.total` by configured
   message family/language family/reason only if app enables such metric.
3. A release detects missing Russian translation rate after a deploy without
   recording user args, raw `Accept-Language`, translated text or tenant identity.
4. OTel service span remains application operation owner; i18n formatting adds
   no per-message child span on ordinary error path by default.
5. A test meter/trace recorder proves English/Kazakh/Russian same code produces
   equal core command metric cardinality and no locale data leak.

### Edge use cases

1. Thousands raw locale tags arrive from browsers. They collapse to supported
   resolved enum or are omitted; they cannot create metric time series.
2. Missing message ID comes from attacker string. Telemetry records bounded
   `unknown_message`, never exact requested ID/value.
3. A localized argument includes customer name/token. Formatter decorator has no
   arbitrary-argument attribute API and privacy scanner rejects export.
4. Exporter fails or sampler drops. Formatting/error response behavior remains
   unchanged; no fallback retry/error depends on telemetry success.
5. Operator asks for per-tenant fallback dashboard. Tenant ID is prohibited;
   use authorized audit/support diagnosis outside generic metrics.
6. Locale fallback causes a user-visible issue. Trace ID may correlate safe code,

### Invariants and acceptance evidence

- i18n core has no OTel import; bridge is a dedicated optional satellite;
- all i18n metric labels have finite calculated maximum set;
- multilingual hostile corpus finds no locale/raw text/args in output payloads;
- no formatter span/event multiplication occurs per nested format attempt;
- OTel no-op/sampled/exporter-failure equivalence fixtures pass.

### First implementation slice

Implement no instrumentation until OTel satellite has its semantic registry. Add
one fallback counter in bridge only after catalogue states and privacy corpus are
stable; error code observability should continue using existing OTel mapping.

## I-13 — audit, support and translation change accountability

**Decision.** Translation catalogue publication and user preference/content
changes may need audit, but normal message formatting does not write audit rows.
The audit satellite records authorized actor/action/version/purpose with stable
message IDs/language tags under its own protected retention/read policy. It does
not persist every translated sentence or interpolation value by default.

### Top-level declarative DX

```go
audit.Record(ctx, audit.Action("i18n.catalogue_published"), audit.Subject(version))
```

### Happy use cases

1. Release publishes catalogue manifest version; audit records actor, deployment,
   language set and stable artifact/version subject under authorized audit policy.
2. Admin changes tenant default locale; audit records bounded old/new tag and
   reason code if business policy demands it, without changing tenant routing.
3. User changes profile language; profile/audit domain records action subject
   according to privacy/retention policy, not formatter every request.
4. Support ticket carries stable error code/message ID and optional trace ID;
   an authorized support system can identify catalogue release without collecting
   the user's full localized text in observability backend.
5. Translation rollback publishes a prior signed manifest/version and audit
   records the rollback action/reason, giving release traceability.

### Edge use cases

1. A translated message contains personal data through interpolation. Audit of
   formatting must not copy rendered string; it records only needed action/state.
2. Translation author identity is sensitive/internal. Audit reader access/purpose
   controls it; OTel metrics/traces never receive it.
3. A bulk locale preference migration changes millions profiles. Audit policy
   chooses batch revision/summary rather than individual unbounded records.
4. Catalogue asset is tampered. Signature/hash verification failure produces
   security/release audit event with bounded artifact identity, no asset contents.
5. Support needs “what text did user see?” For regulated flows, domain response
   snapshot/version policy explicitly stores it; generic i18n/audit cannot infer.
6. Audit backend is unavailable during catalogue deploy. Deployment policy must
   decide fail/hold/retry; formatter runtime never silently writes async audit.

### Invariants and acceptance evidence

- audit integration imports audit satellite only, never reverse into i18n core;
- formatter unit tests show zero audit writes for ordinary high-volume render;
- audit fixtures protect actor/preference/version access and redact message args;
- catalogue publication/rollback has immutable manifest/hash evidence;
- trace correlation optionality does not affect audit/release completeness.

### First implementation slice

Document release/audit event schema and test it with audit fake. Defer translation
management UI/workflow/permissions to an owning deployment/content system, not
the i18n runtime library.

## I-14 — event source and asynchronous messages

**Decision.** Event types, revisions, payload field names and projection logic
remain stable machine contracts. i18n renders at read/UI/notification edges; it
does not localize stored domain events or cause a replay to emit language-specific
side effects. An async task includes an explicit locale only when its output is
human-facing and its domain command authorizes/persists that choice.

### Top-level declarative DX

```go
// Stored event: orders.payment_failed { order_id, code }
// Projection/notification later resolves locale and formats human message.
```

### Happy use cases

1. `orders.payment_failed` event stores stable code/value; a notification worker
   loads recipient's authorized/pinned locale and formats current or specified
   template at send time under its own policy.
2. An event-sourced projection replays historic events and updates read model;
   no translation service/catalogue format call creates email/log side effect.
3. A scheduled report command persists requested locale as explicit domain input
   so retry/replay sends same language rather than using worker host environment.
4. Event revision/upcaster changes payload shape but leaves user-facing message
   ID/code contract stable or explicitly maps it in projection/notification code.
5. Outbox integration event uses stable machine fields for other bounded contexts;
   partner decides human presentation/localization separately.

### Edge use cases

1. Current translation changes after event occurred. If legal/audit needs exact
   historic copy, event/domain stores approved template version/snapshot explicitly.
2. Worker retries a notification with no durable locale choice. It must resolve
   current policy deliberately and audit outcome; i18n cannot recover old request.
3. Event payload includes translated copy to simplify client. This is rejected
   unless event schema declares audience/version/retention/localization contract.
4. Upcaster tries to invoke formatter to migrate historic message text. Upcasters
   must be pure deterministic payload transforms, not locale-dependent I/O.
5. A tenant default locale changes while outbox message waits. Notification
   contract decides pinned-vs-current; no silent resolver behavior is assumed.
6. One event fans out to multiple recipients/languages. Worker creates bounded
   per-recipient domain work; no event source metric labels every locale/user.

### Invariants and acceptance evidence

- event-source core imports no i18n implementation and applies no locale logic;
- replay fixture proves same persisted events yield same state with i18n absent;
- async notification fixtures test explicit/pinned/current locale policy/retry;
- upcaster tests have no clock/network/catalogue dependencies;
- telemetry/audit retain stable event/code correlation without message text leak.

### First implementation slice

Add a reference notification/read-model example to the event-source roadmap
after its outbox contract exists. Do not add locale fields to every event envelope
or propagate locale blindly in OTel baggage.

## I-15 — catalogue release, rollback and compatibility management

**Decision.** Catalogue manifest/schema is a versioned deployment artifact.
Translation change can be safe copy correction, additive ID, argument schema
change, plural grammar change, locale add/remove, deprecation or security
rollback. Each class has a review/rollout/rollback rule; language files are not
unreviewed static assets appended after code release.

### Top-level declarative DX

```text
release i18n/v12
  manifest: sha256:...
  default language: en
  supported: en, kk, ru
  compatibility: readers v10-v12
```

### Happy use cases

1. Copy-only correction keeps message ID/argument schema stable; manifest diff
   marks content change and release can ship independently if host allows it.
2. New message ID is additive: old binaries ignore it, new binary requires all
   configured language/default coverage according to policy.
3. New optional argument has a default/compatibility plan; old template readers
   continue through overlap window rather than formatting malformed output.
4. New language is added with plural/corpus/pseudolocale tests and supported set
   activation after its assets are deployed everywhere.
5. Translation rollback atomically selects prior valid signed manifest; old/new
   binaries see complete catalogue rather than half files from a directory watch.
6. Release notes state message schema/language/fallback changes and dashboard
   implications, treating them as operational compatibility not editorial trivia.

### Edge use cases

1. Remove/rename ID still used by a rollback binary. Deprecation manifest keeps
   it/read compatibility until all supported versions retire.
2. Change `count` from integer to string argument. Compiler marks breaking;
   release creates new message ID/schema rather than mutating historic contract.
3. Drop a language while users still prefer it. Resolver fallback/migration/user
   communication policy is explicit; no opaque `unsupported` production surprise.
4. Dynamic reload sees mixed files from two versions. First release forbids it;
   future reload uses one validated atomic artifact pointer/swap.
5. Artifact signature/hash verification fails. Deployment does not activate it;
   safe prior catalogue or startup failure policy is chosen deliberately.
6. A translation update adds unsafe rich markup. Source review/HTML policy blocks
   it before manifest activation; rollback/audit has same evidence path.

### Invariants and acceptance evidence

- release CI diffs manifest ID/arg/language/schema/fallback policy explicitly;
- old/new/mixed binary fixtures exercise format of shared/deprecated IDs;
- every release has immutable artifact version/hash and rollback pointer test;
- translation-only change still runs plural/escaping/privacy corpus as applicable;
- docs name support window and deprecation removal criteria.

### First implementation slice

Version the manifest from first release, even with one language. Add CI snapshot
and a rollback fixture before offering live reload or independent translation
deployment; an unversioned catalogue becomes a hidden API immediately.

## New-language onboarding workbook

Adding a language is a product, linguistic, accessibility, release and
operations change. The language is not placed in the supported resolver set
until every applicable confirmation below has concrete evidence.

### Language identity and negotiation

- Record the canonical BCP 47 tag and any supported regional/script variants.
- Record the exact matcher behavior for base-to-region and region-to-base fallbacks.
- Decide whether users can select the language in profile/UI at first release.
- Decide whether anonymous header negotiation may select the language immediately.
- Decide which default/fallback language applies to each missing message class.
- Test casing, aliases, deprecated tags and malformed tag handling.
- Test header quality ordering against existing supported languages.
- Test wildcard header policy and unsupported-language non-disclosure behavior.
- Test background/CLI/report default selection without operating-system locale.
- Test user preference precedence over tenant default and request hint.
- Test tenant default precedence only after verified tenancy scope is established.
- Test cross-tenant admin/report rendering policy independently from routing.
- Document whether language tag has a separate display/format locale component.
- Document whether script choice changes any legal/brand/communication policy.
- Add a bounded resolved-language enum mapping if operational metrics truly need it.

### Catalogue and message completeness

- Add language source artifact under approved immutable source/deployment path.
- Add manifest entry with language tag, source hash and catalogue schema version.
- Include every required default-language message ID or explicitly approved fallback.
- Include all required error title/detail and validation-field label IDs.
- Include all declared plural/select branches required by selected syntax/library.
- Use exactly the manifest's argument names and declared types for every template.
- Do not introduce a translated message ID, machine enum, event type or API code.
- Do not include user content, secrets, endpoints, storage keys or tenant names.
- Do not include raw HTML/JS/URL template contexts without renderer threat model.
- Add translator context/comment where needed without turning it into output data.
- Review punctuation, whitespace and bidi control characters through source lint.
- Review maximum message length and output expansion under UI/e-mail/document limits.
- Verify templates work with zero, empty, long and Unicode argument fixtures.
- Verify deprecated IDs remain readable through the current compatibility window.
- Produce deterministic compiled manifest and compare it in CI/release review.

### Linguistic and formatting correctness

- Add CLDR cardinal plural test vectors appropriate to the language.
- Add ordinal plural test vectors only when a product message actually needs them.
- Add numeric grouping/decimal/currency formatting snapshot fixtures as relevant.
- Add date/time formatting fixtures with fixed instant and explicit time zone policy.
- Confirm locale does not infer a user time zone or currency conversion policy.
- Add select/gender grammar only for declared bounded domain values.
- Verify translator can reorder named arguments without code positional assumptions.
- Verify singular/plural logic is in template, not English-only service conditionals.
- Verify punctuation/quotes/typography render correctly in the selected output surface.
- Test text direction and mixed-script identifiers if language/script requires it.
- Test pseudolocale expansion to find concatenation/layout assumptions around new text.
- Test screen-reader/accessibility labels separately from visual translated copy.
- Test truncation/wrapping behavior in host UI/document renderer, not i18n core.
- Document linguistic reviewer/owner and correction/rollback communication path.
- Re-run fixtures on external CLDR/library upgrade before accepting changed output.

### Security and privacy

- Run hostile string arguments through plain output fixture.
- Run hostile string arguments through every approved rich/HTML renderer fixture.
- Verify no raw locale header/profile value enters traces, logs or metric labels.
- Verify no translated output or interpolation argument enters OTel attributes/events.
- Verify no normal formatting call creates a durable audit record.
- Verify profile/default changes use protected domain/audit path if retained.
- Verify error rendering never calls unknown `err.Error()` as a translation argument.
- Verify unknown dynamic message IDs collapse to one safe diagnostic category.
- Verify result/error limits prevent source/template/argument data exhaustion.
- Verify catalogue source files/artifacts follow deployment integrity/signing policy.
- Verify translators cannot inject raw unreviewed rich markup where it is executable.
- Verify locale selection cannot bypass tenant/policy/authentication checks.
- Verify localized display text cannot become SQL, URL, storage key or event type.
- Verify support trace correlation cannot reconstruct private rendered text by default.
- Document who is authorized to access source artifacts and publish/rollback them.

### Release and operational readiness

- Update supported-language manifest and resolver configuration in one release plan.
- Run old/new/mixed binary catalogue compatibility fixtures.
- Run fallback/missing-translation metrics cardinality calculation after addition.
- Update API/e-mail/document/UI examples and stable-code integration guidance.
- Update pseudolocale/translation quality test targets and CI required checks.
- Prepare rollback artifact/pointer and test atomic activation before user exposure.
- Update release notes with availability, fallback and known unsupported surfaces.
- Train support on stable error/message ID rather than requesting pasted UI strings.
- Set owner/SLO for missing translation/fallback signals if those metrics are enabled.
- Confirm no dashboards/alerts assume static pre-addition language enum inadvertently.
- Verify rollout does not change API codes, event revisions or storage identities.
- Audit initial publication action according to deployment/audit policy.
- Record compiler/library/CLDR versions in release artifact metadata.
- Rehearse disabling language from resolver set without corrupting saved preferences.
- Do not call language production-supported until all target workflow tests pass.

## Translation pull-request review checklist

Reviewers answer each question with a test, manifest diff or explicit decision.
No item is waived merely because a change “only edits text.”

### Stable contracts

- Does the change preserve existing message ID exactly?
- If not, is a new ID/deprecation mapping/release window documented?
- Does the change preserve every declared argument name and type?
- If not, is the compatibility break represented as a new schema/ID?
- Does it preserve stable error/API/event/domain codes outside human copy?
- Does it preserve output machine field names and JSON/gRPC status behavior?
- Does it avoid encoding business state in a translated phrase?
- Does it avoid creating dynamic/caller-derived message IDs?
- Does it avoid changing storage key, tenant identifier or resource name semantics?
- Does it avoid turning a fallback string into a control-flow sentinel?

### Template correctness

- Does every plural/select form compile under the selected syntax?
- Does every required plural category have an approved language fixture?
- Are named placeholders spelled/type-matched exactly against manifest?
- Is a missing/extra placeholder caught by generated validation rather than review alone?
- Does the template handle zero/empty/long argument values without malformed text?
- Are number/date/currency arguments semantically appropriate and explicitly typed?
- Does a date have an explicit zone/instant policy in its caller?
- Does the template use one full grammatical sentence rather than code concatenation?
- Are bidi/whitespace/control characters intentional and linted?
- Is output expansion under documented renderer limits?

### Security and rendering

- Is this a plain-text template? If yes, does no caller infer HTML safety?
- Is this rich/HTML content? If yes, is renderer/context threat model approved?
- Are argument placements safe for their exact HTML/URL/attribute/JS context?
- Could user text be parsed as template syntax or execute in a target renderer?
- Could raw error/request/secret/identity reach an argument through this message?
- Could a message be logged/traced/audited with more data than intended?
- Does the change preserve redaction/argument length restrictions?
- Does it avoid using translated display text in link, key, path or SQL context?
- Does it avoid giving a user a detailed refusal reason that weakens authorization?
- Is source artifact access/translation-management security appropriate for content?

### Fallback and language policy

- Does default language retain a valid copy for this message?
- Does every currently required supported language have compatible translation?
- Is missing-language fallback behavior still acceptable for this message purpose?
- Does a legal/regulated/financial message require strict completeness instead?
- Is an optional/deprecated message lifecycle state changed in the manifest?
- Does region/script matcher behavior produce intended language fallback?
- Does new copy need profile/tenant default precedence documentation?
- Does background/e-mail/report path have a pinned/current locale decision?
- Does removing/renaming language require saved-preference migration/support plan?
- Does pseudolocale detect any hard-coded/concatenated adjacent strings?

### Operational and release impact

- Is generated manifest source hash updated and deterministic?
- Does CI compile all catalogues and run multilingual fixtures?
- Does the change alter fallback metrics/enum/cardinality dashboard query?
- Does it introduce a new language/library/CLDR version requiring rollout tests?
- Is a translation-only hotfix artifact versioned and rollbackable?
- Does a rolling deployment tolerate old code with new catalogue and vice versa?
- Is the change included in release notes/support documentation when user-visible?
- Does it require audit publication/approval under organizational policy?
- Has the assigned message/language owner reviewed sensitive semantic changes?
- Has the final rendered output been checked in its actual UI/e-mail/document surface?

## Incident response workbook

### Missing or broken translation after deployment

1. Confirm affected stable message ID and resolved canonical language, not raw header.
2. Confirm whether issue is unknown ID, missing translation, parser failure or renderer error.
3. Check immutable active manifest version/hash and binary version cohort.
4. Confirm fallback policy delivered safe machine code/status and safe human text.
5. Inspect bounded fallback metric/trace correlation without retrieving user arguments.
6. Compare manifest against last known-good artifact and source compilation report.
7. If copy defect, prepare corrected complete artifact through normal validation.
8. If schema defect, do not edit historic ID in place; use compatibility/new ID plan.
9. If security/rich-template issue, disable/rollback artifact before broad diagnostics.
10. Activate prior or corrected artifact atomically and record release/audit action.
11. Re-run relevant plural/escaping/transport golden fixtures before closing incident.
12. Update user/support communication using stable code/affected locale family only.

### Locale negotiation anomaly

1. Reproduce with a bounded sanitized preference vector, never a pasted raw header.
2. Verify supported/default set and matcher/compiler/library version.
3. Check authenticated preference and tenant default precedence through authorized test fixture.
4. Check whether background/notification operation had explicit or implicit locale policy.
5. Confirm no invalid credentials were treated as anonymous locale preference.
6. Verify canonical tag/fallback output against recorded resolution tests.
7. Do not add a raw-header telemetry label as a diagnostic shortcut.
8. Patch resolver policy with a new test vector and release compatibility note.
9. Recheck no tenant routing/authz behavior changed while resolving locale.
10. Re-run concurrent context isolation/race fixture before release.

### Translation artifact integrity failure

1. Stop activation; retain last verified immutable catalogue artifact.
2. Verify source hash/signature/provenance through deployment system, not runtime formatter.
3. Identify whether source, manifest generation, packaging or activation produced mismatch.
4. Do not log full source/template artifact if it might contain sensitive internal content.
5. Use artifact version/hash and authorized audit record for investigation.
6. Rebuild from trusted source with deterministic compiler and compare manifest diff.
7. Validate all languages/default completeness before retry activation.
8. Roll back atomically if any active readers could see mixed artifact state.
9. Review translator/source access controls if unauthorized modification is suspected.
10. Record corrective release and add regression/verification test before closure.

## Implementation sequencing and evidence gates

The implementation order intentionally starts with deterministic artefacts and
machine contracts. A formatter without an executable catalogue/release boundary
will look convenient in development and become impossible to support during a
mixed deployment or translation incident.

### Phase I1 — catalogue foundation

- Choose a CLDR-capable template/parser library in a satellite dependency ADR.
- Define ASCII-like message ID grammar and generated constant/reference policy.
- Define manifest schema: ID, arguments/types, language, lifecycle and source hash.
- Define default/support/required-language and missing-message/fallback policies.
- Implement `io/fs`/embedded source loader with file/count/byte/depth limits.
- Implement deterministic compiler and source/manifest mismatch CI target.
- Implement strict duplicate/default/argument/plural/select validation corpus.
- Implement plain text formatter with output/argument size limits.
- Add no-global-state/no-environment/no-network dependency tests.
- Gate I1 on reproducible compile plus all parser/privacy/manifest tests.

### Phase I2 — locale resolution and error boundary

- Implement canonical tag matcher over caller-supplied supported/default config.
- Implement bounded preference/header inputs without transport package import.
- Add resolved immutable locale context helper and concurrency/race fixtures.
- Specify user/header/tenant/default precedence as a host policy interface.
- Implement safe missing-ID/missing-translation result types.
- Build external errors renderer adapter preserving `errs` code/status/wrapping.
- Add multilingual golden responses for current error code families incrementally.
- Add malformed carrier/invalid auth/no-context/background/default test matrix.
- Document M2M/no-human-text integration path.
- Gate I2 on language-independent machine error/API contract evidence.

### Phase I3 — plural, rendering and language quality

- Implement selected cardinal plural support with English/Kazakh/Russian corpus.
- Add select support only for finite declared domain enum values.
- Add number/date rendering with explicit instant/time-zone policy.
- Keep plain text as only default output context.
- Design HTML/e-mail/document renderer integration only on real owning use case.
- Add pseudolocale assets and hard-coded/concatenation snapshot target.
- Add output expansion, Unicode/bidi and hostile argument safety tests.
- Add translation reviewer/owner/source integrity workflow documentation.
- Add new-language onboarding workbook as a CI/release checklist.
- Gate I3 on approved linguistic fixtures and renderer-specific threat evidence.

### Phase I4 — release, observability and cross-satellite bridges

- Version/publish manifest hash with binary release and test old/new mixed readers.
- Implement atomic artifact activation/rollback only after full validation exists.
- Add one optional bounded fallback metric through OTel bridge if operations need it.
- Add audited catalogue/profile-default change reference integration.
- Document event/outbox notification pinned-vs-current locale policy.
- Document tenant/default locale boundary without importing tenancy implementation.
- Document storage display-name/key separation and localized document rendering path.
- Publish incident, migration and support runbooks with stable-code correlation.
- Run no-op/sampled/audit-unavailable equivalence suites across all bridges.
- Gate I4 on all optional bridges being removable without behavior change.

## Public API review checklist

Reject a proposed API if it violates any item below.

- It sets or reads a process-global current locale.
- It takes raw unbounded `Accept-Language` string in core formatter API.
- It accepts a dynamic message ID constructed from user/domain data.
- It takes an untyped `map[string]any` without a declared argument schema.
- It returns a magic “safe localized HTML/string” valid in every output context.
- It loads translation files from network/current working directory per request.
- It fetches translation SaaS, profile, tenant, database or identity itself.
- It persists a user preference, tenant default or localized content in i18n core.
- It mutates a catalogue/template/messages map after construction.
- It hides a missing ID/argument/schema bug through generic runtime string output.
- It changes stable error code/API/projection/event type based on resolved locale.
- It places raw locale/text/arguments into metrics or default OpenTelemetry fields.
- It writes a durable audit entry on every render.
- It makes event replay/upcaster call a formatter or inspect current locale.
- It uses display text as storage key, database identifier, URL slug or policy key.
- It implies translations provide HTML escaping, legal versioning or user-content CMS.
- It requires root vv or `errs` to import `golang.org/x/text`.
- It bundles HTTP/gRPC/router/logging/exporter dependencies into `vv/i18n`.
- It reloads multiple language files non-atomically in an already serving process.
- It claims support for a locale without its catalogue, plural and release evidence.

## Catalogue manifest reference schema

The exact serialization can be JSON, generated Go, binary or another reviewed
artifact. The logical fields and their compatibility rules are what matter:

| Field | Meaning | Compatibility rule |
|---|---|---|
| manifest version | schema/compiler format | reader supports known versions explicitly |
| artifact hash | immutable source/compiler identity | changes on any source/semantic change |
| default tag | guaranteed fallback language | must exist and be complete per policy |
| supported tags | declared selectable/matchable language set | additions/removals have release policy |
| message ID | stable code-facing key | no in-place semantic reuse |
| lifecycle | active/deprecated/optional/removed | removal waits for compatibility window |
| argument schema | names/types/required/default rules | incompatible change becomes new ID/schema |
| template fingerprint | source/rendering compatibility evidence | never a runtime user identifier |
| plural/select schema | declared grammar/branches | validated per language/library version |
| source ownership | reviewer/team/context metadata | not emitted in public runtime output |
| renderer eligibility | plain-only/rich-reviewed constraints | no implicit escalation to HTML |
| release notes link | support/migration context | required for non-copy schema changes |

## Cross-domain acceptance examples

### Localized validation error

1. Transport receives raw request and authenticates it normally.
2. Request resolver chooses bounded supported locale according to host policy.
3. Service validates command and returns stable `errs` invalid-field code.
4. Error adapter maps code/declared safe field label ID to catalogue message.
5. Formatter renders plain human detail in resolved/default fallback language.
6. Transport serializes stable status/code/type independently from that detail.
7. OTel service span records code/outcome only; no text/field/raw locale value.
8. Audit records nothing unless a separately declared security attempt policy says so.
9. Client can use code regardless of language and displays human detail safely.
10. Missing translation still preserves all machine/authorization semantics.

### Event-driven notification

1. Aggregate appends stable domain event and transactional outbox intent in Postgres.
2. Event payload holds domain reference/code, not translated message/tenant header.
3. Worker receives event at least once and loads authorized recipient/policy data.
4. Domain notification command supplies pinned or current locale policy explicitly.
5. Formatter renders approved notification template after event replay boundary.
6. Sender owns rich e-mail/HTML output escaping and external delivery retry policy.
7. Audit records durable delivery action/policy as needed; trace links remain optional.
8. Retry/replay does not use worker environment locale or call aggregate Apply formatter.
9. Translation update/rollback follows manifest version policy before new delivery.
10. Recipient/content identifiers remain outside generic metrics/OTel telemetry.

### Multitenant report

1. Control plane verifies admin/report actor and selects one authorized tenant scope.
2. Tenancy resolver routes/narrows data before report query executes.
3. Report command chooses viewer/pinned locale under explicit product policy.
4. Domain data fields remain structured/raw until the report rendering layer.
5. i18n formats static labels, counts and safe errors; it does not select tenant DB.
6. Localized display names remain domain content, not storage/object/event identity.
7. Audit records report access/purpose/tenant under protected audit read/write rules.
8. OTel reports bounded topology/operation outcome, never tenant/locale/user content.
9. Failure fallback keeps machine result secure and does not broaden report access.
10. Removing i18n leaves authorization/routing/data result semantics unchanged.

## Definition of done for the first i18n satellite

The initial implementation is complete only when:

1. `vv/i18n` is an external-dependency satellite and root `errs` is unchanged.
2. One immutable validated catalogue artifact and manifest build deterministically.
3. Message IDs, arguments, plural/select grammar and fallback policy have tests.
4. Locale resolution is explicit, bounded, concurrent-safe and environment-free.
5. English, Kazakh and Russian initial corpus includes approved plural fixtures.
6. Plain text formatting has size/error/sensitive-argument controls.
7. Error boundary preserves existing public machine code/status/error identity.
8. HTTP/CLI examples remain optional adapters, with core transport neutral.
9. No raw locale, translated text or args leak in default telemetry/audit/log paths.
10. New-language, release, rollback and incident workflows above are executable CI/runbook evidence.
11. Event, storage, tenancy, audit and OTel bridges remain optional and directional.
12. No UI CMS, live translation SaaS, global locale or generic rich HTML API ships by accident.

## First-release operational contract

### What an application must configure

- one immutable catalogue source/artifact owned by its build/deployment system;
- one explicit default supported language tag;
- one finite supported language set;
- one missing-message policy appropriate to environment and public boundary;
- one missing-translation fallback policy appropriate to each message class;
- one host locale precedence policy for profile/request/tenant/default inputs;
- one chosen plain-text renderer path, plus separate policy for any rich surface;
- one manifest validation command in CI before packaging;
- one rollback pointer/artifact process before independent translation deployment;
- one owner for each sensitive message family and language quality review.

### What an application must not assume

- browser language proves user language, residence, identity, consent or tenant;
- a language tag gives currency, time zone, legal jurisdiction or text direction;
- a translated error text is stable enough for client branching or support search;
- a passing English snapshot proves plural/grammar/copy quality in another language;
- a successful template compile proves safe HTML, e-mail, PDF or browser rendering;
- an S3 object key, event type, audit action or database field should be localized;
- a trace ID can recover a rendered sentence, argument or audit record later;
- a current catalogue represents what a user saw at a historic legal/event moment;
- an async worker can safely inherit a request locale after request completion;
- a translation SaaS or live file update has atomic/reviewed production semantics.

### What the first satellite explicitly provides

- parsed/canonical locale matching against finite caller-supplied supported tags;
- immutable validated catalogue instances from caller-owned embedded/`io/fs` data;
- stable message IDs with declared argument schema and strict validation;
- chosen CLDR-aware plural/select behavior with versioned test corpus;
- bounded plain text rendering and controlled fallback/missing result types;
- transport-neutral locale context helper and boundary examples;
- optional bridge seams for OTel/audit/events/tenancy/storage without reverse imports;
- manifest diff, compatibility, rollback and incident checklists;
- language-neutral error-machine contract preservation;
- a route for later capability work without weakening root-module dependency rules.

### What the first satellite deliberately defers

- a generic web UI/component/template framework;
- an integrated translation-management/SaaS synchronization client;
- runtime editable/live-watched catalogue directory;
- a user-content CMS or localized domain-record persistence model;
- a generic HTML/Markdown/JS/URL-safe rendering promise;
- automatic geolocation, browser fingerprinting or language inference service;
- currency conversion, time-zone profile storage or calendar business rules;
- arbitrary per-tenant catalogue overrides loaded from a database;
- per-user/per-locale telemetry diagnostics with open cardinality;
- translation of database/event/storage/API/policy/authorization identifiers;
- exact historical “what text was shown” evidence without a domain snapshot policy;
- root-package i18n, exporter, router, database or background reload worker.

## Final i18n boundary

Internationalization becomes a framework capability only when it remains
presentation-oriented, versioned and explicit about who owns language choice,
content, escaping, retention and deployment. It must make a localized product
easier to evolve without making every stable contract human-language-dependent
or leaking the user's words and preferences into the framework's operations
plane.

## Pre-merge scenario sampler

This short sampler complements the exhaustive corpus and is intended for every
change touching a formatter, resolver or translation artifact. Each answer must
be an executable test or an intentional unchanged result from an existing test.

### Resolver sampler

- Valid explicit English resolves to English.
- Valid explicit Kazakh resolves to Kazakh.
- Valid explicit Russian resolves to Russian.
- Regional tag resolves according to recorded matcher fixture.
- Unsupported tag resolves to declared fallback.
- Malformed tag cannot panic or echo input.
- Oversized header cannot create unbounded work.
- Equal-quality choices follow one deterministic tie rule.
- User preference precedence follows host policy.
- Tenant default never selects a tenant or database.
- Background job uses explicit/pinned/default locale.
- Concurrent requests cannot exchange locale values.

### Catalogue sampler

- Default language exists and contains required error/message IDs.
- Each changed ID has compatible declared args in every required language.
- Duplicate IDs/tags fail compile.
- Changed plural/select branches have language fixture snapshots.
- Changed template cannot produce unbounded result from bounded inputs.
- Source encoding/control character lint passes.
- Manifest diff is generated and reviewed.
- Artifact hash/version changes deterministically when source changes.
- Old binary/deprecated-ID fixture remains valid where support window requires it.
- Atomic activation/rollback fixture has no mixed-catalogue state.
- Translation-only artifact can be reproduced offline from reviewed source.
- No new runtime network/filesystem global dependency was introduced.

### Boundary sampler

- Same stable error code/status is returned in every test locale.
- Missing formatter message cannot mask original business error.
- Raw error/header/argument values are absent from export scanner.
- Plain output is not presented as HTML-safe output.
- Rich output changes have renderer/context security evidence.
- Regular rendering produces no audit write.
- Publication/profile changes use controlled audit policy if required.
- Event replay/upcaster has zero formatter calls.
- Storage key/signing path remains locale-neutral.
- OTel metrics remain under cardinality budget.
- Telemetry exporter failure changes no rendering/error semantics.
- Removing bridge/adapters leaves domain behavior unchanged.

### Release sampler

- Supported/default language set is explicit in artifact/release notes.
- Fallback change has product/support owner approval.
- New language completed the onboarding workbook.
- Removed language has a saved-preference migration/fallback plan.
- Compiler/library/CLDR version change re-ran language snapshots.
- Pseudolocale detects new hard-coded/concatenated UI fragments.
- Support can find message/version through stable code rather than user text.
- Incident rollback owner and artifact pointer are named.
- Documentation index still links this roadmap and dependent satellites.
- The release contains no unverified claim about localization coverage.

The sampler is intentionally not a substitute for the detailed cases. It is a
guard against the common failure mode where a small change skips the exact
boundary that makes localization operationally risky.

## Closing release rule

Do not ship a translation update that cannot answer three questions:

1. Which stable message/code/schema does this text represent?
2. What will an old binary, missing language and failed renderer do safely?
3. Which user/tenant/event/storage/audit/telemetry boundary remains unchanged?

If one answer is unknown, the work is not a harmless copy edit—it is an
architecture or release decision and needs the corresponding evidence above.

## Final compatibility reminders

- A stable message ID is an API-like contract even when users never see it.
- A translated sentence is not a stable API-like contract even when tests see it.
- A language tag is a preference, never an authorization credential.
- A default locale is configuration, never an application global.
- A fallback is a deliberate product decision, never a parser accident.
- A plural category is language data, never an English conditional.
- A formatter is a presentation component, never a CMS or policy engine.
- A catalogue version is a release artifact, never a mutable directory.
- A template argument is untrusted data, never an arbitrary context map.
- A renderer owns escaping, never a generic `Translate` helper.
- An error code remains canonical, never its localized detail string.
- A trace can correlate safely, never preserve the rendered response.
- An audit can record a release/action, never every format call.
- An event can carry stable fact/code, never implicit UI copy authority.
- A storage key stays opaque, never a translated filename.
- A tenant default helps presentation, never datasource selection.
- A worker receives locale policy explicitly, never through environment drift.
- A translation vendor is a build integration, never a request dependency.
- A new language is a tested release, never a tag added to a list.
- A rollback is atomic artifact selection, never editing files in production.
- A privacy review applies to language/args just as to any other user data.
- A satellite isolates x/text choice, never adds it to the root module.

## Final first-release non-goals

- automatic translation generation or machine-translation quality guarantees;
- editable production translation files through an application endpoint;
- translation of arbitrary database values by reflection;
- per-request network calls to discover a user's language;
- universal calendar, transliteration, collation or search-language framework;
- implicit rendering of domain rich content in an HTML-safe context;
- automatic storage filename, event payload or audit snapshot localization;
- fallback decisions hidden in third-party library defaults;
- support for a language whose fallback/plural/renderer release evidence is absent;
- mutable singleton catalogue shared across otherwise independent applications.

These omissions are intentional first-release integrity boundaries, not missing
convenience overloads. Any later addition enters through a named owner, a
versioned contract and the same multilingual/privacy/release evidence model.

No hidden global locale is acceptable.

No hidden translation data path is acceptable.

# Internationalization roadmap — one optional full-i18n extension — 2026-09-01

**Status:** proposed, not an accepted delivery commitment. No full i18n package
or module exists. The root `errs` and `port` seams already implement the current
localized-error need; M0 must demonstrate a concrete need for CLDR-grade
application messages before an optional module is built.

This revision supersedes the package and bridge sketches in the
[2026-08-26 i18n snapshot](2026-08-26-1558-i18n-roadmap.md). The older document
remains design evidence for locale, plural, rendering, privacy and release
semantics. Package growth and integration direction are governed by the
[optional extension architecture roadmap](2026-09-01-extension-architecture-roadmap.md).

## Scope and honest baseline

[[D-048]] remains binding. The framework does not currently need a root `i18n`
subsystem. It already ships:

| Current seam | Role |
|---|---|
| `errs.MessageSource` | One dependency-neutral method that resolves a violation and locale to human text |
| `errs.Messages` | Standard-library message catalogue with locale/base/default fallback |
| `errs.LoadMessages` and `Messages.Load` | `io/fs` JSON catalogue loading |
| `port.WithLocale` / `port.LocaleFrom` | One shared explicit locale context key |
| `port.FirstLanguageTag` | Small first-tag helper for the current narrow transport need (HTTP and gRPC) |
| `porthttp.WithMessages` | Injects any `errs.MessageSource` into the HTTP renderer |
| `crudgrpc.WithMessages` | Injects the same seam into the optional gRPC renderer |

These APIs remain the complete supported path until this roadmap passes M0. A
consumer that needs only localized validation/error messages should continue to
use `errs.Messages`; it must not acquire `golang.org/x/text`, a formatter, a
transport bridge or an OTel graph.

The proposed extension is only for a concrete application need that the current
catalogue cannot honestly meet: CLDR plural/select rules, canonical BCP 47
matching, declared typed arguments, culturally correct formatting or a coherent
versioned translation artefact. “A framework should have i18n” is not evidence.

## Architectural decision

If M0 accepts full i18n, one optional module represents the consumer decision
“use Frostgrove full i18n and the selected CLDR/text ecosystem.” The working
path is `github.com/frostgrove/vv/i18n`, with package name `i18n`; M0 freezes the
path and exact dependency profile.

That one module may contain catalogue, locale, formatter, manifest and
`errs.MessageSource` adapter files. It does not create public packages per
transport or per cross-cutting integration.

```text
                         application composition root
                                      |
             resolves locale and injects ordinary typed values
                                      |
          +---------------------------+--------------------------+
          |                           |                          |
   porthttp renderer             gRPC renderer           application UI
          ^                           ^                          ^
          | errs.MessageSource        | errs.MessageSource       | explicit locale
          +---------------------------+--------------------------+
                                      |
                              optional i18n module
                                      |
                            selected text/CLDR ecosystem

errs / port / transports --------X--------> optional i18n
i18n -----------------------------X--------> vvotel, audit, tenancy,
                                             event source, storage, routers
optional extension A ------------X--------> optional extension B
```

The root never exposes an i18n-owned type. The optional module implements or
adapts root seams in the dependency direction above. If a future generic
translation contract is proposed in root, it must independently satisfy
[[D-048]] in the same change; this roadmap does not prepay that abstraction.

## Target module and package layout

The working first release is one public package organized by files:

```text
i18n/
  go.mod                     one selected full-i18n ecosystem decision
  doc.go                     boundary and ownership
  catalogue.go               immutable validated catalogues
  locale.go                  canonical tags, matching and fallback
  message.go                 declared IDs and typed argument schema
  format.go                  selected plural/select/plain-text formatter
  message_source.go          errs.MessageSource implementation/adapter
  manifest.go                deterministic release artefact metadata
```

The production module may require the root module plus the M0-selected text,
language and parser packages that form one inseparable i18n choice. It may not
require OTel, an exporter, audit, tenancy, event sourcing, storage, a router,
gRPC, Fx, a database, a broker, a translation SaaS client or another optional
Frostgrove extension.

A compiler command or translation vendor synchronizer is not silently bundled
with the runtime. M0 decides whether deterministic validation is a library API,
an unpublished build tool or a separately selected tool; runtime consumers do
not inherit CLI, credential or network dependencies.

## Base-owned composition points

### Error wording

`errs.MessageSource` is the current base seam:

```go
type MessageSource interface {
    Message(context.Context, Violation, string) (string, bool)
}
```

The full catalogue either implements it directly or exposes a small adapter
from the same `i18n` package. No `errsi18n`, `i18nerrs`, `i18nhttp` or
`i18ngrpc` package is needed. Error codes, kind, status, wrapping, path and wire
shape stay owned by `errs`/`port`; i18n supplies optional human wording only.

The existing `errs.Messages` remains valid and supported alongside the full
implementation. Adopting full i18n is an application bootstrap change, not a
root migration or a forced replacement for every consumer.

### Locale propagation

`port.WithLocale` and `port.LocaleFrom` remain the one context seam read by
framework renderers. The optional module does not introduce a second context
key, global current locale or environment-derived default.

A full resolver may parse and match richer caller-supplied preferences, but the
application/transport boundary owns raw HTTP headers, gRPC metadata, authenticated
profile values and tenant defaults. It passes bounded inputs to the resolver,
then stores only the resolved supported tag in the base context or passes it
explicitly to a formatter.

`port.FirstLanguageTag` keeps its current narrow semantics. Full q-weighted
negotiation does not silently change that helper's contract; an accepted API
change needs its own compatibility evidence.

### Application messages

Messages outside `errs` use the optional module's explicit formatter API. M0
freezes message ID grammar, argument types, fallback result and plain-text
rendering shape. The API must not accept a dynamic user-controlled ID or an
unbounded `map[string]any` as an undeclared payload channel.

No root-wide translation facade is added for one implementation. User-authored
or product-managed localized content remains domain/CMS data with its own
authorization, publication and retention rules.

## Illustrative linear composition

The i18n constructor names below are illustrative until M0/M1. The existing
`porthttp` and `crudgrpc` entry points are current:

```go
catalogue, err := i18n.New(i18n.Config{
    Source:    embeddedMessages,
    Supported: []string{"en", "kk", "ru"},
    Default:   "en",
})
if err != nil {
    return err
}

messages := i18n.Messages(catalogue) // implements errs.MessageSource

httpRenderer := porthttp.NewRenderer(
    porthttp.WithMessages(messages),
)

grpcRenderer := crudgrpc.NewRenderer(
    crudgrpc.WithMessages(messages),
)

resolved := catalogue.Resolve(requestedPreferences)
ctx := port.WithLocale(request.Context(), resolved.String())
```

The application may import both optional `i18n` and `crudgrpc`; neither module
imports the other. HTTP uses the root `porthttp` package. A router-specific
binding receives the already configured renderer through its existing options,
so adding Fiber or Gin creates no i18n × router package.

The example language set is evidence for the old proposal, not a promise that
those three languages ship. M0 names the initial supported corpus and reviewers.

## Cross-extension behaviour belongs to the application

### OpenTelemetry

There is no `i18notel` package and `vvotel` does not import optional i18n.
Command/transport telemetry continues to record stable bounded machine outcomes,
never rendered text, arguments, raw locale headers or tenant identity.

A fallback metric is deferred until an operator question, finite vocabulary and
dependency-neutral seam are all accepted. An application-local callback may
connect independently selected components, but it is not published as a
framework bridge or a generic dynamic telemetry API.

### Audit and release accountability

Ordinary formatting writes no audit row. The application or deployment workflow
that publishes/rolls back a catalogue calls its independently selected audit
component with a bounded artefact version/action. Profile and tenant-default
changes are audited by their owning domains. The i18n module imports none of
them and does not persist rendered text by default.

### Tenancy and user preference

Authentication, authorization and tenant routing finish before locale resolution.
The application passes an allowed user preference or configured default as
bounded input. i18n never reads a tenant resolver, selects a database/bucket or
uses a locale as identity. There is no `i18ntenancy` or `tenanti18n` package.

### Events and asynchronous work

Events retain stable types, revisions, field names and machine codes. A worker
receives an explicit pinned/current locale policy as application/domain input
and formats only after the replay/projection boundary. Event source and i18n
modules do not import one another, and replay/upcasters never call a formatter.

### Storage

Object keys, namespaces, URLs and provider identities remain language-neutral.
Localized display names are domain data passed to a renderer, not a reason for
an i18n × storage adapter.

## Forbidden combinations and shortcuts

Do not create:

- `i18nhttp`, `i18ngrpc`, `i18nfiber`, `i18ngin` or another transport bridge;
- `i18notel`, `i18naudit`, `i18ntenancy`, `i18nevent` or `i18nstorage`;
- a translation bundle that imports a router, container, database, broker,
  exporter, provider SDK or translation SaaS runtime;
- a shared global locale/catalogue registry or mutable default printer;
- a generic framework `Observer`, `Extension`, service locator or reflection
  registry introduced only for i18n integration;
- build tags that hide `golang.org/x/text` inside the root module; or
- translated strings as error codes, API enums, policy names, event types,
  storage identities or telemetry dimensions.

## Delivery plan

### M0 — go/no-go and contract freeze

1. Name at least one concrete full-i18n use case that `errs.Messages` cannot
   meet without false semantics.
2. Choose and record the CLDR/text/parser ecosystem, template grammar and
   compatibility policy.
3. Freeze module path/package name, direct dependency allow-list and generated
   artefact strategy.
4. Decide whether `errs.MessageSource` plus explicit formatter APIs are enough;
   do not add a root contract without satisfying [[D-048]].
5. Freeze locale precedence ownership, message ID/argument schema, fallback,
   output limits and initial language corpus.
6. Record explicit non-goals and the no-cross-extension-import gate.

M0 may close with a no-build decision. If it does, current `errs.Messages`
remains the supported solution and later milestones do not start.

### M1 — one optional catalogue module

1. Create exactly one `i18n` module and one initial public package.
2. Load caller-owned embedded/`io/fs` sources under file/count/byte/depth limits.
3. Validate immutable catalogues, default/supported tags, duplicate IDs and
   declared argument schemas before serving traffic.
4. Produce a deterministic manifest/hash and source mismatch check.
5. Implement `errs.MessageSource` compatibility without changing root `errs`.
6. Add no-global/no-environment/no-network and concurrent catalogue tests.

### M2 — locale, plural and safe rendering

1. Implement canonical BCP 47 matching over caller-supplied supported tags.
2. Implement selected CLDR cardinal plural/select behaviour with approved
   language fixtures.
3. Keep plain text the first renderer and bound input arguments, nesting and
   output expansion.
4. Preserve stable error code/status/path/wrapping across every locale.
5. Fuzz parser, locale and hostile-argument inputs; retain regression seeds.
6. Add pseudolocale and release compatibility fixtures where the use case needs
   them.

### M3 — application composition and release evidence

1. Build HTTP and gRPC examples by injecting the same `errs.MessageSource`.
2. Build tenancy/profile, event-worker and catalogue-audit examples in an
   application module; no framework bridge package is added.
3. Prove OTel/audit absence and failure cannot change formatting semantics.
4. Exercise old/new/deprecated IDs, mixed binary versions, atomic activation and
   rollback.
5. Publish new-language, translation-review, incident and support checklists.
6. Run isolated base-only, i18n-only and representative multi-extension module
   fixtures with `GOWORK=off`.

## Verification gates

| Area | Required evidence |
|---|---|
| Honest status | Current `errs`/`port` APIs and proposed `i18n` APIs are labelled separately |
| Root optionality | Root and base-only consumers have no text/CLDR dependency or i18n module graph |
| One decision | The optional module contains only the selected i18n ecosystem and root seams |
| No extension edge | Source/import checks reject OTel, audit, tenancy, event, storage/provider, transport and container satellites from i18n |
| Existing seam | The same catalogue satisfies `errs.MessageSource` in HTTP and gRPC application fixtures |
| Locale ownership | One resolved locale crosses `port` context; no second key, environment lookup or global mutable default exists |
| Machine compatibility | Error codes, kinds, status, paths, event types and API enums are equal across locales |
| Catalogue safety | File/count/byte/depth, template nesting, argument and output bounds fail safely |
| Language semantics | Every advertised language has approved fallback and plural/select fixtures |
| Privacy | Raw preference/header, rendered text, templates and arguments are absent from default logs, OTel and audit |
| Linear growth | Selecting i18n plus a transport/OTel/audit extension adds no intersection package |
| Activation/release | Catalogue construction is side-effect free after validation; artefact activation/rollback is atomic and reproducible |
| Workspace/release | Module discovery/workspace membership and lockstep tag rules pass without published `replace` directives |

## Definition of done

The first optional full-i18n release is complete only when:

1. M0 records a real need and an accepted single-module dependency decision;
2. root `errs`, `port` and every consumer not selecting i18n retain their current
   API, behaviour and dependency graph;
3. exactly one optional i18n module implements `errs.MessageSource` and provides
   explicit full-message formatting without a root-wide facade;
4. HTTP and gRPC consume the same message source through existing seams, with no
   i18n-specific transport package;
5. locale selection is explicit, bounded and application-owned, with no global
   or ambient environment state;
6. every advertised language passes catalogue, fallback, plural/select,
   rendering and reviewer evidence;
7. stable error/API/event/storage/policy identities are language-independent;
8. no rendered text, template, argument, raw locale or tenant identity leaks
   through default telemetry, audit or logging paths;
9. no optional extension imports another and isolated module graphs prove
   consumers download only their selected choices; and
10. build, release, compatibility, rollback and incident evidence is executable
    rather than a documentation-only claim.

## Explicit non-goals

- replacing `errs.Messages` for consumers whose current catalogue is sufficient;
- promising a full i18n module before M0 accepts a concrete use case;
- a generic UI/component framework or user-content CMS;
- runtime translation SaaS credentials, network lookup or editable live files;
- automatic language inference from IP, name, tenant, process locale or baggage;
- universal HTML/Markdown/JSON/URL safety from one rendered-string type;
- implicit time zone, currency conversion, collation or search-language policy;
- translating machine contracts, object keys or authorization policy; or
- framework-owned pairwise adapters for OTel, audit, tenancy, events, storage or
  transports.

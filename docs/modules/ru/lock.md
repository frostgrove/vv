# lock — критическая секция, на которую могут положиться два процесса

```go
import "github.com/frostgrove/vv/vvdb/lock"         // контракт и бэкенд PostgreSQL
import "github.com/frostgrove/vv/vvdb/lock/locksql" // для драйвера, который держит database/sql
```

**Модуль:** оба в корневом модуле — только стандартная библиотека и свои пакеты, так что ни один не
добавляет зависимости ([[D-033]]) · **Зависит от:** `crud`, `crud/sqlfault`, `errs`, `errs/sqlerr` ·
**От него зависят:** `jobspg`, `eventpg`, `auditpg`

Advisory-блокировка PostgreSQL — это блокировка на числе, которое вы выбрали сами, а не на строке.
Она нужна там, где сериализовать надо *решение*, у которого нет одной строки: «какие языки предлагает
эта инсталляция», «кто сейчас подчищает retention», «кто мигрирует эту схему». Держит её база,
поэтому она исключает все процессы, говорящие с этой базой, а не только горутины текущего.

Блокировка и данные разделяют транзакцию, соединение и домен отказа. Ради этого её и предпочитают
аренде в кэше: TTL-аренда может истечь, пока держатель ещё работает, и держатель об этом не узнает
никогда. Здесь базa снимает блокировку ровно в момент конца транзакции — в том числе когда процесс
умер.

## Что вы получаете

### `lock` — контракт

| | |
|---|---|
| `Key`, `KeyOf(parts...)` | имя, сведённое к `int64`: FNV-1a по частям, разделённым NUL |
| `KeyFrom(raw int64)` | для того, кто выводит ключ сам и хочет только механизм |
| `Guard`, `Exclusively(key)`, `Sharing(key)` | одна блокировка и режим, в котором она берётся |
| `Policy{Timeout, Retries}` | сколько ждать guard и сколько раз переигрывать транзакцию, попавшую в дедлок |
| `For(source, policy) (*Locks, error)` | один раз резолвит движок и отказывает тому, который не обслуживает |
| `Locks.Take(ctx, exec, guards...)` | берёт все guard в транзакции вызывающего |
| `Locks.TryTake(ctx, exec, guard)` | отвечает, был ли guard свободен, не дожидаясь |
| `Locks.Guarded(ctx, guards, fn)` | выполняет `fn` в собственной транзакции, которая держит все guard |
| `Locks.Retry(ctx, fn)` | сам цикл повторов — для того, кто открывает транзакцию иначе |
| `Locks.Retryable(err)`, `Locks.RetryCode(err)` | является ли отказ тем, что чинит повтор, и каким именно |
| `ErrNoTransaction`, `ErrDialectUnsupported` | два отказа |

```go
locks, err := lock.For(source, lock.Policy{Timeout: 10 * time.Second, Retries: 3})
if err != nil {
    return err // this engine has no advisory lock with these semantics
}

err = locks.Guarded(ctx, []lock.Guard{
    lock.Sharing(deploymentKey),      // many writers read this decision at once
    lock.Exclusively(documentKey),    // one writer at a time on this document
}, func(ctx context.Context) error {
    return write(ctx)
})
```

### `locksql` — для драйвера, который держит `database/sql`

| | |
|---|---|
| `Take(ctx, tx, policy, guards...)` | то же, что `Locks.Take`, поверх `*sql.Tx` |
| `TryTake(ctx, tx, guard)` | то же, что `Locks.TryTake`, поверх `*sql.Tx` |
| `In(tx, policy) (*lock.Locks, crud.Executor, error)` | оба сразу, когда их хочется сохранить |
| `Hold(ctx, db, key, work)` | **сессионная** блокировка на закреплённом соединении на всё время `work` |
| `ErrNotHeld` | unlock ответил false — блокировка ничего не сериализовала |

```go
// A schema migration spans several transactions, so its lock has to outlive any one of them.
err := locksql.Hold(ctx, db, migrationKey, func(conn *sql.Conn) error {
    return migrate(ctx, conn)
})
```

## Один source — одно пространство ключей

Advisory-блокировка ограничена одной **базой**. Личность критической секции — пара «база и ключ», а
не ключ сам по себе: два `Locks` над двумя базами не исключают друг друга даже на одинаковом `Key`,
а два над одной — исключают, через любые пулы и процессы. Поэтому `For` привязывается к source, а не
раздаёт свободные функции: набор guard не может случайно растянуться на две базы, а `Guarded`
открывает транзакцию ровно на том source, на котором взяты guard.

Блокировка, взятая на реплике чтения, не координирует ничего. `crud.ReadWrite` отправляет и `Exec`, и
`Query` на primary и отдаёт реплику только через `ReadSource()`, так что обычный путь безопасен;
передать `For` реплику явно — нет.

## Порядок, в котором берутся guard, выбираете не вы

`Take` сортирует по ключу и схлопывает дубликаты до самого сильного запроса. Двое, попросившие одну и
ту же пару в противоположном порядке, отправят одни и те же два оператора в одном порядке и не
смогут встретиться дедлоком. Какой это порядок — ненаблюдаемо: все guard удерживаются до того, как
пойдёт тело. `[[D-139]]`

## Повторы и где они кончаются

`Guarded` и `Retry` переигрывают дедлок, сбой сериализации, истечение lock_timeout и транзакцию,
прерванную самим движком, — коды, которые `errs/sqlerr` помечает как retryable для этого диалекта,
взятые из его версионированной таблицы, а не из списка, живущего здесь. `Take` и `TryTake` не
повторяют: они выполняются в executor, который дал вызывающий, а переигрывать чужую транзакцию —
не повтор. Ровно это разделение и есть `[[D-139]]`, сузившее `[[D-040]]`.

`Policy.Timeout` превращается в `SET LOCAL lock_timeout`, поэтому он ограничивает **любое** ожидание
блокировки в этой транзакции, а не только advisory, и откатывается вместе с транзакцией.

## Движку, который так не умеет, отказывают

`For` возвращает `ErrDialectUnsupported` для всех диалектов, кроме PostgreSQL, ещё до первого
оператора. `GET_LOCK` в MySQL сессионный там, где этот контракт транзакционный, не имеет разделяемого
режима и не участвует в детекции дедлоков; SQLite отображать не на что. Ответить любому из них более
слабой блокировкой — значит вернуть критическую секцию, которая выглядит взятой и не является ей.
`[[D-139]]`

## Ключ заморожен

`KeyOf` — это FNV-1a по частям, разделённым NUL, и производимые им числа закреплены литералами в
`TestKeyOfStillAnswersWhatItAlwaysAnswered`. Смена вывода не ломает ни сборку, ни выполнение: при
раскатке старые поды и новые просто перестают исключать друг друга — молча, до конца выкатки. Новый
вывод — это новая функция рядом, принимаемая в окно, когда ни одна блокировка не удерживается.

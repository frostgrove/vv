# accessjwt — подписанные access-токены поверх ротируемого refresh

```go
import "github.com/frostgrove/vv/auth/access/accessjwt"
```

```bash
go get github.com/frostgrove/vv/auth/access/accessjwt
```

**Модуль:** отдельный · **Зависит от:** [access](access.md), [authjwt](authjwt.md),
`golang-jwt/jwt/v5`, `google/uuid`

[`access.Strategy`](access.md#Стратегии): короткоживущий подписанный токен,
который верификатор проверяет без базы, поверх refresh-credential, ротируемого
на каждом использовании.

---

## Прочитайте это до того, как выбрать

**Работы с базой в обычном случае это не экономит.** Аутентификация всё равно
читает директорию — активен ли субъект, — и читает гранты, чтобы разрешить роли
и права. И то и другое из строк, на каждый запрос, и это намеренно ([[D-066]]):
снятая роль обязана действовать со следующего вызова, а не когда истечёт токен.
Подписанный токен убирает чтение *сессии* — одно из трёх.

**Причина его выбрать — верификатор, который не может дотянуться до базы.**
Другой сервис, другой периметр, edge с одним публичным ключом. Внутри одного
процесса с одной базой `access.OpaqueToken()` проще, а это сложность, купленная
ни за что.

**Отзыв запаздывает на `AccessTTL`, пока не добавлен список.** Подписанный токен
работает до истечения. При пяти минутах большинству продуктов этого хватает;
если нет — см. [revokeredis](revokeredis.md).

## Обвязка

```go
strategy := accessjwt.Strategy(accessjwt.Spec{
	Method: jwt.SigningMethodHS256,
	Key:    secret,
	Verify: authjwt.HMAC(secret),
	Issuer: "example.com",

	AccessTTL:    5 * time.Minute,
	RefreshGrace: 10 * time.Second,
})

users, signUp, err := access.Mount(runtime, access.SubjectSpec[SignUpForm]{
	Type:      "user",
	Directory: userDirectory,
	Strategy:  strategy,
})
```

| Поле | По умолчанию | Что это |
|---|---|---|
| `Method`, `Key` | обязательно | чем подписывается access-токен |
| `Verify` | обязательно | чем он проверяется; публичная половина для асимметрии |
| `Issuer` | обязательно | идёт в `iss` и требуется на обратном пути |
| `AccessTTL` | `5m` | время жизни токена, и задержка отзыва без списка |
| `RefreshTTL` | TTL сессии | ограничивает всю линию |
| `RefreshGrace` | `10s` | сколько только что заменённый credential ещё считается конкурентным обновлением |
| `Revocation` | нет | см. [revokeredis](revokeredis.md) |

Ответ несёт обе половины:

```json
{ "token": "…", "expiresAt": "…", "refresh": "…", "refreshExpiresAt": "…", "principal": {…} }
```

а биндинг монтирует `POST /auth/refresh` только для субъекта, чья стратегия
ротирует.

## Что лежит в токене

```go
type Claims struct {
	Subject     string `json:"sub"`
	SubjectType string `json:"sty"`
	SessionID   string `json:"sid"`
	Issuer      string `json:"iss"`
	IssuedAt    int64  `json:"iat"`
	ExpiresAt   int64  `json:"exp"`
}
```

Ролей и прав в нём **нет**. Они приходят из строк на каждом запросе, поэтому
снятая роль действует со следующего вызова.

`sty` проверяется, а не принимается на веру. Токен, выпущенный для одного вида
вызывающего и предъявленный guard'у другого субъекта, проходит проверку подписи
идеально: сессия настоящая, ничего не выглядит сломанным, просто вызывающий —
не тот, кого предполагал роут.

## Ротация

Refresh-credential тратится тем вызовом, который его использует. Строка сессии
держит дайджест текущего и предыдущего, а ротация — это compare-and-swap по
текущему. Проигранный swap — это **две** разные ситуации, и различение их и есть
весь дизайн:

```go
func Classify(presented Presented, now time.Time, grace time.Duration) Outcome
```

| Outcome | Когда | Что происходит |
|---|---|---|
| `Rotate` | дайджест текущий | меняем, отвечаем нормально |
| `RotateAgain` | предыдущий, внутри `RefreshGrace` | два таба обновились разом — ротируем ещё раз, отвечаем нормально |
| `Replay` | предыдущий, после grace | потраченный credential вернулся: **закрываем линию** |
| `Unusable` | всё прочее, либо сессия закрыта или истекла | один отказ |

Отказ на конкурентном обновлении разлогинивает человека за два открытых окна —
это тот отказ, с которым люди реально сталкиваются. Принять реплей за
конкурентное обновление — оставить украденный credential рабочим. `Classify`
чистая и базы не трогает, и только поэтому обе ситуации закреплены тестами, а не
аргументом.

На реплее закрывается вся сессия — держатель *нового* credential тоже его
теряет. В этом и смысл: одна из двух сторон не владелец аккаунта, и отсюда
невозможно определить какая. В строке остаётся `ReasonRefreshReplayed` — та
самая причина отзыва, на которую стоит настроить алерт.

Любая неудачная ротация получает один и тот же отказ, чем бы она ни была.

## Схема

`auth/access/accessjwt/migrations/00001_accessjwt.sql` добавляет две колонки в
таблицу `sessions`, которой access уже владеет:

| Колонка | Зачем |
|---|---|
| `previous_token_hash` | дайджест, заменённый последней ротацией |
| `rotated_at` | когда, чтобы окно grace что-то значило |

Отдельно от миграции access, потому что деплой на непрозрачных сессиях не
ротирует и обе колонки ему не нужны. Строка сессии *и есть* семья: один вход,
одна линия. Отдельного id для неё нет нигде, потому что семья, способная
пережить свою сессию, была бы вторым, что надо закрыть при выходе, и вторым, про
что можно забыть.

# auth — кто вызывает

```go
import "github.com/shardit-io/vv/auth"
```

**Модуль:** корневой — импортирует стандартную библиотеку и `errs`, больше
ничего · **Манифест контрактов:** нет ([[D-048]], [[D-055]])
· **Зависит от:** `errs`

`Principal` — это четыре метода. Транспорт кладёт его в контекст запроса,
политика достаёт. Между этими двумя точками весь словарь, о котором обеим
сторонам нужно договориться, — здесь.

Импортируйте напрямую, если пишете аутентификатор, middleware или политику,
читающую вызывающего.

---

## Что вы получаете

| | |
|---|---|
| `Principal` | четыре метода: `Subject`, `In`, `Has`, `Attr` |
| `Claims` | готовый `Principal` — если своего типа нет |
| `Role`, `Permission` | строки со своим типом; `RoleMap` разворачивает одно в другое |
| `Credential` | схема и токен, обе строки — транспортного типа здесь нет |
| `Authenticator` | шов, который реализует провайдер; `Chain` пробует несколько |
| `Guard` | транспортно-нейтральная половина middleware |
| `WithPrincipal`, `PrincipalFrom`, `Require` | единственный в дереве ключ контекста, несущий личность |
| `ErrUnauthenticated`, `Unauthenticated` | 401 и sentinel, который он оборачивает |

## Принципал

```go
type Principal interface {
	Subject() string
	In(r Role) bool
	Has(p Permission) bool
	Attr(name string) (any, bool)
}
```

Четыре ответа, а не четыре списка. Гейт спрашивает их один раз на операцию,
поэтому `Roles() []Role` был бы аллокацией на запрос ради списка, который в
библиотеке никто не читает.

**Свой тип личности уже есть?** Реализуйте интерфейс поверх него — этот пакет
ваш тип никогда не увидит. Ровно для этого он и интерфейс.

**Нет?** `auth.Claims` — готовая реализация:

```go
p := auth.Claims{
	Sub:         "u-1",
	Roles:       []auth.Role{"editor"},
	Permissions: []auth.Permission{"article:read"},
	Attrs:       map[string]any{"tenant": int64(7)},
}
```

`Attr` отличает «клейма нет» от «клейм есть и он nil» — то же различие, что
`crud.Opt` проводит для колонки.

## Роли и пермишены

Пермишен — та единица, которую должно называть правило: правило, называющее
роль, приходится править при каждой реорганизации ролей, а правило, называющее
пермишен, — нет.

```go
var roles = auth.RoleMap{
	"editor": {"article:read", "article:write"},
	"admin":  {"article:read", "article:delete"},
}

p := auth.Claims{Roles: []auth.Role{"editor"}}.Grant(roles)
p.Has("article:write")
p.Has("article:delete")
```

Первое — true. Второе — false: это даёт `admin`, а вызывающий им не является,
так что разворачивание ограничено ролями, которые токен действительно нёс.

**Разворачивание происходит один раз, при построении принципала.** `Has`,
который ходил бы по карте ролей в момент проверки, отвечал бы по-разному в
зависимости от того, какая карта доступна на месте вызова, — и один токен значил
бы в одном процессе две разные вещи.

`RoleMap` — значение, которое вы передаёте, а не реестр внутри пакета. Две
библиотеки, объявившие `"admin"` по-разному, не должны решать спор порядком
линковки.

`auth.Scopes("read write admin")` разбивает OAuth-клейм `scope` на пермишены —
провайдеры пишут его именно так, и вам не должно быть до этого дела.

Три квантора расходятся в пустом случае, и это сделано намеренно:

| | пермишены не названы |
|---|---|
| `HasAll(p)` | **true** — правило, не называющее ничего, ничего и не запрещает |
| `HasAny(p)` | **false** — «любой из ничего» невыполним |
| `InAny(p)` | **false** — по той же причине |

## Контекст

```go
ctx = auth.WithPrincipal(ctx, p)
p, err := auth.Require(ctx)
p, ok := auth.PrincipalFrom(ctx)
```

Первое — дело транспорта, один раз на запрос. Второе — дело политики, один раз
на операцию. Третье — для тех, кому отсутствие принципала нормальный ответ.

**Один ключ на все транспорты.** Второй ключ в HTTP-пакете был бы невидим для
gRPC-интерсептора, тесты обоих пакетов проходили бы, а политика молча
закрывалась бы только на одном протоколе.

`Require` возвращает 401, когда принципала нет. Закрываться здесь — и есть
смысл: политика, прочитавшая отсутствующего принципала как «сужения нет»,
расширила бы каждый запрос ровно на том, где middleware не подключили.

Nil-принципал не сохраняется, поэтому `PrincipalFrom` никогда не отвечает
`(nil, true)`.

## Аутентификаторы

```go
type Authenticator interface {
	Authenticate(ctx context.Context, c Credential) (Principal, error)
}
```

Две реализации в поставке: [authjwt](authjwt.md) и [apikey](apikey.md).
Напишите третью для mTLS, серверных сессий или заголовка от шлюза — остальная
подсистема не изменится.

`auth.Chain` принимает на одной точке несколько видов учётных данных:

```go
authn := auth.Chain(jwtAuthn, apiKeyAuthn)
```

Отказ, когда не сработал никто, ничего не сообщает о том, сколько было
попыток. «3 из 3 отказали» — это список схем, которые принимает деплой.

## Guard

Всё, что делает middleware и что не является формой фреймворка:

```go
guard := auth.NewGuard(authn,
	auth.Header("X-Api-Key"),
	auth.Optional(),
)

ctx, err := guard.Authenticate(r.Context(), r.Header.Get)
```

Обе опции меняют умолчание: без них учётные данные читаются из `Authorization`,
а запрос, не предъявивший их, отклоняется.

`Authenticate` принимает `func(name string) string`. `http.Header.Get`,
`gin.Context.GetHeader`, `fiber.Ctx.Get` и метаданные gRPC — все дают такую
функцию, и именно это позволяет четырём транспортам разделять все решения выше
неё.

`auth.Lookup` заменяет правило целиком, если учётные данные лежат не в
заголовке:

```go
auth.Lookup(func(get func(string) string) (auth.Credential, bool) {
	if k := get("X-Api-Key"); k != "" {
		return auth.Credential{Scheme: "ApiKey", Token: k}, true
	}
	return auth.Bearer(get("Authorization"))
})
```

**`Optional` не пропускает плохие учётные данные.** Токен, не прошедший
проверку, — это 401 независимо от того, опциональна ли точка: считать его
анонимом означало бы, что протухшая сессия молча видит публичную выдачу вместо
предложения войти заново.

**Второй guard не аутентифицирует повторно.** Контекст, где принципал уже есть,
возвращается нетронутым, поэтому middleware, подключённый глобально и ещё раз на
группе, стоит одной проверки.

## 401

```go
return auth.Unauthenticated("signature does not verify")
```

- `errs.KindUnauthorized`, поэтому любая существующая таблица статусов отвечает
  401 — `porthttp.StatusFor` и `crudgrpc.CodeFor` умели это и раньше, новой
  ветки не понадобилось;
- оборачивает `ErrUnauthenticated`, поэтому `errors.Is` по-прежнему работает;
- **причина никогда не попадает в тело.** Она едет в обёрнутой ошибке.

Последнее — не вопрос вкуса. `port.Violations` синтезирует одно нарушение для
fault без нарушений (а 401 всегда таков) и копирует туда `Fault.Message`, и это
нарушение рендерится. Причина, положенная туда, сообщает тому, кто перебирает,
над какой половиной токена работать. Все отказы рендерятся одинаково:
`unauthenticated`, «authentication is required» ([[D-056]]).

Чтобы достать причину для лога — `errors.As` до `*errs.Fault` и `Unwrap`.
Учтите, что `errors.Unwrap` до неё **не** доберётся: fault разворачивается в
срез, а односоставная форма по срезу не ходит.

## Связь с репозиторием

`auth` ничего не решает. Что именно разрешает пермишен — это
[security](security.md):

```go
policy := security.Combine(
	security.RequirePermission[Article, int64]("article:read"),
	security.ScopeAttr[Article, int64]("TenantID", "tenant"),
)
articles := Articles.Bind(db, security.Gate(policy))
```

Импорт идёт в одну сторону — `security` знает про `auth`, `auth` про репозиторий
не знает, — поэтому middleware никогда не втягивает в сборку AST предикатов.

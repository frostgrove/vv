# errs/sqlerr — ошибка драйвера становится кодом

```go
import "github.com/shardit-io/vv/errs/sqlerr"
```

**Модуль:** корневой · **Зависит от:** `errs` и стандартной библиотеки. **Без
импортов драйверов, без базы данных**

Чистые функции, одна таблица на диалект. Дайте им то, что сказал драйвер, и они
ответят, чем нарушение *было* — `unique`, `foreign_key`, `required` — плюс какая
таблица и какие колонки, там, где движок вообще потрудился это сказать.

**Вы редко вызываете это напрямую.** [sqlfault](sqlfault.md) вызывает это за
вас, а `crudsql.WithFaults` / `crudpgx.WithFaults` подключают это. Читайте эту
страницу, чтобы знать, что ваш движок может сказать, а что нет.

---

## Точка входа

```go
code, source, ok := sqlerr.Classify("postgres", &sqlerr.Err{
    SQLState: "23505",
    Fields:   map[string]string{"ConstraintName": "users_email_key", "TableName": "users"},
})
// code == errs.CodeUnique, source.Constraint == "users_email_key", ok == true
```

`dialect` — один из `"postgres"`, `"mysql"`, `"mariadb"`, `"sqlite"`.

**Третий результат `false` означает «ни одна ветка не подошла».** Вызывающий не
должен превращать это в собственный код: неклассифицированная ошибка — это 500,
а догадка хуже молчания.

Функция тотальна — неизвестный диалект и nil-ошибка одинаково отвечают false, а
не паникуют.

## Три ключа, потому что три из четырёх движков ломают очевидный

Классификатор ключуется по `(dialect, sqlstate, native)`, и **ни одна его ветка
не проверяет класс SQLSTATE** ([[D-046]]).

| Движок | Ключ |
|---|---|
| PostgreSQL | весь SQLSTATE — `23505` |
| MySQL | состояние **и** номер вместе — `1062` / `23000` |
| MariaDB | то же самое, но это **другая таблица**, чем у MySQL |
| SQLite | номер, читаемый как байты; **SQLSTATE отсутствует вовсе** |

Почему не класс:

- **MySQL** отвечает на упавший CHECK кодом `3819 / HY000`, а на отсутствующее
  значение по умолчанию — `1364 / HY000`. Ни один не начинается с `23`.
- **MariaDB** отвечает на тот же CHECK кодом `4025 / 23000` — внутри класса 23.
  Одинаковое ограничение на двух движках с общим драйвером, диалектом и
  протоколом требует двух разных веток.
- **SQLite вообще не сообщает SQLSTATE.** Для четверти поддерживаемых движков
  проверка класса просто отсутствовала — каждое нарушение ограничения в SQLite
  было неклассифицированным 500, пока это не нашёл корпус.
- **Один и тот же номер может нести разные классы.** `1366` у MySQL — это
  `HY000`, а у MariaDB — `22007`.

## Что не имеет права читать ни одна ветка

`Err.Message`, `Fields["Detail"]`, `Fields["Hint"]` и `Err.Type`.

PostgreSQL, MySQL и MariaDB локализуют первые три поля через языковую настройку
сессии, так что парсер, читающий любое из них, классифицирует по-разному в
зависимости от того, где развёрнут сервер ([[D-039]]). Корпус хранит
дублирующийся кейс, снятый с сервера, отвечавшего **на русском**, — чтобы это
было тестом, а не обещанием.

## Что каждый движок реально сообщает

**Измерено, а не по памяти.** Каждая ячейка спровоцирована на живом сервере и
зафиксирована в `errs/sqlerr/testdata/corpus/`: PostgreSQL 17, MySQL 8.4,
MariaDB 11.4, SQLite 3.53.

| Нарушение | PostgreSQL | MySQL | MariaDB | SQLite |
|---|---|---|---|---|
| unique | `23505`; ограничение, таблица, схема | `1062`/`23000`; имя индекса в сообщении | `1062`/`23000`; имя индекса без префикса таблицы | ext `2067`; имена `table.column`, без ограничения |
| первичный ключ | `23505` на pk-индексе | `1062` на `PRIMARY` — имя на *каждой* таблице InnoDB | так же | ext `1555` |
| FK, родитель отсутствует | `23503` | `1452`/`23000` | `1452` | ext `787`, **вообще без деталей** |
| FK, есть ссылающийся потомок | `23503` — **не** `23001`; `TableName` — это *потомок* | `1451`/`23000` | `1451` | ext `787`, без деталей |
| NOT NULL | `23502`; колонка и таблица | `1048`/`23000` | так же | ext `1299`; имена `table.column` |
| отсутствует значение по умолчанию | схлопывается в `23502` | **`1364`/`HY000`** — отдельное условие | так же | схлопывается в ext `1299` |
| CHECK | `23514`; ограничение | **`3819`/`HY000`** | **`4025`/`23000`** | ext `275`; безымянное → исходник выражения |
| exclusion | `23P01` — **ветки ещё нет**, см. roadmap | — | — | — |
| слишком длинно | `22001` — **ни колонки, ни таблицы** | `1406`/`22001`; колонка и строка | так же | **не проверяется** |
| вне диапазона | `22003` | `1264`/`22003` | так же | **не проверяется** |
| неверный синтаксис типа | `22P02` | `1366`/`HY000` | **`1366`/`22007`** | **не проверяется** |
| deadlock | `40P01` | `1213`/`40001` | так же | `5` — один писатель, цикла быть не может |
| сбой сериализации | `40001` | `1213`/`40001` — для InnoDB это цикл блокировок | так же | `5` |
| таймаут блокировки | `55P03` | `1205`/`HY000` | так же | `5` |
| транзакция прервана | `25P02` | нет — откат на уровне запроса | нет | нет |

### Пять следствий, которые стоит знать до того, как проектировать вокруг этого

1. **SQLite не проверяет ни ширину, ни диапазон, ни объявленный тип.**
   `VARCHAR(8)` хранит 27 символов, 99999 помещается в маленькую колонку, а
   `'abc'` остаётся текстом в колонке INTEGER. Один и тот же payload даёт 422 на
   двух других серверах и 200 на SQLite ([[D-019]]).
2. **Ошибка внешнего ключа в SQLite не несёт ничего** — `FOREIGN KEY constraint
   failed`, и это всё сообщение целиком. Сказать, какой именно ключ, может
   только [каталог](catalog.md).
3. **PostgreSQL не может отличить два направления внешнего ключа** по
   структурированным полям. Оба — `23503` с одинаковым именем ограничения, и для
   направления «ссылающийся потомок» `TableName` — это **потомок**, таблица,
   которую запрос вообще не упоминал. Поэтому `restrict` репортится как
   `foreign_key` на PostgreSQL и SQLite, а на MySQL и MariaDB остаётся
   `restrict`.
4. **Даже значению нельзя доверять.** `1062` у MySQL склеивает значения
   составного ключа через `-`, так что `('x-1','y')` репортится как `'x-1-y'`.
   На префиксном индексе репортится *усечённый префикс*, а не то, что было
   отправлено.
5. **В MySQL любой структурный факт помимо номера берётся из каталога.**
   `mysql.MySQLError` имеет `Number`, `SQLState` и `Message` — и больше ничего.

## Корпус

`errs/sqlerr/testdata/corpus/{postgres,mysql,mariadb,sqlite}.json` — по 20
кейсов на движок, каждый **спровоцирован на живом сервере** и записан дословно,
вместе с запросом, который его вызвал.

```json
{
  "name": "unique",
  "kind": "integrity",
  "want": "unique",
  "stmt": "INSERT INTO cx_users (email) VALUES ('taken@example.com')",
  "err": { "type": "*pgconn.PgError", "sqlstate": "23505", "native": 0,
           "message": "duplicate key value violates unique constraint …",
           "fields": { "ConstraintName": "cx_users_email_key" } }
}
```

Парсеры написаны по этим записям, а затем прогоняются на них же, так что
**ничто не отделяет протестированное от того, что поставляется**. Кейс с
`"want": ""` должен оставаться неклассифицированным — неопределённая таблица,
отказ в доступе, соединение, так и не дошедшее до сервера. Кейс с
`"unreachable"` фиксирует, что этот движок такое нарушение вообще не производит,
и почему.

`make corpus` пересобирает его заново. `sqlerr.Load(dir, engine)`, `Save`,
`Path` и `Corpus.Case(name)` читают и пишут его.

Таблица, которую это заменило, была написана по документации, и **половина в
ней была неверна**. Первый же прогон нашёл живой баг, живший столько же,
сколько существовала поддержка SQLite.

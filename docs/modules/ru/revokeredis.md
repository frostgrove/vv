# revokeredis — список отзыва accessjwt в Redis

```go
import "github.com/frostgrove/vv/auth/access/accessjwt/revokeredis"
```

```bash
go get github.com/frostgrove/vv/auth/access/accessjwt/revokeredis
```

**Модуль:** отдельный · **Зависит от:** [accessjwt](accessjwt.md),
`redis/go-redis/v9`, `google/uuid`

Заставляет подписанный токен перестать работать сразу, как сессия закрыта, а не
когда он истечёт.

---

## Когда это нужно

Только когда `accessjwt.Spec.AccessTTL` — слишком большое окно между отзывом
сессии и тем, как отзыв начнёт действовать. При пяти минутах обычно не слишком.
Добавление этого стоит одного обращения на **каждый** аутентифицированный
запрос, поэтому оно обязано быть быстрее того чтения сессии, ради избегания
которого подписанный токен и выбирали.

В это окно попадает не только реплей, но и обычный выход. `access` сообщает
стратегии о каждой закрытой сессии ([[D-072]]), поэтому со сконфигурированным
списком `POST /auth/logout`, `logout-all`, закрытие одной сессии из списка и оба
пути смены пароля действуют со следующего запроса; без него — с момента
истечения access-токена. Что из этого продукт переживёт — и есть всё решение.

**Deny-list в базе держать смысла нет.** Это то же самое чтение сессии обратно,
только с худшей семантикой: allow-list, который не читается, отказывает всем —
это громко и безопасно, — а deny-list, который не читается, пустил бы всех, если
это специально не остановить. Поэтому `Revoked` возвращает ошибку, а не `false`.

## Обвязка

```go
list, err := revokeredis.New(client)          // клиент открываете вы
if err != nil {
	return err
}
if _, err := list.VerifyEvictionPolicy(ctx); err != nil {   // на старте, а не здесь
	return err
}

strategy := accessjwt.Strategy(accessjwt.Spec{
	// … подпись, issuer, TTL …
	Revocation: list,
})
```

Клиент передаётся снаружи, а не поднимается здесь, ровно по той же причине, что
и подключение к базе: кто открывает соединение, с каким пулом и какими
таймаутами — решение приложения.

| | |
|---|---|
| `New(client, options...)` | собирает список и никуда не ходит |
| `Prefix(string)` | пространство имён для ключей; по умолчанию `access:revoked:` |
| `Logger(*slog.Logger)` | куда уходит предупреждение со старта; по умолчанию `slog.Default()` |
| `OnUnknownPolicy(Reported\|Refused)` | что делать с сервером, который не говорит, что он вытесняет; по умолчанию `Reported` |
| `VerifyEvictionPolicy(ctx)` | проверка на старте — см. ниже |
| `Ping(ctx)` | доступность сама по себе, с `ErrUnreachable` внутри |

`New` не открывает соединения и ничего не спрашивает, поэтому проверка
принадлежит тому, кто владеет жизненным циклом. Под fx это
[биндинг ниже](#fx-форма): он вешает её хуком старта, потому что конструктор
исполняется внутри `fx.New`, куда `fx.StartTimeout` не достаёт и где отказ не
откатывает ничего из уже построенного.

## Проверка

Redis под `maxmemory` с вытесняющей политикой удаляет холодные ключи, чтобы
освободить место, а отзыв между выходом и следующим запросом — примерно самый
холодный ключ, какой бывает. `Revoked` не отличает это удаление от истечения, с
которым запись создавалась, поэтому отвечает «не отозван», и вышедший токен
снова работает. Ни один тест этого не увидит: в разработке Redis живёт с
`maxmemory 0` и `noeviction`, где бага просто нет.

Поэтому список спрашивает. `VerifyEvictionPolicy` отправляет
`CONFIG GET maxmemory-policy` и возвращает то, что узнал, вместе с отказом —
если отказ есть.

| Вердикт | Когда | Что происходит |
|---|---|---|
| `Retaining` | сервер ответил `noeviction` | проверка проходит |
| `Evicting` | сервер назвал любую другую политику | отказ с `ErrEvicting`, с именем политики |
| `Unknown` | сервер не ответил | `WARN`, либо `ErrUnknownPolicy` при `OnUnknownPolicy(Refused)` |

**Семейство `volatile-*` отвергается тоже.** `volatile-lru` вытесняет только
ключи с TTL — звучит как освобождение от правила, а на деле ровно наоборот:
каждый ключ этого списка написан с TTL, так что под вытеснение попадает весь
список.

**`Unknown` — это вердикт, а не проходной балл.** На Elasticache, Upstash и
большинстве других managed Redis `CONFIG` выключен или закрыт ACL, и ответом
приходит ошибка прав, а не политика. Отказывать там — значит сделать пакет
непригодным на площадках, где крутится большинство деплоев; считать это успехом —
значит сделать самый частый случай самым молчаливым, а это и есть исходный
дефект. Поэтому ни то, ни другое: вердикт — `Unknown`, он несёт причину, которую
назвал сервер, и по умолчанию `WARN` называет параметр, последствие и два выхода.
Деплой, который подтвердил `noeviction` вне канала — или который лучше не
запускать, пока не подтвердил, — пишет `OnUnknownPolicy(Refused)`, и то же
событие тогда возвращается, а не логируется.

**Сервера, которого нет, это не касается: он отвергается при любой опции.**
`CONFIG` падает одинаково и от ACL, и от того, что никто не слушает, а второе —
не «политика, которую не назвали»: это список, который провалит каждое чтение, а
deny-list, который не читается, отказывает каждому аутентифицированному запросу.
Поэтому ветка `Unknown` сначала пингует, и отсутствующий сервер падает с
`ErrUnreachable`. Поблажку `Reported` получает только сервер, который ответил, —
а значит, проверка вытеснения заодно и есть проверка доступности, и отдельный
`Ping` на старте уже ничего не добавляет.

См. [[D-112]].

## fx-форма

```go
import "github.com/frostgrove/vv/auth/access/accessjwt/revokeredis/revokeredisfx"
```

```bash
go get github.com/frostgrove/vv/auth/access/accessjwt/revokeredis/revokeredisfx
```

**Модуль:** отдельный · **Зависит от:** revokeredis, `go.uber.org/fx`

Отдельный модуль, чтобы сборка списка руками — или другим контейнером — не тянула
за собой fx ([[D-033]], [[D-074]]).

```go
fx.New(
	fx.Provide(func() redis.UniversalClient { … }),   // клиент по-прежнему ваш
	revokeredisfx.Auto(),
)
```

| | |
|---|---|
| `Auto()` | список из `redis.UniversalClient` графа, опубликованный как `*revokeredis.List` и как `accessjwt.RevocationList`, с проверкой на старте |
| `Revoking(options...)` | то же самое, но со своими `revokeredis.Option` |
| `Verifying()` | только хук старта, над `*revokeredis.List`, который корень собрал сам |

`*slog.Logger` из графа становится логгером списка. Он необязателен, а
написанный в `Revoking` `revokeredis.Logger(...)` его перебивает: граф даёт
умолчание, вызывающий решает.

Пока граф строится, до Redis не доходит ничего. Проверка идёт на хуке старта,
поэтому её ограничивает `fx.StartTimeout`, а отказ откатывает пулы и клиентов,
которые старт уже успел открыть.

## Где он должен жить

Проверка спрашивает, что сервер делает, когда переполняется. Кто ещё живёт на
этом сервере — вторая половина того же вопроса, и `CONFIG` на неё не отвечает:
кеш на том же инстансе и есть то, из-за чего инстанс переполняется, а `Prefix`
здесь не помогает — он разделяет имена, а не память.

Поэтому идентичностей ресурса три, по одной на вид состояния — кеш, durable
work и этот список, — и объявляются они в композиционном корне. Назовите ресурс,
куда смотрит этот клиент, тенантом `cache.DurableSecurityTenant`
([cache](cache.md)); активация после этого отвергает любой кеш, попавший на
тот же ресурс, и никакой waiver этого не извиняет. Совместное проживание с
очередью задач — единственное пересечение, которое извиняет написанный
`cache.SharedDurableSecurity(reason)`. Необъявленный ресурс не проверен, а не
доказанно отдельный. См. [[D-104]].

## Что там лежит

По одному ключу на отозванный **id сессии**, а не на id токена: id сессии
переживает ротацию, поэтому отзыв обязан закрыть и те credential'ы, которые ещё
не выпущены, а не только тот, что в полёте.

Каждая запись истекает тогда, когда истёк бы последний токен, называющий эту
сессию, — так список остаётся размером с токены, реально находящиеся в полёте, а
не со всеми когда-либо закрытыми сессиями. Уже прошедший момент записывается с
полом в одну секунду, а не пропускается: часы вызывающего и Redis'а могут
расходиться, а держать бесполезный ключ секунду не стоит ничего рядом с ценой
выброшенного живого.

# event/eventpg — хранилище событий на PostgreSQL

```go
import "github.com/frostgrove/vv/event/eventpg"
```

```bash
go get github.com/frostgrove/vv/event/eventpg
```

**Модуль:** собственный — его живым фикстурам нужен драйвер, а один сателлит —
это одно решение о зависимости ([[D-033]], [[D-051]]) · **Зависит от:**
[event](event.md), [crud](crud.md), [crudsql](crudsql.md), [errs](errs.md) ·
**От него зависят:** ничто

`eventpg` — полная реализация `event.Store` поверх PostgreSQL 14+. Допуск по
ожидаемой версии — это условное обновление строки, которое вычисляет сам
PostgreSQL, а не версия, прочитанная в Go; одно добавление — это **один
оператор**, поэтому продвижение версии и строки событий фиксируются или
откатываются вместе на пуле точно так же, как внутри транзакции вызывающего;
история неизменяема на уровне базы данных, а не потому, что в этом пакете нет
`UPDATE`; а обход журнала выдаёт **осевший** водяной знак, а не самую новую
позицию.

Он прогоняет [`eventtest`](eventtest.md) без единого изменения, дважды — на
значениях по умолчанию и на узких пределах, — и девятнадцать из двадцати секций
отчитываются *passed*. Двадцатая — `monotone visibility`, которую это хранилище
не заявляет. Эта перепись проверяется по секциям, а не читается глазами из
журнала: секция, которую `eventtest` не смог сертифицировать, сообщается, не
проваливая прогон.

## Что вы получаете

| | |
|---|---|
| `New(Spec)` | `*Store`. Не выполняет ввода-вывода, ничего не запускает, не читает окружение |
| `Store.Prepare(ctx)` | миграция (только под `ManageSchema`), затем проверка. Пока он не вернул nil, любая операция отказывает |
| `Store.Migrate(ctx)` · `Store.Verify(ctx)` | две половины развёртывания, запускаемые по отдельности. `Migrate` отказывает под `VerifySchema` |
| `Store.Check(ctx)` | ответ о готовности — структурно `health.Probe`, без импорта `health` и без собственной важности ([[D-091]]) |
| `Store.Schema()` · `Store.SchemaManagement()` | то, с чем это значение было построено |
| `MigrationStatements(Schema)` | путь оператора: одиннадцать операторов по порядку, все — транзакционный DDL |
| `Schema.Resolved()` · `Schema.Fingerprint()` | числа, которые развёртывание собирается записать, и отпечаток, который сравнивают при инциденте, — оба без построения хранилища |

```go
store, err := eventpg.New(eventpg.Spec{
	DB:               pool,
	Source:           crudsql.Postgres(pool),
	Schema:           eventpg.Schema{Name: "frostgrove_events"},
	SchemaManagement: eventpg.ManageSchema, // разработка; продакшен не говорит ничего
})
if err := store.Prepare(ctx); err != nil {
	return err
}

repo, err := event.Bind(event.Open(store), Account)
```

`Spec.Source` **обязателен**. Хранилище, которое не видит транзакцию
вызывающего, пишет рядом с его работой, а не внутри неё, — это ловушка, а не
урезанная конфигурация; `New` отказывает `Source`, который указывает не на тот
же источник данных, что `DB`.

Каждое число необязательно и каждое проверяется. `Schema.MaxPayload` и
`Schema.MaxKey` — операнды `CHECK` и входные данные отпечатка, поэтому они живут
на схеме; `Spec.MaxBatch`, `Spec.StreamPage` и `Spec.MaxRead` не касаются ни
одной строки и живут на спецификации. Ноль берёт значение по умолчанию,
отрицательное отвергается, как и всё, что выше потолка фреймворка.

## Любой драйвер `database/sql` для PostgreSQL

Хранилище связывает только `string`, `int32`, `int64`, `bool`, `time.Time` и
`[]byte` и сканирует только их — и никогда срез Go как массив PostgreSQL, что
является расширением драйвера и что отвергает собственный конвертер
`database/sql`. `xid8` читается как `::text` и разбирается, потому что это не
тип, покрываемый контрактом сканирования, и два основных драйвера возвращают его
по-разному. Поэтому `pgx/v5/stdlib`, `lib/pq` и всё прочее, что говорит на
`database/sql`, собирается вместе, а потребитель уже на `ent`, `gorm`, `sqlx`,
`sqlc` или `bun` передаёт тот пул, который у него уже есть. Модуль требует
`pgx/v5` для собственных живых фикстур и не импортирует его ни в одном
не-тестовом файле — ту же самую версию уже несёт `jobspg`.

## Управление схемой — выбор профиля развёртывания

Не сказать ничего — это `VerifySchema`: процесс проверяет и ничего не создаёт.
`ManageSchema` мигрирует под сессионной advisory-блокировкой, удерживаемой на
**одном закреплённом соединении**, поэтому две реплики, стартующие вместе, берут
одну блокировку на одном бэкенде, а не гоняются за `23505` по
`pg_type_typname_nsp_index`.

Проверка — это три уровня, и она закрывается на первом же: целое число версии,
затем отпечаток байт в байт, затем сам каталог — вид и хранение отношения,
колонки с их умолчаниями и identity, первичные ключи, уникальные и внешние ключи,
сравниваемые **структурно**, check-ограничения, сравниваемые по токенам,
`INCREMENT`/`CACHE`/`CYCLE` последовательности identity, точный набор триггеров
**и то, что делают их функции**, и отсутствие правил и политик. Лишние индексы и
лишние ограничения освобождены, потому что каждый из них громко падает при
записи. `Check` выполняет уровни 1 и 2 плюс идентичность журнала — единственный
дрейф, которого отпечаток не видит: схема, удалённая и мигрированная заново под
работающим хранилищем, даёт тот же отпечаток, а каждый выданный курсор становится
чужим.

[`MIGRATIONS.md`](https://github.com/frostgrove/vv/blob/main/event/eventpg/MIGRATIONS.md)
несёт путь оператора, одиннадцать операторов и назначение каждого, а также способ
удалить строку, которую отвергает чтение.

## Добавление — это один оператор

```
WITH admitted AS (INSERT INTO streams … ON CONFLICT DO UPDATE … WHERE s.version = $expected RETURNING version)
INSERT INTO events … SELECT … FROM admitted, (VALUES …) AS record(…) ORDER BY record.ord
```

Проигранная гонка — это **нулевое число строк**, а не нарушение уникальности,
поэтому конфликт никогда не зависит от перехвата ошибки. Свежий поток берёт
спекулятивную вставку, поэтому два писателя на версии 0 тоже не влетают в
нарушение: второй блокируется, идёт по ветке `DO UPDATE`, не проходит предикат и
ничего не пишет. `recorded_at` — это `statement_timestamp()`: один момент на всю
пачку, из базы данных, а не из процесса, — поэтому здесь нет `Spec.Clock`.

Хранилище **не выбирает уровень изоляции и ничего не открывает, не фиксирует и не
откатывает**. Оно корректно на `READ COMMITTED`, `REPEATABLE READ` и
`SERIALIZABLE`; различается лишь то, что скажут проигравшему гонку. На
`READ COMMITTED` проигранная гонка — это `ErrConflict`; на двух верхних уровнях
PostgreSQL сначала поднимает `40001`, который это хранилище классифицирует как
отказ бэкенда с **повторяемой** причиной и никогда как конфликт ([[D-126]]).

## Неопределённость никогда не разрешается догадкой

Каждый оператор выполняется на `*sql.Tx`, который привязал вызывающий, или на
`*sql.Conn`, который этот вызов взял из пула, — и никогда на `*sql.DB`, чей
`ExecContext` повторяет `driver.ErrBadConn` на трёх соединениях и выполнил бы
одно добавление трижды ровно на том пути, где исход неопределён.

`NotWritten` отвечается только по доказательству: операция была внутри транзакции
вызывающего, либо не было выполнено вообще ничего, либо драйвер сообщил
`driver.ErrBadConn`, либо вернулся SQLSTATE вне класса `08` и вне трёх кодов
завершения сессии — что означает, что бэкенд обработал оператор, прервал его и
выжил, чтобы об этом сказать. **Всё остальное — `Unconfirmed`**, что ядро
отображает как `ErrUncertain`. Ветки по умолчанию, которая угадывает
`NotWritten`, здесь нет.

## Обход журнала выдаёт осевший водяной знак

`position` берётся из identity-колонки, поэтому значение выбирается при вставке
строки, а не при её фиксации: в позициях есть пропуски, сожжённые откатом, и
писатель, удерживающий низкую позицию, может ещё работать, когда более высокая
уже зафиксирована. Хранилище, отвечающее `position > cursor`, выдало бы более
высокую и никогда более низкую, и ничто ниже по потоку не смогло бы этого
увидеть.

Поэтому курсор — это три числа: докуда дошёл обход, идентификатор транзакции,
выпущенный после того, как были выбраны все позиции до некоторого предела, и сам
этот предел. Пропуск проходится только тогда, когда нижняя граница кластера
прошла этот идентификатор, — а значит, каждая транзакция, которая могла выбрать
позицию ниже, завершилась. Сожжённый пропуск проходится внутри одного `ReadAll`;
живой останавливает обход, пока писатель не закончит.

**Чужие писатели покрыты, и одна форма — нет.** Обход покрывает любого писателя,
который позволяет identity-колонке выбрать позицию, — psql, миграционный скрипт,
другой сервис, — потому что статементный триггер `events_position_needs_xid`
выдаёт пишущей транзакции идентификатор *до* того, как берётся умолчание
identity. Он **не** покрывает писателя, который выбирает позицию через `nextval`
в одной транзакции, даёт этой транзакции завершиться и вставляет строку позже с
`OVERRIDING SYSTEM VALUE`; такая строка будет пропущена. Выбранная и вставленная
внутри одной транзакции — покрыта.

**Вычитывание журнала — дело вне записи.** Обход на контексте, несущем транзакцию
этого backing'а, останавливается на первом же встреченном пропуске и не проходит
его, сколько бы раз его ни вызвали: он никогда не выпускает границу, по которой
пропуск оседает, — потому что на собственной транзакции вызывающего такая граница
ничего не осаждает (нижняя граница, о которой сообщает снимок этой транзакции,
никогда не проходит идентификатор, который держит сама транзакция), а выпуск её
на втором соединении, пока вызывающий держит первое, — это то, как пул на своём
пределе входит в взаимную блокировку. На `REPEATABLE READ` снимок заморожен, и
обход не смог бы осадить даже в принципе. Курсор, сохранённый из такого обхода,
к тому же стоит за событиями, которые транзакция ещё может откатить.

## Чего это стоит в идентификаторах транзакций

Триггер, выдающий xid, срабатывает один раз на оператор независимо от того,
произвёл ли оператор строки, — поэтому **проигравшее** добавление, которое ничего
не записало, тоже потребляет идентификатор транзакции. Это не проблема
корректности: идентификатор принадлежит транзакции, которая немедленно
завершается и оседает в тот же момент, — это и есть работа водяного знака. Рядом
с этим обход, встретивший пропуск, для которого нет полезной непогашенной
границы, выпускает один идентификатор — и только тогда.

## Что оно говорит о себе

| Возможность | Ответ |
|---|---|
| `Transactions` | `Supported` — `Spec.Source` обязателен, поэтому это безусловно |
| `Persistence` | `Supported` |
| `MonotoneVisibility` | `Unsupported` — обход может остановиться раньше добавления, которое уже вернулось; это работа осевшего водяного знака |
| `SharedBacking` | `Supported` — backing — это пул **и** схема вместе, поэтому две схемы одной базы данных суть два backing'а, и курсор между ними не переходит |

`Close` идемпотентен, каждый раз возвращает nil, не закрывает ни одного `*sql.DB`
и не разрешает ни одной транзакции: пул открыт корнем композиции и разделяется со
всеми прочими хранилищами, репозиториями и подсистемами над ним.

Ничто здесь не запускает горутину, не регистрирует `runtime.Runner`, не читает
переменную окружения и не пишет в логгер ([[D-092]]).

## Чего здесь намеренно нет

| Не экспортировано | Почему |
|---|---|
| `Open(ctx, db, …)` | схема хранилища событий — это история; `New` + `Prepare` — единственное написание, поэтому никто не получит мигрирующее хранилище, потянувшись за коротким конструктором |
| `Tail(ctx)` | курсор в конце журнала корректен только если осели все позиции ниже, а никакое чтение за O(1) этого не доказывает |
| `Spec.Clock` | `recorded_at` — это `statement_timestamp()`; часы, которые хранилище затем игнорирует, были бы ложью |
| `Spec.TxOptions` | ни один из восьми методов не начинает транзакцию |
| повтор, backoff или предохранитель | [[D-040]] |
| собственный тип курсора, позиции или исхода | все три принадлежат ядру |

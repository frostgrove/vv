# query — DSL для передачи по проводу

```go
import "github.com/frostgrove/vv/crud/query"
```

**Модуль:** корневой · **Зависит от:** `crud` и стандартной библиотеки
· **Contract manifest:** есть ([[D-048]])

Один JSON-документ компилируется в `crud.Options`. Каждый путь резолвится
относительно модели **до того, как появится хоть какой-то SQL**, поэтому
неизвестное поле — это отказ с указанием проблемного пути, а не тихо
отброшенное условие ([[D-013]]).

**Вы почти никогда не импортируете этот пакет напрямую** — четыре транспортных
биндинга говорят на нём за вас. Импортируйте его, чтобы ограничить, что вправе
запросить клиент (`query.Config`), или чтобы принимать документ запроса на
своём собственном эндпоинте.

---

## Документ

```json
{
  "page": 2, "limit": 20,
  "sort": ["-createdAt", "author.name"],
  "preload": ["author", {"path": "comments", "filter": {"approved": true}, "maxRows": 100}],
  "select": ["id", "title"],
  "search": "generics", "searchFields": ["title", "body"],
  "filter": {
    "views":       {"gte": 100, "lt": 1000},
    "status":      ["draft", "review"],
    "author.name": {"contains": "an"},
    "tags.slug":   {"in": ["go", "rust"]},
    "publishedAt": {"isNull": false},
    "or":  [ {"title": "a"}, {"and": [{"views": {"gt": 10}}, {"pinned": true}]} ],
    "not": {"title": "spam"}
  }
}
```

| Ключ | Значение |
|---|---|
| `page`, `limit`, `offset` | постраничная выборка по смещению |
| `after`, `before` | постраничная выборка по курсору — непрозрачная строка, отданная предыдущей страницей. Заменяет `page`/`offset`, но сохраняет лимит endpoint-а. Нужна явная сортировка, чьи поля (и неявный PK-tiebreaker) разрешены для фильтрации |
| `sort` | `["-views", "author.name"]`. Ведущий `-` — по убыванию |
| `select` | проекция. Колонки join'ов из preload сохраняются автоматически |
| `preload` | `["author"]` или `[{"path": "comments", "filter": {…}, "maxRows": 100}]`; для вложенного пути нужно явно объявить каждое звено. `maxRows` ужесточает потолок строк preload у endpoint-а, но не может его расширить. |
| `filter` | вложенная форма, см. ниже |
| `terms` | плоская форма, соединяется с `filter` через AND |
| `search`, `searchFields` | заключённое в скобки регистронезависимое OR по текстовым колонкам |
| `unpaged` | запросить все подходящие строки; требует `AllowUnpaged` и физически ограничивается `MaxLimit`, если он задан на репозитории |
| `skipTotal` | отбросить `COUNT` |
| `distinct` | `SELECT DISTINCT`; требует `AllowDistinct` |

## Операторы

```
eq  ne  gt  gte  lt  lte
like  notLike  ilike  contains  startsWith  endsWith
iContains  iStartsWith  iEndsWith
in  notIn  between  isNull  isNotNull
```

С алиасами через `$`-префикс и символьными — `$gte`, `>=`. Голое значение
означает `eq`, голый массив — `in`, `null` — `IS NULL`.

Имена полей сопоставляются без учёта регистра и разделителей, поэтому
`createdAt`, `created_at` и `CreatedAt` — одна и та же колонка.

`like`, `notLike` и `ilike` принимают сырой SQL-паттерн. `contains`,
`startsWith`, `endsWith` и их варианты `i…` трактуют значение как обычный
текст: `%`, `_` и обратная косая черта экранируются, сервер добавляет wildcard
и диалектный `ESCAPE`. Варианты `i…` сравнивают переносимо через `LOWER()`.

## Три вещи, которые здесь сделаны правильно

- **Значения типизируются по своей колонке.** `{"views": {"gte": 100}}`
  биндится как `int`, а не `float64`; `{"createdAt": {"gte": "2026-01-02"}}`
  биндится как `time.Time`. Колонка, чей тип реализует `TextUnmarshaler`,
  парсится через него, так что типы uuid и enum сохраняют собственные правила
  ([[FL-012]]). Byte-колонки используют base64 и в JSON, и в query string — как стандартное
  JSON-представление Go.
- **Search не может вырваться за пределы своего скоупа.** OR по полям поиска —
  отдельный узел AST, поэтому он всегда в скобках. Конкатенация
  `a LIKE ? OR b LIKE ?` прямо в `WHERE` — вот как отфильтрованный список
  тихо начинает возвращать всё подряд.
- **Вывод детерминирован.** У JSON-объектов нет порядка, а у Go-карт его ещё
  меньше; ключи сортируются перед компиляцией, поэтому один и тот же запрос
  всегда даёт один и тот же оператор — и его можно тестировать ([[D-014]]).

## Форма в строке запроса

Та же семантика, для `GET`:

```
?page=2&limit=20&sort=-createdAt,author.name&preload=author,comments.author
&select=id,title&q=generics&searchFields=title,body
&f=views:gte:100&f=tags.slug:in:go,rust&f=publishedAt:isNull:true
&filter={"or":[{"status":"draft"}]}
```

`f=field:op:value` повторяется и соединяется через AND. **Структурны только
первые два двоеточия**, поэтому таймстампы не ломаются. Pipe начинает следующий
term, только если текст после него имеет форму term-а; в неоднозначном случае
literal pipe пишется как `\\|`. Запятая разделяет значения только для `in` и
`notIn`; для scalar operator это обычный символ, а `\\,` сохраняет запятую
внутри значения списка. Backslash экранирует только запятую, pipe, backslash и
literal `null`; обычный backslash (например в Windows path или regexp) остаётся
как есть. Голый `null` означает SQL null, `\\null` — строковый literal.
`filter=` принимает полный JSON-документ для всего, что плоская форма выразить
не может.

**JSON — один однозначный документ.** Дублирующиеся ключи объекта дают 400 на
любой глубине; сам option и элемент `sort`, `select`, `searchFields` или
`preload` не могут быть `null`. Так proxy или validator не увидит один filter,
а сервер не выполнит last-wins вариант. `null` сохраняет смысл там, где DSL
явно его задаёт: например, в filter operand или term value.

## Ограничение

DSL управляется недоверенным вводом, поэтому ограничивайте его на каждом
эндпоинте ([[UC-002]]).

```go
cfg := &query.Config{
    Filterable:  []string{"Title", "Views", "Author.*"},  // .* разрешает поддерево
    Sortable:    []string{"CreatedAt", "Views"},
    Selectable:  []string{"ID", "Title", "Views"},
    Preloadable: []string{"Author", "Comments", "Comments.Author"},
    Searchable:  []string{"Title", "Body"},

    DefaultSearchFields: []string{"Title"},

    MaxDepth:      4,   // вложенность and/or и длина пути
    MaxConditions: 32,  // листовых сравнений в одном документе
    MaxPreloads:   4,
    MaxInValues:   200, // значений в одном списке `in`
    MaxSort:       4,   // термов сортировки
    MaxSelect:     8,   // элементов проекции
    MaxBindValues: 500, // все bind-значения во всём документе
    MaxLimit:      50,  // размер страницы клиента; по умолчанию 100
    MaxOffset:     5000,
    MaxPreloadRows: 100, // children на каждом звене запрошенной связи; превышение даёт 400

    AllowUnpaged: true, // этот эндпоинт отдаёт результат целиком
    AllowDistinct: true, // только когда endpoint действительно нуждается в DISTINCT
}
```

**Пустые списки разрешают всё, что маппит модель.** Ограничения на глубину,
условия, preload, длину списка и число сортировок действуют в любом случае.
Нулевой `Config` остаётся рабочим для первого экрана, но включает бюджеты:
100 строк страницы клиента, offset 10 000, 8 192 значений на документ и 1 000
children на preload. Большой `limit` зажимается; этот потолок передаётся даже
без `limit` и при курсорной пагинации. Слишком глубокий offset, слишком много
проекций, bind-значений либо строк preload отклоняются. Список `in` считается
за одно условие, поэтому у списков и bind-значений отдельные бюджеты. Курсор
считается как лексикографический predicate, который построит репозиторий: две
сортировки стоят три condition и три bind, поэтому cursor не обходит те же
бюджеты ([[D-060]]).

Скалярные контролы строки запроса намеренно строги: контрол может появиться
только один раз и только под одним именем. Повтор `limit`, сочетание `q` с
`search` или одновременные `after` и `before` дают 400, а не выбор, зависящий от
порядка. Так proxy, фреймворк и сервис не интерпретируют один URL по-разному.

**`AllowUnpaged` и `AllowDistinct` закрыты по умолчанию.** У первого нет
собственного потолка, второй способен запустить полную дедупликацию.
`unpaged` всё ещё ограничивается `MaxLimit` репозитория, поэтому export должен
использовать репозиторий с подходящим объявлением размера результата. Без этого
поля `{"unpaged": true}` (или `?unpaged=true`,
или `?all=1`) отклоняется как `query.Error` по пути `unpaged`: 400 по HTTP и
`InvalidArgument` по gRPC ([[D-060]]).

`remote.GetAll` никогда не передаёт `unpaged`. Он читает ограниченные страницы
и идёт по cursor edges, используя sort вызывающего или primary key модели.
Ограничительный endpoint для удалённых export-ов разрешает этот root path и в
`Sortable`, и в `Filterable`: второе требуется, потому что cursor —
лексикографический filter. Кастомный list без cursor edges — как и `Distinct`
projection без primary key, которую нельзя keyset-сортировать без смены смысла —
использует offset-страницы, поэтому его `MaxOffset` должен покрывать весь
export.

Подключите его к любому биндингу:

```go
crudfiber.WithQuery[Article, int64, ArticleUpdate](cfg)
crudgin.WithQuery[…](cfg)
crudnet.WithQuery[…](cfg)
crudgrpc.WithQuery[…](cfg)
port.WithQuery(cfg)
```

`port.NewService` проверяет каждый статический allow-list из `WithQuery` на
модели при построении сервиса: опечатка падает там, где endpoint монтируется.
При прямом использовании вызовите `cfg.MustCheck(articles.Meta())` рядом с
объявлением.

Если одному route действительно нужны vocabulary по ролям, они остаются
декларативными: `port.WithQueryFor(defaultCfg, map[string]*query.Config{
"admin": adminCfg}, selectVocabulary)` проверяет все vocabulary при старте.
Selector получает request context; `""` выбирает default, а неизвестное имя
отклоняется вместо permissive fallback.

## Использование напрямую

```go
var req query.Request
if err := json.NewDecoder(r.Body).Decode(&req); err != nil { … }

opts, err := req.Compile(articles.Meta(), cfg)
if err != nil {
    var qe *query.Error
    if errors.As(err, &qe) {
        // qe.Path и qe.Reason оба безопасно отдавать наружу
    }
}
page, err := articles.Get(ctx, opts...)
```

`query.ParseQuery(url.Values)` парсит форму строки запроса. `query.Coerce(s, t)`
конвертирует одно текстовое значение в Go-тип через собственный
`TextUnmarshaler` этого типа — экспортирована, потому что транспортам она
нужна и для параметров пути.

**Всё, что лежит в `query.Error`, безопасно рендерить.** Он называет путь,
который был неверен, и почему — и никогда не называет внутреннее имя
([[D-044]]).

## Во что обходится каждый вызов, в стейтментах

Снаружи потребитель это измерить не может, а именно это число — основная цена
использования библиотеки. Все цифры ниже сняты с записывающего `crud.Source`,
гоняющего настоящие вызовы, на PostgreSQL при размере страницы 20.

| Вызов | Стейтментов | Почему |
|---|---|---|
| `GetByID` | 1 | |
| `Get` | **2** | страница, затем `SELECT count(*)` |
| `Get`, короткая первая страница | 1 | страница короче лимита — уже весь ответ |
| `Get` со `SkipTotal` | 1 | `LIMIT n+1`; лишняя строка — проба на «есть ещё» |
| `Get` с курсором или `Unpaged` | 1 | |
| `GetAll` | 1 | без `LIMIT` — его контракт это все подходящие строки |
| `Count`, `Exists`, `Aggregate` | 1 | |
| `Save` | 1 | `INSERT … RETURNING` либо `INSERT … ON CONFLICT DO UPDATE … RETURNING` |
| `SaveAll(n)` | k | минимум bind-budgeted многострочных statements `VALUES`; чанки атомарны |
| `InsertBatch(n)` | 1 native либо k | pgx COPY при явно доступной точной capability; иначе insert-only SQL-чанки |
| `Update` | **2** | load-diff-write из [[D-010]]: `SELECT`, затем `UPDATE … RETURNING` |
| `UpdateAll`, `DeleteAll` | 1 | |
| `Delete(ids…)` | k | минимум bind-budgeted statements со списком ID; чанки атомарны |

Здесь `k` — минимальное число чанков операции после того, как фиксированные
аргументы statement и ширина строки/ID расходуют bind-лимит диалекта. Пока вызов
помещается, это 1; значение растёт только по границам строк/ID. Для insert оно может
равняться `n`, если вся форма состоит только из `DEFAULT`. `crud.PortableBatch()` принудительно
выбирает SQL-ветку строки `InsertBatch`, а `sqlrepo.PortableBatch()` объявляет этот выбор один
раз. Строки предполагают непустой input; пустые `SaveAll`, `InsertBatch` и `Delete(ids…)` —
универсальные no-op с нулём statements.

**MySQL добавляет обратное чтение** везде, где PostgreSQL пользуется
`RETURNING`: `Save` 2, `Update` 3.

**Preload — это один стейтмент на связь на уровень**, на каждые 900 ключей
([[D-006]]). Две связи на одном уровне — два стейтмента, а не join. Бюджет
`MaxPreloadRows` действует на каждом звене вложенного пути, забирает одну
строку сверх потолка и отказывает вместо того, чтобы тихо вернуть неполную
связь.

**Гейт безопасности добавляет стейтменты только там, где обязан.** Свой scope
без `Inspect` доступен только для чтения: записи с body, включая `InsertBatch`,
отклоняются до SQL. С `Inspect` фильтрованные записи забирают свои жертвы:
`UpdateAll`, `Delete` и `DeleteAll` становятся по 2, потому что правило обязано
увидеть каждую уничтожаемую строку ([[D-026]]). `InsertBatch` вместо этого
инспектирует входящие строки как `Create`, поэтому назначенные ключи не
добавляют lookup/update statements.

**Внутри транзакции счёт тот же**, а загрузка `Update` получает `FOR UPDATE`.
**С репликой** страница и счётчик `Get` идут на реплику, а всякое чтение,
решающее запись, остаётся на primary ([[D-032]]).

## Какие индексы подразумевают эти формы

DSL запросов ограничивает то, что запрос может *назвать*. Он не ограничивает то,
во что этот запрос обойдётся, и четыре формы стоит знать до того, как таблица
вырастет.

| Форма | SQL | Что нужно |
|---|---|---|
| `?search=go` без `searchFields` | `LIKE '%go%'` по **каждой строковой колонке** корневой модели, через OR | ведущему шаблону не поможет ни один B-tree индекс. Нужен триграммный или полнотекстовый, либо задайте в `Searchable` те одну-две колонки, по которым действительно ищут |
| фильтр через связь | коррелированный `EXISTS` на каждый переход ([[D-005]]) | индекс по join-колонке цели и по фильтруемой колонке |
| сортировка через связь | скалярный подзапрос на каждую внешнюю строку | то же самое, а при сортировке по умолчанию стоит подумать о денормализации |
| `?page=5000` | по умолчанию отклоняется: `MaxOffset` — 10 000, а `LIMIT 20 OFFSET 99980` за его пределом | поднять `MaxOffset` можно, но это купит глубину, а не скорость: `OFFSET` — O(n) на любом движке. Для этого и существуют курсоры ([[D-028]]) |

Первые три на страничном чтении выполняются **дважды**: для страницы и для
итога. `SkipTotal` уполовинивает их.

# authjwt — проверка JWT в вашу собственную структуру клеймов

```go
import "github.com/frostgrove/vv/auth/authjwt"
```

**Модуль:** `github.com/frostgrove/vv/auth/authjwt` — одна зависимость,
`github.com/golang-jwt/jwt/v5`
· **Зависит от:** `auth`, golang-jwt/v5

Generic по клеймам. Отдайте ему свою структуру — и она единственное, что вы
увидите: ни встроенного типа нашего, ни типа golang-jwt.

---

## Что вы получаете

| | |
|---|---|
| `New[C]`, `Parser[C].Warm`, `Parser[C].Parse` | readiness и проверка, сразу в ваш тип |
| `HMAC`, `HMAC256/384/512`, `RSA`, `ECDSA`, `EdDSA`, `JWKS`, `Custom` | источники ключей, каждый пиннит методы, которые проверяет |
| `Issuer`, `Audience`, `Leeway` | что проверяется |
| `AllowAnyIssuer`, `AllowAnyAudience`, `AllowNoExpiry` | как сказать, что проверка пропущена намеренно |
| `Authenticator` | мост к `auth.Principal` |
| `Claims`, `Standard` | готовый тип клеймов и оба вызова одним |

## Парсер

```go
type MyClaims struct {
	Subject string `json:"sub"`
	Tenant  int64  `json:"tenant"`
	Scope   string `json:"scope"`
}

parser := authjwt.New[MyClaims](
	authjwt.HMAC(secret),
	authjwt.Issuer("https://id.example.com"),
	authjwt.Audience("articles-api"),
)

claims, err := parser.Parse(ctx, token)
```

Выше нигде не упомянут `auth.Principal`. **Тот, кому нужен парсер JWT и ничего
больше из этой библиотеки, останавливается здесь** — ради этого парсер и мост
разделены на два вызова.

Цена: один переход map → JSON → структура после проверки. Registered claims
валидирует golang-jwt по карте, и только затем payload укладывается в `C`. Этот
переход — источник свободы.

Целочисленный клейм остаётся целым. При обычном разборе каждое число приходит
как `float64`, и прочитанный оттуда tenant id компилируется во float в `WHERE`
каждого суженного запроса.

## Источник ключа пиннит алгоритм

`KeySource` несёт ключ **и** методы, которые может проверить, и разделить их
нельзя:

| | проверяет |
|---|---|
| `HMAC(secret)`, `HMAC256(secret)` | HS256, минимум 32 байта секрета |
| `HMAC384(secret)` | HS384, минимум 48 байт секрета |
| `HMAC512(secret)` | HS512, минимум 64 байта секрета |
| `RSA(pub)` | RS256/384/512, PS256/384/512 |
| `ECDSA(pub)` | ES256 для P-256, ES384 для P-384 или ES512 для P-521 |
| `EdDSA(pub)` | EdDSA |
| `JWKS(url)` | все асимметричные методы выше |
| `Custom(methods, keyfunc)` | что перечислите — аварийный выход |

Ключ сам по себе оставил бы заголовку `alg` решать, как его использовать, — а
это и есть подделка key confusion: дайте RS256-верификатору токен, подписанный
HS256, и он проверит подпись, использовав **публичный** RSA-ключ как
HMAC-секрет. То есть кто угодно, кто может прочитать публичный ключ, — а это
все, — сможет выпускать токены. `alg: none` — то же семейство.

`Custom` принимает список методов отдельным аргументом, а не полем, чтобы
непиннутый парсер был виден в диффе. Никогда не выводите список из токена.

`HMAC` — короткий безопасный default: ровно HS256, не семейство алгоритмов.
Короткий секрет вызывает panic там, где объявлен источник. Явные конструкторы
нужны издателю, выбравшему другой HMAC-алгоритм; заголовок `alg` токена этот
выбор не расширяет.

Статические asymmetric-декларации проверяются и снапшотятся там же. RSA требует
нечётный составной модуль от 2048 до 16384 бит, взаимно простой с разумным
нечётным exponent; верхняя граница не даёт remote-sized big integer стать CPU
работой каждого verify. ECDSA требует точку на P-256, P-384 или P-521. Ed25519
строго декодируется как canonical curve point, а low-order точки запрещены:
одной длины недостаточно, потому что identity public key допускает универсальную
подделку `R=identity,S=0`. Парсер хранит глубокие копии, поэтому последующая
мутация вызывающего `big.Int` или byte slice не меняет trust и не создаёт гонку
с проверкой. `Custom` — явный путь для собственной схемы проверки, и её
валидация и lifetime остаются на вызывающем.

## О чём нельзя забыть

Конструкторы **паникуют при построении** на декларациях, которые дали бы лишнее
доверие: не стартовавший процесс — лучший исход ([[D-021]]):

- источник ключа, который ничего не проверяет;
- HMAC-секрет короче минимума выбранного алгоритма;
- сломанный или слабый статический RSA-, ECDSA- или Ed25519-ключ;
- нет `Issuer` и нет `AllowAnyIssuer()`;
- нет `Audience` и нет `AllowAnyAudience()`.

Каждое лечится одной строкой на месте вызова. Отказы от проверок существуют,
чтобы пропуск был осознанным и грепаемым действием, а не упущением: токен без
audience воспроизводим против любого другого сервиса, доверяющего тому же
издателю.

`exp` обязателен, если не задан `AllowNoExpiry()`. Токен без срока — учётные
данные, которые не перестают работать: одна утечка навсегда, а отозвать можно
только ротацией ключа подписи для всех.

`Leeway` по умолчанию нулевой. Тридцать секунд — обычная продовая настройка для
двух часов, которые могут разойтись.

## JWKS

```go
authjwt.JWKS("https://id.example.com/.well-known/jwks.json",
	authjwt.JWKSClient(&http.Client{Timeout: 3 * time.Second}),
)
```

Чтобы загрузить trust material до объявления readiness, а не на первом
запросе:

```go
parser := authjwt.New[MyClaims](authjwt.JWKS(jwksURL),
	authjwt.Issuer(issuer), authjwt.Audience(audience))
if err := parser.Warm(startupCtx); err != nil {
	return err
}
```

`Warm` загружает и валидирует документ тем же путём кэша, что и `Parse`. Для уже
проверенных статических источников это no-op. Протухший набор не проходит
readiness при недоступном провайдере, даже если request-трафику явно разрешено
stale-on-error окно.

Читаются ключи RSA, EC (P-256/384/521) и Ed25519; запись `oct` игнорируется,
потому что набор ключей — публичный документ, и HMAC-запись в нём это общий
секрет, опубликованный в интернете. Запись с `use`, отличным от `sig`, тоже
игнорируется. Если задан `key_ops`, он обязан быть настоящим массивом строк с
`verify`; JSON `null`, null-элементы и пустой массив — не отсутствие поля. Одна
нечитаемая запись не стоит всего набора. Но у каждой записи обязан быть
непустой `kid`, а повтор идентификатора отклоняет весь документ: trust anchor
никогда не выбирается порядком JSON-массива. Remote RSA- и Ed25519-ключи
подчиняются тем же strength и point правилам, что их static constructors:
публикация через JWKS не является более слабым путём.

У каждого закэшированного ключа ровно один JWT method. EC выводит его из `crv`,
Ed25519 — как `EdDSA`; RSA JWK обязан назвать один поддерживаемый `alg`, потому
что модуль не выбирает hash и padding. Если `alg` задан у EC или Ed25519, он
обязан быть непустым, не `null` и совпадать с выведенным методом. Только
отсутствующее поле означает unspecified. Эта per-key проверка отдельна от общей
asymmetric-family проверки parser: заголовок токена не расширяет ни одну из них.

**У закэшированного набора конечный срок свежести.** По умолчанию
`JWKSFreshness` равен пяти минутам. Первый токен на границе обновляет весь набор,
даже если его `kid` уже есть в кэше и метод токена расходится с протухшей
per-key policy: до credential verdict policy должна быть обновлена. Успешный
ответ заменяет map, поэтому отозванный провайдером ключ перестаёт проверять без рестарта.
`JWKSStaleAfter(d)` меняет возраст. `UnsafeJWKSNoFreshness()` — явный
compatibility waiver, доверяющий кэшу до miss или рестарта.

**Перезагрузка ограничена по частоте, и ограничение держится, когда провайдер
лежит.** Протухший hit или токен с `kid`, которого нет в кэше, вызывает не более
одной перезагрузки за `JWKSMinRefresh` (минута по умолчанию) и не более одной
одновременно. Без этих двух границ одна подделка на один запрос к провайдеру —
это отказ в обслуживании по провайдеру, а `kid` — вход самого вызывающего, так
что частоту выбирает он.

Обе границы — ровно то, что очевидная версия делает неправильно. Ограничение,
взводимое *успешной* загрузкой, не делает ничего, пока провайдер падает, то есть
именно тогда, когда оно нужно; а блокировку приходится отпускать на время
HTTP-запроса, так что пачка, пришедшая одновременно, проходит проверку до того,
как хоть кто-то зафиксировал попытку. Ограничение читает последнюю *попытку*, а
конкурентные промахи разделяют одну идущую загрузку, а не получают отказ: после
ротации они спрашивают `kid`, который действительно вот-вот появится.

Загрузка отделена от инициировавшего её запроса и ограничена
`JWKSFetchTimeout`. Инициатор и каждый waiter независимо ждут только в пределах
своего контекста, поэтому любой из них быстро возвращается, не отменяя работу,
которая нужна остальным. Этот caller получает исходный `context.Canceled` или
`context.DeadlineExceeded`. А timeout или transport error самой отделённой
загрузки — outage провайдера: он возвращает `ErrKeySourceUnavailable` либо
использует явно заданное stale-on-error окно, пока оно не закончилось.

Токен без `kid` подходит, только если в наборе ровно один ключ. Иначе пакет
выбирал бы за вас, какому ключу доверять. Присутствующий пустой, non-string или
иначе malformed `kid` отклоняется и никогда не переосмысливается как отсутствие.

У клиента по умолчанию нет таймаута — `JWKSClient` для того и есть.
`JWKSMinRefreshEvery(d)` сдвигает само ограничение частоты — для провайдера,
который ротирует ключи чаще или реже, чем раз в минуту, — и отклоняет ноль и
отрицательное значение. `UnsafeJWKSNoMinRefresh()` явно разрешает один запрос к
провайдеру на каждый последовательный miss. `JWKSClock` заменяет только часы
кэша, чтобы boundary-тесты не зависели от реального времени и не меняли HTTP
timeouts.

Ошибка fetch, ответа или самого документа возвращается как typed
`ErrKeySourceUnavailable`, а не как `auth.ErrUnauthenticated`: проверить
credential было невозможно. Stale-on-error по умолчанию выключен. Deployment,
которому нужно ограниченное окно доступности, объявляет его вместе с
операционным сигналом:

```go
authjwt.JWKS(jwksURL,
	authjwt.JWKSServeStaleFor(10*time.Minute,
		func(ctx context.Context, state authjwt.JWKSDegraded) {
			metrics.JWKSDegraded(ctx, state)
		}),
)
```

Observer ставится в очередь только после того, как provider singleflight
освободил waiters. Он не несёт явных `kid` или URL и получает provider cause,
возраст кэша и обе границы. Вызовы получают секундный context, сериализуются и
coalesce до новейшего pending descriptor; callback может re-enter parser,
panic или проигнорировать cancellation, не блокируя requests и не создавая по
зависшему goroutine на каждый refresh. Observation — operational work вне
authentication critical path. Ровно на конце окна закэшированный ключ уже не
подходит, и побеждает typed unavailable error.

## Мост

```go
authn := authjwt.Authenticator(parser,
	func(_ context.Context, c MyClaims) (auth.Principal, error) {
		return auth.Claims{
			Sub:         c.Subject,
			Permissions: auth.Scopes(c.Scope),
			Attrs:       map[string]any{"tenant": c.Tenant},
		}, nil
	})
```

Отображение ваше, потому что только вы знаете, что `org` — это tenant, что
`groups` — это роли или что subject нужно префиксовать, чтобы он был уникален
между двумя издателями.

**Маппер может отказать.** Возврат ошибки отклоняет токен, который прошёл
проверку, — сюда относится «валиден, но его tenant удалён». Стройте её через
`auth.Unauthenticated`, чтобы причина не попала в ответ.

Для обычной формы токена `Standard` — это оба вызова:

```go
authn := authjwt.Standard(authjwt.HMAC(secret),
	auth.RoleMap{"editor": {"article:read", "article:write"}},
	authjwt.Issuer("https://id.example.com"),
	authjwt.Audience("articles-api"),
)
```

`authjwt.Claims` читает `sub`, `roles`, `permissions` и `scope` — оба написания
пермишена, потому что издатели расходятся в том, какое присылать, — а `Attr`
достаёт любой другой клейм payload'а. `Standard` требует непустой `sub`: этот
principal служит ключом аудита и ownership scope, поэтому одни permissions ещё
не identity. Если издатель идентифицирует вызывающего другим claim, используйте
`New[C]` вместе с `Authenticator` и явно выведите subject в mapper.

## Любой отказ — один и тот же ответ

Неверная подпись, истёк срок, ещё не наступил, чужой издатель, чужая audience,
нет срока, не парсится, payload не лёг в `C` — всё это
`auth.Unauthenticated`, и клиент их не различит. Сообщать, какая проверка не
прошла, значит подсказывать перебирающему, что менять дальше ([[D-056]]).

Недоступный JWKS provider намеренно не входит в этот список. Он возвращает
`ErrKeySourceUnavailable` и остаётся infrastructure answer вместо сообщения
вызывающему, что его, возможно, валидные credentials неверны ([[D-078]]).

## Чего он не делает

Не подписывает, не обновляет, не ротирует ключи на стороне выпуска, не хранит
пользователей. Он читает предъявленное.

# access — кто вызывающий, и что ему можно

```go
import "github.com/frostgrove/vv/auth/access"
```

```bash
go get github.com/frostgrove/vv/auth/access
```

**Модуль:** отдельный · **Зависит от:** `vv` (auth, crud, errs, port),
`google/uuid`, `golang.org/x/crypto`

`auth` — это контракт: `Principal` и `Guard`. `access` — рабочая реализация
одного такого, как `apikey` и `authjwt`: восемь таблиц, сессионные учётные данные,
пароли на argon2id и RBAC с точечными исключениями.

Импортируйте, когда вход и авторизация должны быть строками в вашей базе, а не
claims в токене.

| Ещё | |
|---|---|
| [accessjwt](accessjwt.md) | подписанные access-токены поверх ротируемого refresh |
| [revokeredis](revokeredis.md) | список отзыва для него, в Redis |
| [accessnet](accessnet.md) / [accessgin](accessgin.md) / [accessfiber](accessfiber.md) | роуты, по модулю на фреймворк |

## Форма

Два вызова. Всё остальное собирается за вас.

```go
runtime, err := access.New(access.RuntimeSpec{
	Source: source,
	Config: cfg.Access,
	Logger: logger,
})

users, signUp, err := access.Mount(runtime, access.SubjectSpec[SignUpForm]{
	Type:      "user",
	Prefix:    "",                   // "" монтирует в /auth/login
	Directory: userDirectory,
	Normalize: strings.ToLower,
	Registrar: userRegistrar,
	Strategy:  access.OpaqueToken(),
})
```

`SubjectSpec` и есть документация: пропущенное поле — это ошибка компиляции, а
не поведение, о котором надо знать. Наружу не отдаётся ни `Store`, ни хешер, ни
аутентификатор — это те детали, у которых важны порядок и парность, и
потребитель, собирающий их руками, ошибётся так, что оно скомпилируется.

`Mount` отвечает двумя значениями, потому что у субъекта две половины разной
формы: `*MountedSubject`, который нужен любому биндингу, и `*SignUpUseCase[P]`,
несущий **вашу** полезную нагрузку регистрации. Никто её не стирает и не
восстанавливает ассершеном.

## Субъект

Здесь нигде не назван пользователь. Каждая строка указывает на **субъект** —
тип и id, ровно та форма, что у `model_has_roles` в Laravel. Хранилище за типом
— это `Directory`, который реализуете вы. Три метода, и все читают:

```go
type Directory interface {
	SubjectType() SubjectType
	Active(ctx context.Context, id uuid.UUID) (bool, error)
	Describe(ctx context.Context, id uuid.UUID) (Profile, error)
	Touch(ctx context.Context, id uuid.UUID) error
}
```

`Active` читается на каждом аутентифицированном запросе — именно поэтому
деактивация аккаунта блокирует его на следующем вызове, а не когда истечёт
сессия.

`Mount` отказывает на старте, если тип субъекта зарегистрирован дважды, если два
субъекта делят префикс и если директория отвечает не за тот тип, что в спеке.
Все три иначе всплывают в рантайме как вызывающий, аутентифицированный не тем
хранилищем.

Nil-like extension values отклоняются на той же границе. Literal nil в
`Strategy` осознанно выбирает `OpaqueToken`; interface с typed-nil стратегией
или директорией — ошибка конфигурации, а не panic на первом запросе. Literal
nil в `Registrar` осознанно убирает self-service sign-up, а typed-nil registrar
отклоняется до сборки стратегии и публикации маршрута.

## Стратегии

**Стратегия** — это то, как один вид вызывающего держит сессию. Одно значение
объявляет оба конца — что выдаётся при входе и что принимается на следующем
запросе, — потому что разведённые по разным местам они согласованы ровно до
первой правки одного из них, а отказ выглядит либо как «всех разлогинило
разом», либо как токен, выпущенный для одного типа субъекта и принятый как
другой.

| | выдаётся | проверяется | отзыв |
|---|---|---|---|
| `OpaqueToken()` | 256 случайных бит, дайджест в `sessions` | одно чтение по дайджесту | строка (allow-list) |
| [`accessjwt.Strategy(...)`](accessjwt.md) | короткий подписанный токен + ротируемый refresh | подпись, без чтения сессии | с задержкой в access TTL |
| он же с `Revocation` | " | подпись + deny-list | мгновенный, по id сессии |

`OpaqueToken` — умолчание и обычно правильный ответ. Всё, что продукт просит от
сессии, — это свойство строки: выход закрывает её, деактивация аккаунта
блокирует, снятая роль действует со следующего запроса. Цена — одно чтение на
запрос. За `accessjwt` стоит браться, когда верификатор не может дотянуться до
базы (другой сервис, другой периметр), и не раньше.

**Стратегии, чей верификатор не читает строку, сообщают о закрытии сессии.** Это
`Issued.Revocations` — `RevocationSink`, который стратегия объявляет, а `Mount`
регистрирует за её субъектом. `OpaqueToken` не объявляет ничего и не нуждается:
строка, которую его верификатор читает на следующем запросе, — это та самая
строка, которую написал выход. Подписанный токен проверяет подпись, поэтому
`revoked_at`, в который он не заглядывает, ничего не меняет: без стока выход
закрывает сессию везде, кроме того места, куда посмотрит следующий запрос. Через
сток отчитывается каждый путь закрытия сессии, включая сброс пароля
администратором за `Runtime.SetPassword`, и отчёт уходит после коммита
транзакции. Отчёт, который сток не принял, пишется в лог и не роняет уже
состоявшийся выход — и не теряется:
`Runtime.ReannounceRevocations(ctx, since)` читает строки, отозванные с этого
момента и ещё не истёкшие, и рассказывает стокам снова. Он идемпотентен, поэтому
джоба, гоняющая его раз в минуту за последний час, — правильная форма, и он
возвращает ошибку, а не логирует её: его вызывает воркер. См. [[D-072]].

`Mount` строит custom strategy на приватном candidate resolver и валидирует весь
результат `Issued` до публикации субъекта. `Issuer` и `Authenticator`
обязательны и не могут быть literal- или typed-nil. `Refresher` и `Revocations`
опциональны как literal nil; typed nil — это сломанная объявленная capability.
Ошибка `Build` или валидации не публикует directory, grants resolver,
revocation sink или mounted subject, поэтому исправленную декларацию можно
безопасно повторить.

**Проверка персубъектная, а не общая на API.** У каждого смонтированного
субъекта свой guard, и группа роутов, на которую пришёл запрос, выбирает его до
всякого парсинга:

```go
guard := users.Guard()          // верификатор этого субъекта
admin := runtime.AdminGuard()   // цепочка по объявленным стратегиям, для общих роутов
```

Обе принимают `auth.Option` — так развёртывание говорит, откуда читать
credential; см. [Куда уходят учётные данные](#куда-уходят-учётные-данные).

Деплой, выдающий один вид токенов, запускает один верификатор и отвечает «это не
валидный токен», а не 401 после нескольких неудачных попыток.

## Три вещи, которых модуль не делает

Все три — это [[D-066]], и каждая ваша.

**Не создаёт аккаунты.** На порту нет `Provision`. У вашей строки ваши колонки;
порт, достаточно тонкий, чтобы библиотека могла его описать, — это список полей,
который не подходит никому. Строку вы пишете в `Registrar[P]`, а остальную часть
регистрации библиотека делает в той же транзакции.

**Не монтирует роуты.** Под `auth/access` не импортируется ни один веб-фреймворк.
Роуты — опциональные биндинги, по модулю на фреймворк.

**Не нормализует идентификаторы.** `credentials.identifier` хранится и
сравнивается байт в байт. Адрес складывается по регистру, google-овский `sub` —
нет, и знает об этом только тот, кто выдал идентификатор. Поэтому
`SubjectSpec.Normalize` применяет библиотека с обеих сторон колонки, а правило
вы задаёте один раз.

## Регистрация

Реализуйте `Registrar[P]` над своей полезной нагрузкой. Он выполняется внутри
транзакции зачисления, поэтому дубль, отбитый вашим же уникальным индексом,
откатывает и credential:

```go
func (this *Registrar) Create(ctx context.Context, form SignUpForm) (uuid.UUID, string, error) {
	if !this.config.Enabled {
		return uuid.Nil, "", registrationClosed()
	}
	account, err := this.users.Save(ctx, &User{Email: form.Email, Name: form.Name, IsActive: true})
	if err != nil {
		return uuid.Nil, "", err
	}
	return account.ID, form.Email, nil        // id, и то, чем он будет входить
}

func (this *Registrar) Password(form SignUpForm) string { return form.Password }
```

Высокоуровневый `SignUp` владеет этой транзакцией и до единственного commit
записывает account, credential, grant default role и session. Ambient-
транзакцию он игнорирует и не возвращает credential до успешного собственного commit. Поэтому
reset или logout-all видит либо ничего от параллельной регистрации, либо вместе
её credential и session, но никогда — закоммиченный credential без session. Для
caller-owned транзакции, которая должна атомарно собрать account и credential,
но не выпускать токен, остаётся намеренно joinable низкоуровневый `Enroll`.

Добавить поле в форму регистрации — это правка `SignUpForm` и `Create`, и ничего
под `access`.

**`Role()` здесь нет, и это [[D-070]].** Что выдаёт регистрация — это строка в
`subject_default_roles`, ключом по типу субъекта: не константа и не ключ
конфигурации. И то и другое — строка, которую никто не сверяет с таблицей
`roles` до первой регистрации, где опечатка отвечает 500 постороннему человеку
через недели после деплоя. Строку сверяют в момент записи:

```go
seeder := runtime.Seeder()

seeder.EnsureRole(ctx, access.RoleSpec{
	Slug: "client", Name: "Client", System: true,
	Permissions: []auth.Permission{PermInvoiceRead},
})
seeder.SetDefaultRole(ctx, "user", "client")   // откажет сразу, если "client" нет
```

Обе операции идемпотентны и обе — для команды сида, а не для старта; см.
[Сид](#сид). Отсутствие строки не выдаёт ничего, и это то, что нужно
deployment'у «только по приглашениям».

## Заведение аккаунта администратором

У аккаунта, созданного администратором, есть профиль и нет секрета, поэтому
войти он не может, пока у access не появится credential. `runtime.SetPassword()`
— это то, что его выдаёт, и это же тот самый use case, что стоит за сбросом
пароля администратором:

```go
closed, err := runtime.SetPassword().Execute(ctx, access.SetPasswordCommand{
	Subject:  access.SubjectRef{Type: "user", ID: account.ID},
	Password: chosen,
})
```

Идентификатор берётся из директории, а не от вызывающего: администратор,
способный его выбрать, направил бы credential на свой адрес. Все сессии субъекта
закрываются, и их количество возвращается, — потому что причина делать это
обычно в том, что сессию держит кто-то ещё.

Это метод рантайма, а не значение, потому что ему нужен резолвер: вызывайте
после последнего `Mount`.

## Вход

Идентификатор уникален **в пределах** типа субъекта ([[D-067]]), поэтому вход
говорит, для какого типа он. Тип подставляет surface, из тела запроса он не
приходит никогда.

```go
response, err := users.Endpoints().SignIn(ctx, access.SignInRequest{
	Email:    form.Email,          // свёрнут через SubjectSpec.Normalize
	Password: form.Password,
}, agent)
```

Любой отказ — один и тот же отказ: неизвестный идентификатор, неверный пароль,
деактивированный аккаунт и поле длиннее того, что принимает деплой, отвечают
одинаково, а пароль проверяется против `DummyHash()`, когда credential не
найден, — чтобы и время ответа ничего не сказало.

Вход по паролю, reset/change пароля и logout-all используют один DB-backed
протокол сериализации. В одной транзакции они блокируют password credentials
субъекта по возрастанию credential id, прежде чем трогать sessions. Login
проверяет именно locking read, физически версионирует эту строку credential и
открывает сессию до освобождения блокировки. Equal-value update служит
PostgreSQL snapshot fence: reset/logout со старым REPEATABLE READ/SERIALIZABLE
snapshot либо увидит и закроет сессию, либо получит retryable serialization
error; успешно закоммитить пропуск он не может. Если первой была инвалидация,
login увидит уже закоммиченный новый secret и откажет старому паролю. В
канонической PostgreSQL-миграции update trigger также делает
`credentials.updated_at` временем последнего успешного использования/изменения
пароля; MySQL/MariaDB-схеме для такой семантики timestamp нужен аналогичный
trigger. Порядок всегда credentials → sessions. Credential id сначала читаются
без блокировок, сортируются и затем блокируются по точному primary key по одному:
протокол не полагается на то, что InnoDB secondary-index scan превратит SQL
`ORDER BY` в физический порядок захвата блокировок.

### Чем ограничена цена входа

Перед хешированием стоят три вещи, и по умолчанию включены только две последние
([[D-089]]).

```go
runtime, err := access.New(access.RuntimeSpec{
	Source: source,
	Logger: logger,
	Config: cfg.Access,
	Protection: access.Protection{
		Limiter:  access.DefaultMemoryLimiter(),
		Observer: metrics,
	},
})
```

| Шов | Что делает | Что поставляется |
|---|---|---|
| `AttemptLimiter` | `Admit` до попытки, `Record` после | `NewMemoryLimiter(AttemptPolicy{…})` и `DefaultMemoryLimiter()` с дефолтами |
| `AttemptObserver` | получает каждое `succeeded`, `failed` и `refused` | ничего: телеметрия ваша |
| `BulkheadHasher` | ограничивает параллельную работу Argon2 | `NewBulkhead(inner, permits, queue)` и `Bulkhead(inner)` — `min(NumCPU, 4)` разрешений и очередь в восемь раз больше |

`MemoryLimiter` считает по `(тип субъекта, идентификатор)` и по IP внутри одного
процесса. Для одного инстанса это то, что нужно, для четырёх — нет: реализуйте
`AttemptLimiter` поверх того, что общее у реплик, и предоставьте его — в
`accessfx` вся проводка сводится к тому, чтобы дать графу `access.AttemptLimiter`.
Отказ — retryable fault с кодом `too_many_attempts`; лимитер, который не смог
записать, попадает в лог и никому не отказывает.

`Argon2Hasher.Verify` читает сохранённую PHC-строку по точной грамматике и с
границами на каждый параметр — память 8 КиБ..1 ГиБ, 1..16 раундов, минимум один
поток, соль 8..64 байта, дайджест 16..64 байта — и на всё прочее отвечает
`ErrSecretFormat` ([[D-089]]). Стоимость проверки приходит из колонки, и два
значения, которые эта колонка может содержать, кладут процесс, а не вход: ноль
раундов и дайджест нулевой длины паникуют внутри `argon2.IDKey`. Нечитаемый хеш —
это fault, а не несовпадение, поэтому обрезанная строка не выглядит неверным
паролем.

Bulkhead оборачивает тот хешер, который `Runtime` строит себе сам. Хешер,
переданный в `RuntimeSpec.Hasher`, остаётся вашим нетронутым — вместе с
bulkhead, если он вам нужен. Работа сверх очереди отклоняется как `overloaded`, а
не встаёт в неё: всплеск входов против Argon2 с 64 МиБ на хеш — это ровно то,
как машина перестаёт отвечать вообще на всё.

Пользовательский `SessionIssuer` вызывается внутри транзакции, которой
владеет access use case, даже если context несёт ambient executor. Он обязан
использовать переданный context для записей в access store и вернуть credential
как данные: доставка происходит только после успешного commit `Execute`.
Необратимый внешний side effect внутри `Issue` находится вне гарантий rollback.

Use case, закрывающие сессии, тоже владеют своей транзакцией: JWT
deny-list уведомляется только после её commit. Внешняя application-
транзакция не откладывает и не откатывает login/logout; для атомарной
композиции обычной регистрации остаётся намеренно joinable `Enroll`.

## Куда уходят учётные данные

У сессии две половины с противоположным сроком жизни, и куда каждой из них идти,
зависит от того, кто вызывает. Поэтому это решает запрос — одним заголовком, — и
одна поверхность обслуживает и браузер, и нативный клиент ([[D-075]]).

```go
handler := accessfiber.New(users, accessfiber.Delivering(accesshttp.Cookies{
    Prefix: "/api/v1",   // где смонтирован этот API
    Secure: true,        // false — только на машине разработчика с http://localhost
}))
```

| `X-Auth-Delivery` | access-токен | ротационный credential | кто просит |
|---|---|---|---|
| `cookies` | HttpOnly-кука | HttpOnly-кука | браузер |
| `refresh-cookie` | тело | HttpOnly-кука | страница, которая шлёт свой заголовок |
| `body` | тело | тело | нативный клиент, утилита командной строки |

**Молчание берёт самый закрытый вариант из доступных** — обе куки там, где они
настроены, и тело там, где нет. Браузер, забывший попросить, всё равно остаётся
браузером, который не может прочитать свои учётные данные; нативный клиент,
забывший попросить, получает пустое тело и нерабочую сессию — отказ, который
видно сразу. Значение, которого никто не определял, — это `invalid_enum`, а не
откат к умолчанию; и то же самое — просьба о куке там, где куки не настроены.

**Что ушло в куку, уходит из тела**, а что ушло в тело — вычищает куку, в которую
не пошло. Две копии одного секрета — на одну больше, чем нужно, а протухшая
access-кука хуже: guard, читающий куки, предпочитает её заголовку, и страница со
свежим токеном продолжила бы действовать от имени сессии, которую только что
заменила.

**Ротация — не выбор.** Ротационный credential возвращается тем каналом, которым
пришёл, что бы ни просил запрос. Скрипт, внедрённый в страницу, не может
прочитать HttpOnly-куку, но может заставить браузер её отправить, — и эндпойнт,
уважающий «верни в теле», отдал бы этому скрипту credential, годный неделями и с
чужой машины. Что запрос всё ещё решает — это access-токен.

Без `Delivering` все учётные данные едут в теле, а запрос, просящий куку,
отклоняется. Это честный ответ развёртывания, которое ещё не решило, какими
должны быть `Secure` и `SameSite`.

### Что решает библиотека, а не вы

| | |
|---|---|
| имена | `access` и `refresh` с префиксом самого субъекта — `staff_access`. Иначе два вида вызывающих на одном хосте перетирали бы друг другу access-куку: она ограничена всем API, а не одним эндпойнтом |
| пути | access-кука — на `Cookies.Prefix`, ротационная — только на эндпойнт ротации этого субъекта. Credential, прикладываемый к каждому запросу, попадает в каждый лог и прокси перед API |
| `HttpOnly` | всегда. Кука с учётными данными, которую читает скрипт, — это то, ради чего всё и затевалось, а опция «выключить» — это опция, которую кто-нибудь найдёт |
| `SameSite` | `Strict`, если `Cookies.SameSite` не сказал иного. `None` без `Secure` роняет старт: браузер такую куку выбрасывает, и каждая сессия обрывалась бы на следующем запросе, ничего не написав ни в один лог |

### Кука — это ambient authority, поэтому запись говорит, откуда она пришла

Куку браузер прикладывает сам — это полномочие, которое страница, вызвавшая
запрос, читать не обязана уметь. `SameSite` сужает, какие страницы могут такой
запрос вызвать, и под `None` не отвечает ничего, поэтому поверхность проверяет
сам запрос: небезопасный метод, одна из собственных кук этого деплоя на запросе и
отсутствие заголовка `Authorization` — это запрос, который обязан сказать, откуда
он пришёл.

```go
accesshttp.Cookies{
    Prefix:    "/api/v1",
    Secure:    true,
    SameSite:  accesshttp.SameSiteNone,
    CrossSite: accesshttp.CrossSite{Origins: []string{"https://app.example"}},
}
```

| | |
|---|---|
| `Sec-Fetch-Site: same-origin` или `none` | обслуживается: браузер уже сказал, что запрос отсюда |
| `Origin` из `CrossSite.Origins` | обслуживается: фронтенд, под который этот деплой и сделан |
| всё остальное, включая полное отсутствие `Origin` | `403`, код `cross_site_request` |
| заголовок `Authorization` | обслуживается без проверки — заголовок не ambient |
| `GET`, `HEAD`, `OPTIONS`, `TRACE` | обслуживается без проверки |
| ни одной нашей куки на запросе | обслуживается без проверки |

`CrossSite.Unsafely` — отказ от проверки: написанная причина выключает её для
деплоя, чья защита от CSRF стоит в другом месте. Там предложение, а не `bool`,
чтобы причину можно было прочитать потом.

### Другой конец: guard, который читает куку

Обе половины в куках означают отсутствие заголовка `Authorization`, поэтому
guard'у надо сказать, где смотреть. Это одна опция, и она откатывается на
заголовок — так что один и тот же guard обслуживает и браузер, и нативный клиент:

```go
guard := users.Guard(authhttp.Cookie(accesshttp.For(users).AccessCookie()))
admin := runtime.AdminGuard(authhttp.Cookie(accesshttp.Table{}.AccessCookie()))
```

Под `accessfx` та же опция передаётся в `Module`, который отдаёт её admin-guard'у.
Забыть её — это вход, который выглядит совершенно успешным, и 401 на всём, что
после него.

## Объявление прав

Модуль объявляет то, что сам и проверяет, рядом с кодом, который это делает:

```go
runtime.Declare(access.ModuleGrants{
	Module:      "billing",
	Permissions: []access.PermissionDef{{Code: PermInvoiceRead, Name: "See invoices"}},
	Roles:       map[auth.Role][]auth.Permission{"accountant": {PermInvoiceRead}},
})
```

`runtime.Sync(ctx)` на старте, до того как сервер начнёт принимать запросы. Он
добавляет и никогда не удаляет, и пересчитывает `admin` так, чтобы тот держал
всё — включая права, объявленные после его создания.

## Сид

Два прохода, и это намеренно не один.

| | `runtime.Sync(ctx)` | `runtime.Seeder()` |
|---|---|---|
| что пишет | то, что объявил **код**: права, роли из `ModuleGrants`, `admin` | то, что решил **продукт**: какие роли есть у этого deployment'а и что выдаёт регистрация |
| когда | каждый старт, до первого запроса | команда сида, когда её запустили |
| почему не наоборот | какие права существуют, следует из того, какие модули собраны | запуск на каждом старте откатывал бы правку администратора на следующем деплое |

```go
seeder := runtime.Seeder()

_, err := seeder.EnsureRole(ctx, access.RoleSpec{
	Slug: "lawyer", Name: "Lawyer", System: true,
	Permissions: []auth.Permission{PermContractRead, PermContractWrite},
})
_, err = seeder.SetDefaultRole(ctx, "user", "client")
```

`EnsureRole` создаёт роль, если слаг свободен, и доцепляет права, которых у неё
нет. Существующую роль он **не** перезаписывает спецификацией: переименовывать
роль, которую кто-то поправил в админке, обратно в то, что написано в Go-литерале,
на каждом запуске — это то, из-за чего сид перестают запускать. Право, которого
не объявил ни один модуль, он отклоняет, а не цепляет: код, который никто не
проверяет, — это строка, которая выглядит как грант и ничего не решает.

`SetDefaultRole` резолвит слаг и не пишет ничего, если привязка уже указывает
туда же, — чтобы `updated_at` по-прежнему отвечал на вопрос «когда это меняли в
последний раз». `ClearDefaultRole` выключает её, `DefaultRole` читает обратно.

## Конфигурация

У `access.Config` теги cleanenv, поэтому держите одно поле на весь контекст:

```go
type Config struct {
	Addr   string        `yaml:"addr" env:"ADDR"`
	Access access.Config `yaml:"access"`
}
```

| Ключ | Env | По умолчанию | Что ограничивает |
|---|---|---|---|
| `session.ttl` | `ACCESS_SESSION_TTL` | `720h` | абсолютный срок, ничто его не двигает |
| `session.idle_ttl` | `ACCESS_SESSION_IDLE_TTL` | `168h` | закрывает простаивающую сессию |
| `session.touch_interval` | `ACCESS_SESSION_TOUCH_INTERVAL` | `5m` | насколько может протухнуть `last_used_at` |
| `password.min_length` | `ACCESS_PASSWORD_MIN_LENGTH` | `10` | нижняя граница, в символах |
| `password.max_length` | `ACCESS_PASSWORD_MAX_LENGTH` | `256` | верхняя граница, в байтах, проверяется до хеширования |
| `login.max_identifier_length` | `ACCESS_LOGIN_MAX_IDENTIFIER_LENGTH` | `320` | верхняя граница идентификатора, в байтах |

Длина и ничего больше: правило по составу символов сужает пространство перебора,
которое якобы расширяет. Что угодно сверх этого проверяйте в своём `Registrar`.

Обе верхние границы применяются в одном месте с обеих сторон. Регистрация
отклоняет поле сверх границы как нарушение `too_long` с именем поля; вход
отклоняет его как `bad_credentials`, потому что ничего длиннее границы
регистрации не может быть сохранённым идентификатором, а ответ не должен
подсказывать, какая половина была неверна.

`Config.Clock` ниоткуда не загружается. Это тестовый шов — иначе каждое правило
протухания здесь непроверяемо без `sleep`. И это единственные часы: выдача
сессии, признание её закрытой, отметка об отзыве и список ещё живых читают их же,
так что замороженные часы замораживают модуль целиком, а не наполовину.
`Deps.Now()` каждый раз читает `Config`, а не копию, снятую при сборке графа, и
установить вторые часы нечем: часы, которые можно подменить только на `Deps`, —
это часы, которых не увидит issuer.

## Схема

`auth/access/migrations/00001_access.sql` — скопируйте файл в свою директорию
миграций и переименуйте со своим таймстемпом. Это именно файл для копирования, а
не embed.FS: миграция — факт о *вашей* схеме, применяемый по вашему графику.

Восемь таблиц: `permissions`, `roles`, `role_permissions`, `subject_roles`,
`subject_permissions`, `subject_default_roles`, `credentials`, `sessions`.
Добавлять свои колонки безопасно — репозиторий выбирает те колонки, которые
называет его модель.

`subject_default_roles` уникальна по `subject_type` — у одного вида вызывающего
один дефолт, — а её `role_id` объявлен `ON DELETE RESTRICT`: удаление роли,
которую выдаёт регистрация, отклоняется, а не превращается молча в «новые
аккаунты не получают ничего».

`credentials` уникальна по `(subject_type, provider, identifier)`: два
независимых домена могут оба знать `ops@example.com` ([[D-067]]). У неё есть
второй, частичный уникальный индекс — `(subject_type, subject_id) WHERE provider
= 'password'`, — потому что у аккаунта один пароль. Регистрация второго
отклоняется как конфликт, а reset или change, нашедший больше одного, отказывает,
а не выбирает. Перед добавлением этого индекса в работающую схему дубликаты надо
найти:

```sql
SELECT subject_type, subject_id FROM credentials
WHERE provider = 'password' GROUP BY 1, 2 HAVING count(*) > 1;
```

`subject_type`/`subject_id` не может быть внешним ключом, и файл прямо об этом
говорит: на уровне базы ничего не удаляет гранты субъекта, когда субъект
исчезает. Деактивируйте вместо удаления — за остальное отвечает директория.

## accessfx — проводка через fx

```go
import "github.com/frostgrove/vv/auth/access/accessfx"

fx.Options(
    accessfx.Module(configuration.Access),
    fx.Provide(
        accessfx.AsSubject(mountUsers),
        accessfx.AsGrants(whatUsersMayDo),
    ),
)
```

**Модуль** — тянет uber/fx, поэтому потребитель, который собирает контекст руками,
никогда его не резолвит ([[D-074]]).

| | |
|---|---|
| `Module(config, guardOptions…)` | runtime, резолвер, админский guard, три сервиса, административный сброс пароля и синхронизация на старте |
| `AsSubject(ctor)` | смонтированный субъект попадает в группу |
| `AsGrants(ctor)` | `access.ModuleGrants` попадает в группу |
| `Registered` | обе группы как параметр-объект `fx.In` |
| `Protection` | необязательные `access.AttemptLimiter` и `access.AttemptObserver`, которые граф запрашивает |

Дайте графу `access.AttemptLimiter` — скажем, поверх Redis, — и runtime будет
построен с ним; не дайте ничего — входы не ограничены, и это тот же дефолт, что у
`access.New` ([[D-089]]).

**Ради выражения порядка это и существует.** Всё, что обязано знать про каждый
субъект — резолвер, админский guard, сброс пароля, — зависит от `Registered`,
поэтому fx не может собрать ни одно из них, пока не отработал каждый вкладчик.
Guard, собранный до последнего `Mount`, проверял бы часть форматов и молча
отказывал остальным; юзкейс, собранный рано, паниковал бы на первом вызове — в
точке, где проводка выглядит законченной.

Отсутствие субъектов — это ошибка конфигурации, а не пустой деплой: каждый запрос
резолвился бы в principal без профиля, а каждый вход отказывал бы по причине,
которую никто не найдёт. Отклоняется на проводке.

Он не монтирует **ни одного маршрута** и не называет **ни одного типа субъекта**
([[D-066]]), и не предоставляет `port.Fields`: где именно надо зарегистрировать
`AuthBodyPaths`, зависит от транспорта, а `port.Fields` в графе столкнулся бы со
следующим модулем, которому понадобится свой ([[D-043]]).

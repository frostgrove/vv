# probe — не первое нарушение, а все

```go
import "github.com/frostgrove/vv/crud/probe"
```

**Модуль:** корневой · **Зависит от:** `crud`, `errs`, `catalog`

База данных сообщает о нарушениях по одному: первое же ограничение, до которого
дошло выполнение, обрывает запрос. Клиент исправляет его, отправляет снова — и
узнаёт про следующее. `probe.Full` выполняет **один дополнительный запрос** —
по одному булеву столбцу на каждое ограничение, которое могла нарушить запись —
и сообщает об остальных сразу.

Вы не вызываете это напрямую. [faults](faults.md) подключает это в репозиторий.

---

## Во что это превращает ответ

Без него форма с тремя проблемами — это три круговых обращения:

```json
{ "errors": { "validation": [ {"field": ["email"], "error_code": "unique"} ] } }
```

С ним — одно:

```json
{ "errors": { "validation": [
  {"field": ["email"],  "error_code": "unique"},
  {"field": ["org_id"], "error_code": "foreign_key"},
  {"field": ["code"],   "error_code": "restrict"}
] } }
```

## Подключение

```go
cat, err := catalog.Load(ctx, db)
if err != nil { log.Fatal(err) }

docs := Docs.Bind(db, faults.Enrich[Doc, int64](
    faults.WithProbe(probe.Full(cat)),
    faults.WithProbeError(func(op string, err error) {
        log.Printf("the %s probe failed: %v", op, err)   // справочно. Логируйте, никогда не рендерите
    }),
))
```

`probe.Simple()` — второй обработчик: он оборачивает и возвращает, не
выполняет никакого запроса и ничего не находит. Это честный ответ там, где
второй запрос не бесплатен.

## Два правила, которые не выразить сигнатурой

Оба — [[D-042]], и оба важны, если вы строите поверх этого.

- **`Fault` никогда не `nil`, если запрос его нёс.** Обработчик, который ничего
  не нашёл, упёрся в лимит или провалился совсем, всё равно возвращает то, что
  сказал драйвер. Подавить это значило бы превратить правдивый 409 в тишину.
- **Ошибка носит справочный характер.** Она для лога. Вызывающий код, который
  превратил бы её в ответ, позволил бы самой ненадёжной части конструкции
  понизить корректный 409 до непрозрачного 500 — а она *действительно*
  ненадёжна, потому что заново привязывает значения из уже провалившегося
  запроса.

**Источник истины — индекс, проба лишь советует.** Ничего никогда не
придумывается.

## Что проверяется

Три кода, и никаких других.

| Код | Как |
|---|---|
| `unique` | `EXISTS` по этой таблице, по одному члену на каждый уникальный ключ, которого касаются собственные столбцы записи. Обновление исключает свою же строку |
| `foreign_key` | `NOT EXISTS` по родителю, под защитой условия, что все ссылающиеся столбцы не null |
| `restrict` | **входящее** направление: обновление, меняющее столбец, на который указывает FK другой таблицы, под `ON UPDATE RESTRICT`/`NO ACTION`, когда дочерние строки всё ещё указывают на старое значение |

`restrict` требует входящей половины схемы, которую никакой запрос к
`catalog.Catalog` выразить не может — поэтому каталог, не являющийся
`catalog.Referrers`, просто не производит термов restrict.

### И одна проверка вовсе без запроса

**Дубликаты внутри payload**: две строки одной вставки с одинаковым email.
База сообщит об одной, но неправильны обе, а найти их — дело хеш-таблицы.
Это безусловно корректно, потому что это факт о payload, а не о базе данных —
и это лишь сужает результат, поскольку collation отождествляет *больше*
значений, чем побайтовое сравнение, но никогда не меньше.

## Что она отказывается проверять и почему

- **Ограничения CHECK не вычисляются.** Каталог хранит CHECK только как текст
  движка, а форма этого текста разная у каждого движка —
  `CHECK ((qty > 0))` у PostgreSQL, голое условие из
  `information_schema`, и вовсе ничего у SQLite. Восстановить выражение из
  этого текста — значит разбирать DDL, а это [[D-041]] прямо запрещает.
- **NOT NULL, длина, диапазон и принадлежность enum не проверяются** — ни в Go,
  ни в SQL. MySQL сам приводит аргумент: под `STRICT_TRANS_TABLES` слишком
  длинное значение — это ошибка, а без него то же значение — предупреждение и
  тихое усечение. Любое правило, заново выведенное здесь, было бы верным на
  одном развёртывании и неверным на другом, которое отсюда не видно.
- **Режима предварительной проверки не существует.** Проверка *до* записи
  стоит запроса на каждом счастливом пути, а окно TOCTOU между проверкой и
  вставкой делает чистый ответ ложью в условиях конкурентности.

Любой пробел в этом — шанс сообщить о нарушении, которого сервер бы не поднял,
а это как раз то направление, которое [[D-042]] исключает.

## Матрица транзакций

PostgreSQL отравляет всю транзакцию при ошибке ограничения, и ничего не
выполняется до `ROLLBACK` или `ROLLBACK TO SAVEPOINT`.

| запись выполнялась… | PostgreSQL (отравляет) | MySQL · MariaDB · SQLite |
|---|---|---|
| вне какой-либо транзакции | `Full` | `Full` |
| внутри транзакции, **открытой vv** | `Simple`, если не задан `WithSavepoints()` | `Full` |
| внутри **чужой** транзакции | `Simple`, всегда | `Full` |

Чужой транзакции savepoint **никогда** не выдаётся. У транзакции ent или gorm
свой стек savepoint'ов и свои ожидания, и `ROLLBACK TO SAVEPOINT` посреди
чужой единицы работы может отбросить работу, которую её владелец ещё не
завершил.

На какой стороне этой таблицы окажется диалект, определяет
`crud.StatementRollback`, а не его имя.

## Опции

| Опция | По умолчанию | Делает |
|---|---|---|
| `WithSavepoints()` | выкл | взять savepoint перед записью внутри открытой vv транзакции, чтобы отравляющий движок всё же мог быть проверен |
| `WithMaxConstraints(n)` | 16 | термов на запрос |
| `WithMaxRows(n)` | 50 | строк на пакет |
| `WithMaxSavepoints(n)` | 32 | на транзакцию |
| `WithTimeout(d)` | 250мс | только вокруг запроса пробы |
| `Skip(names...)` | — | исключить ограничения по имени. Отклоняется при старте, если имя ничему не соответствует |
| `WithScope(fn)` | — | сузить уникальные термы предикатом самой политики безопасности |
| `WithValues()` | выкл | поместить нарушающее значение в payload |
| `CodeOnly()` | выкл | убрать путь, оставить код |

### Лимиты, и почему они такие

Лимит без числа — не лимит.

- **16 ограничений.** Релевантность уже сужена записанными столбцами, поэтому
  шестнадцать *релевантных* ограничений на одной записи — уже патология.
- **50 строк.** Пакетная проба — это один плоский запрос с одним термом на
  ограничение на строку, так что 50 × 16 — это 800 столбцов в одной строке
  результата — с запасом внутри лимита PostgreSQL в 1664 столбца, и это
  ограничивает враждебный пакет из 10 000 строк фиксированной стоимостью.
- **250мс.** Запись уже провалилась, а клиент ждёт.
- **32 savepoint'а.** Кеш subxid PostgreSQL переполняется на 64 на
  верхнеуровневую транзакцию, а переполнение вынуждает к поиску в
  `pg_subtrans` **каждого читателя в кластере**. Половина обрыва.

Достижение любого из лимитов выставляет на `Fault` флаг `Partial`, и envelope
рендерит `"partial": true`. Частичный ответ, выданный за полный, хуже того
единственного нарушения, которое он заменил.

## Оракул и четыре средства защиты

Проба обращается к строкам, которые вызывающий может быть не вправе видеть, и
ответ о нарушении unique раскрывает, что значение существует. Четыре средства
защиты, и **ни одно не закрывает утечку полностью**:

1. значение не попадает в payload, если это не разрешено `WithValues()`;
2. `Skip(name)` полностью исключает ограничение;
3. `WithScope(fn)` сужает уникальные термы тем же предикатом, которым политика
   безопасности сужает чтение;
4. `CodeOnly()` убирает путь и оставляет только код.

`WithScope` сужает **только** уникальные термы, и это ограничение не
недосмотр: терм foreign-key читает родительскую таблицу, а терм restrict —
дочернюю, собственный предикат скоупа модели не называет ни ту, ни другую, и
предикат над не той таблицей просто не скомпилировался бы. Там, где это
важно, средством защиты служит `Skip`.

## Отказывает при старте приложения, а не во время запроса

`probe.Full` читает каталог и **никогда не читает схему базы данных во время
запроса**, поэтому отказывает уже при объявлении:

| Ошибка | Значит |
|---|---|
| `ErrUnknownTable` | каталог не знает эту таблицу |
| `ErrKeyDoesNotIdentify` | столбец первичного ключа сам по себе не идентифицирует строку |
| `ErrUnknownConstraint` | `Skip` называет несуществующее ограничение |

`ErrKeyDoesNotIdentify` — отказ на составном ключе. У `crud.Schema` одно поле
`PK`, поэтому составной ключ необъявим — достижимый вред: модель, чьё
единственное поле `pk` отображено на таблицу, чей *настоящий* ключ составной,
где собственный `WHERE pk = ?` репозитория уже неверен. Объявление отказывает,
если каталог не подтверждает, что столбец ключа сам по себе идентифицирует
строку.

## Детерминизм

Термы порождаются в порядке каталога, строки — в порядке payload, а ответ
сортируется через `errs.SortViolations` перед возвратом. Один и тот же
провалившийся запрос дважды даёт один и тот же список ([[D-014]], уровнем
выше).

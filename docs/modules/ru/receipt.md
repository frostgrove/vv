# event/receipt — что случилось с операцией, которую никто не подтвердил

```go
import "github.com/frostgrove/vv/event/receipt"
```

**Модуль:** в корневом модуле. Всё его замыкание — `event`, `crud`, `errs`,
`utils` и стандартная библиотека, так что он не стоит ни одной зависимости
([[D-033]]) · **Зависит от:** [event](event.md) — ради полномочия транзакции и
потока · **От него зависят:** ничто

Команда была отправлена, соединение оборвалось, и у вызывающего на руках нет
ничего, кроме идентичности запроса, которую он выпустил до начала. `receipt` —
это долговечная строка, отвечающая на вопрос *произошла ли эта операция и что
она записала*: записанная рядом с добавлением, в собственной транзакции
вызывающего, в собственной таблице приложения.

Это не возможность хранилища. Ни одно хранилище не получает таблицы, колонки,
миграции или версии схемы: `eventpg` остаётся на `SchemaVersion = 2`,
развёртывание, которому квитанции не нужны, не разворачивает ничего, и любое
хранилище — включая то, которого этот репозиторий никогда не видел — получает
квитанции в тот день, когда его приложение напишет `Ledger`. Весь довод —
[[D-142]].

**Слово здесь не то же, что в `event.Commit`.** Commit — это токен, который
добавление отдаёт внутри сделавшего его процесса, и он этот процесс не переживает;
квитанция — строка в таблице под ключом, который выбрал вызывающий, и это
единственное, что может найти второй процесс.

---

## Что вы получаете

| | |
|---|---|
| `NewKey(raw)` | собственная идентичность вызывающего для одной операции. Рендерится как `"[operation key]"` и никогда не выдаёт своего значения |
| `Key.Value()` | единственная дверь, через которую значение выходит наружу, и она принадлежит оператору `Ledger`'а ([[D-142]]) |
| `NewFingerprint(digest)` · `ParseFingerprint(text)` | два направления `"sha256:"+hex`, так что рендеринг заморожен в пакете, который им владеет |
| `Receipt` | долговечная строка: `Key`, `Fingerprint`, `Stream`, `First`, `Last`, `Complete`, `RecordedAt` |
| `Ledger` | собственная таблица приложения: `Transaction`, `Claim`, `Complete`, `Find`, `Horizon` |
| `Once(ctx, spec, work)` | заявка, решение, добавление, завершение — порядком владеет вызов |
| `Claim(ctx, spec)` | дверь для ручной сборки, для вызывающего, который обязан отвечать на повтор иначе |
| `Held` | `Verdict()` · `Receipt()` · `Complete(ctx, commit)` |
| `Verdict` | `Recorded` · `Repeated` · `Collided` |
| `Resolve(ctx, spec)` | что произошло, из другого процесса |
| `Standing` | `Found` · `Incomplete` · `Unresolved` · `Expired` |
| `ErrSpec` · `ErrCollision` · `ErrIncomplete` · `ErrLedger` | четыре сигнальных ошибки |

### Форма, которую принимает команда

```go
key, err := receipt.NewKey(request.Header.Get("Idempotency-Key"))
if err != nil {
	return err
}

err = crud.InNewTx(ctx, source, func(ctx context.Context) error {
	state, at, err := repo.Load(ctx, id)
	if err != nil {
		return err
	}
	changes := decide(state, command)

	print, err := repo.Digest(at, changes...)     // байты, которые записало бы это добавление
	if err != nil {
		return err
	}
	fingerprint, err := receipt.NewFingerprint(print)
	if err != nil {
		return err
	}

	held, err := receipt.Once(ctx, receipt.ClaimSpec{
		Ledger:      ledger,
		Store:       store,
		Key:         key,
		Fingerprint: fingerprint,
		Stream:      at.Stream(),
	}, func(ctx context.Context) (event.Commit, error) {
		_, commit, err := repo.Append(ctx, at, changes...)
		return commit, err
	})
	if err != nil {
		return err                                // ErrCollision и ErrIncomplete приходят сюда
	}
	answer = held.Receipt()                       // Recorded: диапазон, записанный этой попыткой
	return nil                                    // Repeated: диапазон, записанный первой
})
```

**Сначала тянитесь к `Once`.** Она выполняет работу только на `Recorded`,
выполняет её один раз, выполняет внутри транзакции вызывающего и завершает заявку
в той же транзакции. Повторённый ключ до работы вообще не доходит, так что
повторная попытка стоит одного оператора и ни одного добавления. Ручная сборка
`Claim` / `Append` / `Held.Complete` — для вызывающего, который обязан отвечать
на повтор *иначе*, чем на первую запись; каждый отказ `Claim` достижим и через
`Once`, и `TestEveryRefusalClaimHasIsReachableThroughOnce` — то, что держит это
истинным.

## Порядок: заявка, решение, добавление, завершение

Заявка — **первая**, и соблазнительный порядок теряет ровно тот случай, ради
которого всё это существует.

Запись после добавления безопасна против двух писателей на одной ожидаемой
версии — одного из них хранилище и так допустит единственным. Она **не**
безопасна против **двух повторов на двух разных ожидаемых версиях**, а это ровно
то, что делает вызывающий, не знающий исхода. Вторая попытка перезагружает,
решает на новой версии и допускается, потому что это не конфликт
конкурентности. Обе добавляют. Коллизия обнаруживается тогда, когда оба набора
событий уже в журнале.

Ничто в этом пакете не видит добавление, которое уже случилось на этом контексте,
поэтому порядок не обеспечивается проверкой. `Once` — написание, которое делает
любой другой порядок незаписываемым, и обязательство несёт она.

## Заявка — два оператора, и их порядок и есть механизм

```sql
INSERT INTO receipts (key, fingerprint, family, stream_key, recorded_at)
VALUES ($1, $2, $3, $4, statement_timestamp())
ON CONFLICT (key) DO NOTHING;

SELECT key, fingerprint, family, stream_key, first_version, last_version, complete, recorded_at
  FROM receipts WHERE key = $1;
```

Именно в этом порядке, в одной транзакции вызывающего. `won` — это количество
затронутых вставкой строк и ничто иное.

**Проигравшему отвечают тем, что прочитал `SELECT`**, колонка за колонкой. Список
`RETURNING`, привязывающий параметр там, где имеется в виду колонка, или маппер,
заполняющий структуру из запроса и перезаписывающий только те поля, которые он
знает, возвращают каждому проигравшему тот отпечаток, с которым он пришёл, — и
тогда ни один отпечаток никогда не отличается, всякая коллизия читается как
повтор, `Once` пропускает работу, а `ErrCollision` недостижим. Секция `repeat` в
`eventtest.RunLedger` заявляет один ключ под двумя отпечатками именно поэтому.

**Блокируется именно вставка.** Спекулятивная вставка PostgreSQL заставляет
`DO NOTHING` ждать конфликтующий незафиксированный кортеж и затем вставлять или
нет по исходу той транзакции — вот почему заявке никогда не приходится отвечать
«не разрешено», а `Resolve` приходится.

**Чтение обязано быть отдельным оператором**, потому что на READ COMMITTED второй
оператор — это второй снимок: именно это позволяет проигравшему прочитать
строку, которую победитель зафиксировал, пока проигравший ждал. Единственный
оператор, пытающийся сделать и то и другое, делит один снимок, взятый до фиксации
победителя, и отвечает проигравшему нулём строк — это ни победа, ни повтор, и
здесь такое отвергается через `ErrLedger`. `SELECT`, поставленный **первым**,
хуже: он ничего не видит, его вызывающий решает, что он первый, и добавляет, а
ноль от вставки приходит уже после решения.

**Ничто здесь не выбирает уровень изоляции** ([[D-126]]). Уровень решает,
*как падает проигравший*, а не может ли он добавить:

| Уровень | Проигравший | Кто повторяет |
|---|---|---|
| READ COMMITTED | блокируется на индексе, затем читает строку победителя | этот вызов, отвечая `Repeated` |
| REPEATABLE READ · SERIALIZABLE | блокируется, затем SQLSTATE `40001` — **вся** единица вызывающего откатывается: заявка, добавление и завершение вместе | собственный повтор вызывающего, через `crud.InNewTx` |

`40001` в этом дереве уже повторяемый, так что у повтора есть дом, и повтор —
**вызывающего**: этот пакет не открывает транзакций и ничего не повторяет.

**Чем жертвует форма из двух операторов — сказано здесь, а не обнаруживается
позже:** между двумя операторами есть окно, в котором подметание по сроку
хранения могло бы удалить строку, которую вот-вот прочитает `SELECT`; это
проявляется как `won == false` рядом с отсутствующей квитанцией и отвергается
через `ErrLedger`. Горизонт короче возраста строки, записанной миллисекунды
назад, — это не горизонт, так что окно закрывается сроком хранения, а не
оператором.

`_examples/event-receipts` — **эталонная реализация** `Ledger`: эти два
оператора в этом порядке плюс завершающий `UPDATE`, горизонт на стороне SQL и
подметание. Она эталонная потому, что её прогнал живой набор проверок, а
`TestTheExampleLedgerIsTheOneTheLiveSuiteProved` сравнивает оба оператора — по
порядку и побайтно.

## Отпечаток покрывает добавление и намеренно не покрывает версию

`Repo.Digest` — это SHA-256 над кодированием с префиксами длины по составленному
потоку и по типу, ревизии и полезной нагрузке каждой записи, по порядку. Он не
делает ни одного обращения к хранилищу и ничего не пишет, и отвечает теми же
отказами, что и `Append`, — так что вызывающий, посчитавший отпечаток первым,
узнаёт о негодном добавлении до того, как что-либо заявит.

**Версии, на которой был загружен токен, в нём нет.** Повтор, пришедший в новом
процессе, загружает то, что хранилище держит *сейчас*, — а это версия, на которую
первая попытка сдвинула поток; отпечаток по версии невоспроизводим тем самым
вызывающим, ради которого механизм и существует, так что каждый повтор отвечал бы
`Collided` для операции, которой никто не совершал. Собственная проверка версии
в `Append` не тронута, и якорю место там. Якорь всё ещё читаем: для
существующего диапазона `First - 1` — это версия, на которой была решена
операция, **записанная и никем не сравниваемая**.

**Прообраз — замороженный формат.** Отпечаток читается сборкой более поздней, чем
та, что его записала, а внутри окна хранения развёртывание — обычное дело.
Перестановка полей, сужение длины, смена порядка байтов или добавление
разделяющей метки отвечают **на каждый ключ, ещё живущий в окне**, коллизией по
операции, которой никто не совершал. `TestTheDigestPreimageIsFrozen` держит
раскладку шестью золотыми векторами, а не описанием.

### Три обязательства, которые этот фреймворк проверить не может

Они сказаны здесь по той же причине, по которой три обязательства
`projection.Sequencer` сказаны на его собственной странице: ни одна дверь их не
видит, и каждое из них немо, когда нарушено.

1. **Решение обязано кодироваться в одни и те же байты под одним ключом.** Кодек,
   записывающий часы, свежий идентификатор или map в порядке итерации, кодирует
   каждый раз по-разному, а под одним ключом операции это отказ на **каждом**
   повторе, а не дублирующее добавление — `Collided`, громко и никогда не ошибочно.
   Берите такое значение из команды, из состояния или из ключа операции — так же,
   как `Sequencer` не берёт ничего из часов.
2. **Один ключ покрывает одно добавление в один поток.** `Held.Complete`
   отвергает коммит другого агрегата, что закрывает ту половину, которую он видит;
   чего он не видит — вызывающего, который под одним ключом делает два добавления
   в *один и тот же* поток. **Рецепт — ключ на добавление:** производите второй из
   первого суффиксом, которым владеете, — `NewKey(base + ":shipment")`, — так что
   у каждого добавления своя строка и свой диапазон.
3. **`Ledger` принадлежит приложению, и четыре его обязательства — его
   собственные.** Заявка — это два оператора выше именно в том порядке; горизонт
   монотонен и берётся из часов базы данных; `Find` видит только зафиксированные
   строки; `Claim` и `Complete` выполняются внутри транзакции вызывающего, а
   `Find` и `Horizon` — вне какой-либо. **Прогоните `eventtest.RunLedger` по
   своей реализации** — это опубликованный набор проверок соответствия для
   `Ledger`: семь секций, те же три слова, что и у набора для хранилища, и его
   секция `claim order` — единственное, что скажет вам о порядке двух операторов
   раньше, чем о нём скажет повтор в бою. См. [eventtest](eventtest.md).

## Три ответа у двери записи, и два из них — отказы

| `Verdict` | Когда | Что делает вызывающий |
|---|---|---|
| `Recorded` | строки не было, и эта заявка взяла ключ | выполнить работу, добавить, завершить в той же транзакции |
| `Repeated` | существует **завершённая** строка, и её отпечаток равен | ответить клиенту диапазоном из `Held.Receipt()`; не добавлять ничего |
| `Collided` | завершённая строка существует, и её отпечаток другой | **отказать** — ключ был потрачен на другую операцию |

`Collided` путешествует и как `ErrCollision`, и как вердикт, и важна именно
ошибка: вердикт — значение, которое законно отбросить, а худший компилирующийся
код — `held, err := Claim(...)`, `if err != nil { return err }`, затем `Append` —
обязан отказать, а не потратить чужой ключ. `Repeated` остаётся игнорируемым и
ловится одним вызовом позже: `Complete` отвергает вердикт, который не `Recorded`,
и собственная транзакция вызывающего откатывает вторую копию событий.
**Транзакция и есть обеспечение** — единственное, которое пакет, не открывающий
транзакций, может иметь честно.

**`ErrIncomplete` — не четвёртый вердикт.** Строка, чья заявка зафиксировалась
без завершения, не несёт вердикта вовсе, потому что состояние, из которого ничего
нельзя заключить, — это отказ, а не ответ. Повтору, которому сказали «уже
сделано» из строки с диапазоном `0..0`, сообщён успех, которого могло и не быть,
— а `0..0` это ещё и честный диапазон решения, не давшего изменений, поэтому
различителем служит `Complete`, а не диапазон.

## Четыре ответа у двери чтения, из другого процесса

```go
resolution, err := receipt.Resolve(ctx, receipt.ResolveSpec{
	Ledger: ledger,
	Store:  store,
	Key:    key,
	Issued: whenTheClientMintedIt,   // необязательно
})
```

| `Standing` | Что значит | Что делает вызывающий |
|---|---|---|
| `Found` | присутствует и завершена | ответить диапазоном из `Resolution.Receipt` |
| `Incomplete` | присутствует без диапазона — заявка зафиксировалась без добавления | **отчёт о дефекте**: через это состояние не повторяют |
| `Unresolved` | **отсутствует, и заключить нельзя ничего** | сообщить, что операция в полёте, и спросить снова позже |
| `Expired` | отсутствует и старше того, за что этот леджер отвечает | строка могла существовать и быть подметённой |

**Отсутствующая квитанция не доказывает откат** ([[D-143]]). Разрешающий на
втором соединении не видит строки по двум разным причинам — записывающая
транзакция откатилась либо **всё ещё открыта**, — и PostgreSQL не даёт ему
ничего, чтобы их различить: строки, которую можно заблокировать, нет, так что
разделяемая блокировка блокируется на пустоте. `Unresolved` — это состояние,
названное, а не угаданное.

Ограничивает его `idle_in_transaction_session_timeout` на роли приложения — это
рычаг **развёртывания**. Этот пакет не добавляет второго собственного таймаута.

**Что вызывающий делает с `Unresolved`: он не переотправляет команду.** Свежая
загрузка и свежее решение на новой версии — это *другая* операция под этим
ключом, и вторую запись ничто не поймает. Он сообщает, что операция в полёте, и
разрешает снова, когда этот таймаут истечёт.

`Resolve` отказывает внутри записывающей транзакции — любого из двух
дескрипторов: разрешение на контексте самой заявляющей транзакции читает
собственную незафиксированную строку и отвечает `Found` для операции, которая ещё
может откатиться, — а «сначала разрешить, потом решить, в одной единице» — это
обычная форма повтора, которую кто-нибудь напишет.

## Срок хранения и число, с которого начинают

`Ledger.Horizon` — это **момент не позже самой старой строки, за которую этот
леджер ещё отвечает**, по часам самой базы: `MIN(recorded_at)` либо
`now() - retention`, вычисленный в SQL для таблицы, которая может быть пуста.
Никогда не часы, прочитанные в процессе леджера.

Асимметрия намеренна. Ответить моментом **старее** истины — соответствует
контракту и стоит вызывающему одного лишнего `Unresolved`; ответить **новее** —
не соответствует, потому что подметённая строка тогда читается как та, которой
никогда не было. Леджер, отвечающий нулевым моментом, заявляет, что держит всё и
навсегда, — а это ровно то, чем является таблица без подметания.

**Сколько хранить строки: срок хранения обязан превышать самое длинное окно, в
котором клиент может предъявить тот же ключ снова.** Для HTTP-ключа
идемпотентности это окно по соглашению — **24 часа**, и с него начинает
развёртывание с браузерными клиентами. Развёртывание, чьи повторы принадлежат
рабочему процессу, а не браузеру, ставит вместо этого таймаут того процесса:
число — свойство вызывающего, а не этого пакета. **Фреймворк не подметает
ничего**; подметание — приложения, и `_examples/event-receipts` запускает его
периодической задачей `jobs`.

## Из каких часов берётся каждый момент

| Момент | Часы |
|---|---|
| `Receipt.RecordedAt` | база данных леджера — `statement_timestamp()`, никогда не связанный параметр |
| `Ledger.Horizon` | база данных леджера, в SQL |
| `ResolveSpec.Issued` | **собственные** часы вызывающего, и иными они быть не могут |

Так что межчасовое сравнение ровно одно — `Issued` против `Horizon`, — и его
погрешность равна расхождению между разрешающим хостом и базой. Оно решает только
между двумя **не**-заключениями: часы вызывающего, отстающие от базы, отвечают
`Expired` для операции в полёте, а спешащие — `Unresolved` для подметённой
строки. Ни то ни другое не является ложным `Found` и ни то ни другое — ложным
«этого не было».

`Issued` **необязателен**, и нулевой момент получает `Unresolved`, а не отказ:
у HTTP-обработчика с повторённым ключом идемпотентности есть ключ и нет момента, а
отказ здесь отправляет его к `time.Now()`, который позже любого горизонта и
отключает `Expired` навсегда без единой ошибки где-либо. В его отсутствие
`Resolution.Horizon` несёт момент леджера, чтобы вызывающий сделал сравнение с
датой, которая у него есть.

## `receipt` или `jobs.EnqueueOnce`?

В репозитории два механизма отвечают на «один и тот же ключ предъявили дважды»
триадой создано / существует-с-тем-же-содержимым / конфликт, и они сошлись к этой
триаде, а не заимствовали её друг у друга: это всё, на что может ответить
ключ идемпотентности по содержимому.

**Тянитесь к `receipt`**, когда вопрос — *что случилось с этой операцией* и ответ
обязан быть читаемым позже, **по ключу, из другого процесса**. **Тянитесь к
`jobs.EnqueueOnce`** ([[FL-035]]), когда вопрос — *не запланирована ли эта работа
уже* и ответ нужен только в момент планирования.

Решают три различия: задача — это строка, которая **будет выполнена**, с арендой,
счётчиком попыток и жизненным циклом очереди недоставленных, тогда как квитанцию
никто не исполняет; ключ намерения задачи — **хеш**, чей прообраз не хранится и о
котором потом ничего не спросишь; и квитанция записывает то, что добавление
**произвело**, — на строку, после добавления, в той же транзакции. [[D-142]]
разбирает сравнение посимвольно.

## Чем это не является

- **Не дедуплицирующий `Append`.** `Store.Append` не изменён и не изменится:
  внести ключ в контракт хранилища значило бы стоить каждому хранилищу колонки,
  миграции, версии схемы и секции соответствия ради возможности, которая
  развёртыванию может быть не нужна.
- **Не проигрывание доменного решения.** На `Repeated` вызывающий отвечает из
  записанного диапазона; ничто здесь не предлагает те же факты заново на той
  версии, которую хранилище держит теперь.
- **Не доказательство отката.** Четвёртого положения, говорящего, что операции
  точно не было, нет; вариант через `pg_current_xact_id` / `pg_snapshot_xmin` был
  спроектирован и отвергнут — вместе с его ценой — в [[D-143]].
- **Не вторая таблица долговечных намерений.** Квитанция — долговечная запись
  внутри собственной транзакции вызывающего, а это единственная форма outbox'а в
  этом фреймворке ([[D-118]]).
- **Не подметание.** Здесь ничто не удаляет.
- **Ничего непрерывного.** Этот пакет не открывает транзакций, не запускает
  горутин, не читает часов и не пишет ни строки лога, ни спана, ни метрики.

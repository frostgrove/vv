# health — готовность, по которой можно маршрутизировать

```go
import "github.com/frostgrove/vv/health"            // реестр и его проекции
import "github.com/frostgrove/vv/health/healthfx"   // uber/fx: группа проверок
```

**Модуль:** `health` лежит в корневом модуле — только стандартная библиотека.
`healthfx` — отдельный модуль, потому что берёт uber/fx ([[D-033]])
· **Зависит от:** ничего · **От него зависят:** ничего во фреймворке, и это
намеренно ([[D-091]])

Три ответа трём разным читателям: оркестратору, который спрашивает, не пора ли
перезапустить процесс; балансировщику, который спрашивает, слать ли сюда
следующий запрос; и дежурному инженеру, который спрашивает, какая именно
зависимость виновата.

---

## Что вы получаете

### `health` — реестр

| | |
|---|---|
| `Contribution` | одна зависимость: `Name`, `Code`, `Importance`, `Timeout`, `Probe` |
| `Probe` / `ProbeFunc` | `Check(ctx) error` — и адаптер для всего, что уже так выглядит |
| `Importance` | `Required` · `Degrading` · `Informational` · `Disabled` |
| `Spec` | `Contributions`, `Timeout`, `Freshness`, `Now` |
| `New(spec)` | явный конструктор; отказывает сразу по всем проблемам регистрации |
| `Auto(contributions…)` | то же самое с умолчаниями |
| `Registry.Live()` | `Report{Status: StatusLive}`, не выполняя ни одной проверки |
| `Registry.Ready(ctx)` | публичная проекция: статус и стабильные коды |
| `Registry.Inspect(ctx)` | операторская проекция: имена, сообщения, длительности |
| `Registry.Contributions()` | что было принято, уже с умолчаниями |
| `Report` / `Detail` / `CheckDetail` | проекции, с JSON-тегами |
| `Status` | `StatusLive` · `StatusReady` · `StatusDegraded` · `StatusDown` |
| `State` | `StatePassing` · `StateFailing` · `StateDisabled` |
| `ErrRegistration` / `RegistrationError` | отказ, с `Problems()` |
| `MaxMessageBytes` · `DefaultTimeout` · `DefaultFreshness` | `256` · `2s` · `1s` |

```go
registry, err := health.New(health.Spec{
    Freshness: 2 * time.Second,
    Contributions: []health.Contribution{
        {Name: "postgres.primary", Code: "database", Importance: health.Required,
            Probe: health.ProbeFunc(pool.Ping)},
        {Name: "redis.sessions", Code: "cache", Importance: health.Degrading,
            Probe: health.ProbeFunc(redis.Ping)},
        {Name: "clamav", Importance: health.Disabled},
    },
})
```

### `healthfx` — группа проверок

| | |
|---|---|
| `AsCheck(ctor)` | размечает конструктор, чтобы его `health.Contribution` попал в группу |
| `Registered` | группа как `fx.In`-объект параметров |
| `Spec` | `Timeout`, `Freshness` |
| `Checking(spec)` / `Auto()` | предоставляет `*health.Registry` над тем, что пришло |

```go
fx.Options(
    fx.Provide(healthfx.AsCheck(func(pool *pgxpool.Pool) health.Contribution {
        return health.Contribution{
            Name: "postgres.primary", Code: "database",
            Importance: health.Required, Probe: health.ProbeFunc(pool.Ping),
        }
    })),
    healthfx.Auto(),
)
```

Модуль отдаёт одну проверку и не знает ни про реестр, ни про транспорт, ни про
проверки соседних модулей. Два модуля с одним именем проверки — отказ на старте.

### Маршруты на Fiber

`appfiber.Health` монтирует три проекции как обычный вкладываемый маршрут, так
что загрузочный access-гейт видит их наравне со всеми. См. [app](app.md).

## Важность — ваша, а не проверяющего

Один и тот же пинг Redis обязателен в сервисе сессий и всего лишь ухудшает
работу в выгрузке отчётов. Поэтому `Contribution` несёт и пробу, и решения,
которые про неё принимает программа, и то и другое задаётся там, где программа
собирается.

По той же причине нет и не будет пакета `jobspghealth`. `Probe` — это один
метод; адаптер от драйвера к вкладу — две строки в композиционном корне, и
десять проверяемых зависимостей дают десять таких строк, а не десять пакетов.
[[D-091]].

## Liveness ничего не выполняет

`Live()` не обращается ни к одной зависимости. Liveness-проба, которая пингует
базу, перезапускает все реплики всех сервисов ровно в тот момент, когда база
тормозит, — с холодными кешами и штормом переподключений вместо плана
восстановления. [[D-090]].

## Degraded остаётся в ротации

`StatusDown` — единственный статус, на который биндинг Fiber отвечает 503.
Реплика без ухудшающей зависимости продолжает обслуживать всё, чему та не нужна,
а поскольку зависимости у реплик общие, «убрать деградировавшую» означает убрать
их все. Вместо этого в теле ответа стоит `degraded`. [[D-090]].

## Две проекции, и бедность публичной намеренна

`Ready` возвращает статус и стабильные коды тех проверок, которые его сдвинули.
Вклад без `Code` двигает статус и ничего не называет: публиковать слово
неаутентифицированным вызывающим — это решение, и по умолчанию оно
отрицательное.

`Inspect` возвращает всё — имена, важности, ограниченные сообщения,
длительности — и предназначен для маршрута за разрешением, что и делает
`appfiber.Health` полем `Operator`.

## Один проход, общий

Readiness-эндпоинт скребут все пробы, дашборды и балансировщики, какие есть в
деплое. `Freshness` переиспользует завершённый проход; параллельные вызовы
присоединяются к проходу в полёте, а не запускают свой; и проход не наследует
отмену вызывающего, так что один сдавшийся скрейпер не может уронить ответ,
которого ждут остальные ([[D-084]]). Каждая проверка при этом идёт под своим
таймаутом, а паникующая проба валит только собственную проверку.
